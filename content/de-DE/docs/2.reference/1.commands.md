Tazel startet die Werkzeuge eines Projekts als eigene Programme: Talac, `talafmt` und `talalint` für Tala-Ziele und die
Programme, die die Schritte von Plugins nennen. Die Befehlszeilen der Tala-Werkzeuge sind bei ihnen beschrieben:
[Talac](https://talac.tala.run/docs/command-line) sowie die READMEs von [talafmt](https://github.com/Progmasoft/talafmt)
und [talalint](https://github.com/Progmasoft/talalint). Die Exit-Codes sind gemeinsam: `0` Erfolg, `1` die Arbeit ist
gescheitert, `2` die Befehlszeile selbst war falsch. `tazel run` reicht den Exit-Code des Programms durch, das es
gestartet hat.

```text
tazel [output options] <command> [arguments]
```

`tazel` arbeitet am Projekt, zu dem das aktuelle Verzeichnis gehört: dem nächsten Verzeichnis nach oben, das eine
[Projektdatei](/docs/reference/project-file) enthält.

| Befehl | Was er tut |
| --- | --- |
| `tazel check` | prüft die Quellen, ohne eine ausführbare Datei zu schreiben |
| `tazel build` | baut die Ziele |
| `tazel run [-- arguments]` | baut eine ausführbare Datei und startet sie |
| `tazel test` | baut die Testsuiten und führt sie aus |
| `tazel fetch` | lädt die Abhängigkeiten vorab: Plugins aus ViGet nach `.tazel/plugins`, und scheitert, wenn ein lokales Paket fehlt oder ein ViGet-Paket deklariert ist, weil ViGet noch keine Tala-Pakete liefert |
| `tazel custom [name] [arguments]` | führt einen Befehl aus `tazel_custom.txt` aus oder listet sie auf; siehe [eigene Befehle](#eigene-befehle) |
| `tazel lock resolve` | löst die Abhängigkeiten auf und erneuert `LOCK.sqlite3` |
| `tazel lock create-dump [--path File]` | schreibt die Lockdatei als Text nach `LOCK.dump` oder in die Datei, die `--path` nennt |
| `tazel lock graph [options]` | gibt den Abhängigkeitsgraphen aus; erneuert `LOCK.sqlite3`, außer mit `--locked` |
| `tazel update` | aktualisiert die Abhängigkeiten des Systems und des Projekts |
| `tazel install [--global \| -g] Publisher.Name` | lädt ein Paket aus ViGet in das Projekt oder in das System |
| `tazel vipkg create` | schreibt für jedes Ziel ein lokales `.vipkg`, ohne zu testen oder zu veröffentlichen |
| `tazel viget push` | baut, testet und veröffentlicht das Paket zum ersten Mal in ViGet |
| `tazel viget update` | baut, testet und veröffentlicht eine neue Version des Pakets |
| `tazel viget vipkg-desc Publisher.Name` | gibt die Beschreibung (`project.description`) eines Pakets aus ViGet aus |
| `tazel fmt [-- options]` | formatiert die Quellen mit `talafmt` |
| `tazel lint [--workspace] [-- options]` | prüft die Quellen mit `talalint` |
| `tazel jvm start-daemon` | startet den JVM-Daemon, der Tazel zwischen Befehlen warm hält |
| `tazel jvm restart-daemon` | beendet den Daemon und startet ihn neu |
| `tazel jvm stop-daemon` | beendet den Daemon |
| `tazel version` | gibt die Version von Tazel aus |
| `tazel help [command]` | gibt die Hilfe aus, oder die Hilfe eines Befehls |

`tazel check` startet Talac mit `--emit=metadata` und den Compiler-Optionen der Projektdatei. `tazel build` startet es
mit `--emit=executable` und verschiebt das Ergebnis in das Ausgabeverzeichnis des Build-Modus, unter dem Namen des Ziels,
mit TalaRT daneben, wenn Talac die gemeinsame Bibliothek hinterlassen hat.

## Inkrementelle Builds

`check`, `build`, `run` und `test` starten Talac nur, wenn sich etwas geändert hat, das seine Ausgabe bestimmt: Inhalt
oder Namen der Quellen, die Einstellungen der Projektdatei oder der Compiler. Talac kompiliert die Quellen eines Ziels als
ein Programm, also ist das Ziel die Einheit: Eine geänderte Quelle kompiliert das ganze Ziel neu, und die anderen Ziele
bleiben unberührt.

```text
   Compiling Demo (Demo, 12 sources)
    Finished build in 4.21s

       Fresh Demo (Demo, 12 sources)
    Finished build in 0.31s
```

Der Inhalt zählt, Zeiten nicht, also ändert eine Datei, die nur berührt wurde, nichts. Der Compiler wird an seiner Version
und dem Inhalt seiner Dateien erkannt, und System und Architektur des Hosts zählen auch, also haben zwei Rechner mit
demselben Compiler, denselben Quellen und denselben Einstellungen dieselben Ergebnisse; der Block
[`buildCache`](/docs/reference/project-file#buildcache) der Projektdatei kann sie über einen Server teilen. Ergebnisse
bleiben in `.tazel/cache` des Projekts, standardmäßig die letzten acht jedes Ziels, also zeigt die Rückkehr zu einem
früheren Zweig oder Build-Modus `Restored` und kompiliert nichts. Ein Programm, das gelöscht oder verändert wurde, kommt
auf dieselbe Weise zurück. Die Warnungen des Laufs, der ein Ergebnis erzeugt hat, werden bei jeder Verwendung erneut
gezeigt. Ein gescheiterter Lauf hinterlässt kein Ergebnis. Die Schritte von Plugins werden nicht übersprungen: Sie laufen
in jedem Build, bevor die Quellen gelesen werden, also zählt, was sie erzeugen.

Ein Lauf sagt, warum er läuft – das Erste, was man bei einem Build fragt, der lange gedauert hat:

```text
   Compiling Demo (Demo, 12 sources) Sources/Math.tala changed
   Compiling Demo (Demo, 13 sources) Sources/New.tala added
   Compiling Demo (Demo, 12 sources) Sources/Math.tala changed, and 2 more
   Compiling Demo (Demo, 12 sources) the settings changed
   Compiling Demo (Demo, 12 sources) the compiler changed
```

Die letzte Zeile eines Befehls zählt, was der Cache gespart hat: `Finished build, 3 of 4 from the cache in 2.10s`.

`--no-cache` erledigt die Arbeit trotzdem und hält das Ergebnis dennoch fest. `.tazel/cache` kann jederzeit gelöscht
werden.

## Die Caches pflegen

| Befehl | Was er tut |
| --- | --- |
| `tazel cache status` | zeigt für jedes Projekt des Workspace, was sein lokaler Cache enthält, nach Ziel, und wie es um seinen entfernten Cache steht: Zugriff, Signaturen und ob er antwortet |
| `tazel cache clean` | entfernt `.tazel/cache` jedes Projekts des Workspace; ein entfernter Cache wird nicht berührt |
| `tazel cache push` | schickt, was die lokalen Caches enthalten und der Server nicht hat; braucht `write = true` |
| `tazel cache pull [selection]` | holt die Ergebnisse der Quellen in ihrem jetzigen Stand: der Builds, der Prüfungen, der Testsuiten und der bestandenen Suiten. Nichts wird kompiliert, also findet der nächste Build sie, auch ohne Netz |

Ein Server führt keine Liste seiner Ergebnisse, und `pull` braucht keine, weil die Schlüssel aus den Quellen folgen.
`pull` fragt jedes Ergebnis einzeln ab und zählt, was es gefunden hat: `Pulled 3 of 6 results`. Ein Ergebnis, das noch
niemand gebaut hat, ist kein Fehler.

## Ein Server für den entfernten Cache

`tazel cache serve` hält die Ergebnisse eines [entfernten Caches](/docs/reference/project-file#buildcache) in einem
Verzeichnis:

```text
tazel cache serve --directory /var/cache/tazel --port 7723 --max-size 50
```

| Option | Standard | Wirkung |
| --- | --- | --- |
| `--directory` | erforderlich | wo die Ergebnisse liegen |
| `--host` | `127.0.0.1` | die Adresse, auf der er lauscht |
| `--port` | `7723` | der Port, auf dem er lauscht |
| `--max-size` | `10` | Gigabyte, die er behält; die am längsten nicht verwendeten Ergebnisse gehen zuerst |

`TAZEL_CACHE_TOKEN` ist das Token, das ein `PUT` braucht; ohne es nimmt der Server keine Ergebnisse an.
`TAZEL_CACHE_READ_TOKEN` ist, wenn gesetzt, das Token, das ein `GET` braucht. Token bleiben aus der Befehlszeile heraus,
wo andere Benutzer sie lesen könnten.

Der Server spricht einfaches HTTP. Für andere Rechner steht er hinter einem Proxy mit TLS, weil Tazel für jede Adresse
außer diesem Rechner `https` verlangt. Er sieht in kein Ergebnis hinein; ob ein Ergebnis echt ist, entscheidet der Leser
über seine Signatur, also muss man dem Server darin nicht vertrauen.

`tazel cache keygen` gibt ein neues Schlüsselpaar für eine Projektdatei aus.

Neben `GET` und `PUT` beantwortet er `HEAD`, womit `tazel cache push` herausfindet, was schon da ist.

## Testsuiten

`tazel test` baut jede Testsuite der Auswahl und führt sie nacheinander aus:

```text
   Compiling Unit (Demo, 14 sources)
     Testing Unit (Demo)
PASS Math.Adds
Tests/Unit/MathTests.tala:9:9: expectation failed: Math.Clamp(50, 0, 10) == 9
    Math.Clamp(50, 0, 10) is 10
FAIL Math.Clamps (1 failed expectation)
2 tests, 1 passed, 1 failed
error: 1 suite, 2 tests, 1 passed, 1 failed: 'Unit' failed
```

Eine Suite wird von `talac --test` aus dem kompiliert, was die Auswahl kompiliert, den ausführbaren Dateien und den
Bibliotheken, gefolgt von den Quellen ihres `testDir`. Quellen, die im `testDir` irgendeiner Suite liegen, bleiben aus dem
ersten Teil heraus, also sieht eine Suite nie die Tests einer anderen. Der Runner wird nach `.tazel/tests/<suite>/`
geschrieben und startet im Projektverzeichnis, wo ein Test seine Dateien über Pfade relativ zum Projekt findet.

`tazel test` braucht ein Talac, das `--test` kennt. Eine Suite ohne `.tala`-Quelle ist ein Fehler, also kann ein
vertipptes `testDir` nicht still bestehen. Ein scheiternder Test hält die Suiten danach nicht auf; eine Suite, die sich
nicht kompilieren lässt, beendet den Befehl. Der Exit-Code ist `1`, wenn ein Test gescheitert ist, und auch, wenn ein
Runner endete, bevor er seine Summen geschrieben hat, was auch immer sein Exit-Code war.

Eine bestandene Suite wird nicht erneut ausgeführt, solange alles, was sie sehen kann, gleich bleibt: ihre Quellen, die
Einstellungen, der Compiler und jede Datei unter ihrem `testDir`, Datendateien eingeschlossen. Sie zeigt dann `Cached` und
zählt in den Summen mit. Eine gescheiterte Suite läuft immer erneut, und zwar zuerst, also kommt die Antwort auf das, woran
gerade gearbeitet wird, vor dem Rest. Ein Test, der etwas anderes liest, etwa eine Datei außerhalb des Projekts oder das
Netz, braucht `--no-cache`; ebenso ein Lauf in der CI, der beweisen muss, dass die Tests bestehen.

## Ziele auswählen

`check`, `build`, `run`, `test` und `lint` nehmen eine Auswahl. Ohne Auswahl arbeiten sie an allem. Für `test` wählt eine
Auswahl die Projekte und die Quellen, mit denen die Suiten kompiliert werden; jede Suite eines ausgewählten Projekts läuft.

```text
tazel build --vipkg Name          tazel build -p Name
tazel build --executable Name     tazel build -e Name
tazel build --library Name        tazel build -l Name
```

Jedes Flag darf mehrfach geschrieben werden, und die Arten lassen sich kombinieren; [Optionen schreiben](#optionen-schreiben)
zeigt die Schreibweisen. `--vipkg` behält die genannten ViPkgs; sobald `--executable` oder `--library` geschrieben ist,
bleiben nur genannte Ziele. Ein Name, der nichts auswählt, ist ein Fehler.

`tazel run` baut genau eine ausführbare Datei und startet sie, also nimmt es höchstens ein `--vipkg` und ein
`--executable` und kein `--library`. Ohne `--executable` startet es die einzige ausführbare Datei der Auswahl; gibt es
mehrere, startet es das `project.defaultRun` des einen ausgewählten ViPkg, das es setzt. Alles andere ist ein Fehler, der
die ausführbaren Dateien auflistet, und nichts wird gebaut.

```text
tazel run                    # the only executable, or project.defaultRun
tazel run -p App             # the same, within App
tazel run -p App -e Server   # Server of App
```

## Optionen schreiben

Eine Option nimmt ihren Wert in jeder dieser Schreibweisen; die kurzen funktionieren genauso für `-p`, `-l` und `-i`, die
langen für jede Option mit Wert, etwa `--path`, `--invert` und `--depth`:

```text
tazel build -eFirst -eSecond                 # short, joined
tazel build -e First -e Second               # short, after a space
tazel build -e=First,Second                  # short, after =
tazel build -e:First,Second                  # short, after :
tazel build --executable First --executable Second
tazel build --executable=First,Second
tazel build --executable:First,Second
```

Nach `=` oder `:` nimmt eine Option, die mehrfach geschrieben werden darf, eine durch Kommas getrennte Liste; direkt
angehängt oder nach einem Leerzeichen ist ein Wert ein Name, also wird `-e First,Second` abgelehnt. Der Wert einer Option,
die einmal geschrieben wird, ist alles nach dem ersten `=` oder `:`, also behält `--path=C:\Locks\old.sql` seinen
Doppelpunkt. Ein Wert nach einem Leerzeichen darf nicht mit `-` beginnen, und ein Flag ohne Wert, etwa `--locked`, lehnt
einen ab: `--locked=yes` ist ein Fehler. Ein Hinweis zu einem vertippten Wert wird so geschrieben, wie die Option
geschrieben wurde: `--color:awlyas` schlägt `--color:always` vor.

## Ausgabeoptionen

Diese dürfen überall vor `--` stehen, vor dem Befehl oder danach:

| Option | Wirkung |
| --- | --- |
| `--color always\|auto\|never` | Farben. `auto`, der Standard, verwendet sie auf einem Terminal, das sie hat; `always` auch in einer Pipe oder in der CI |
| `--progress always\|auto\|never` | der Fortschrittsbalken. `auto`, der Standard, zeichnet ihn auf einem interaktiven Terminal, das seinen Cursor bewegen kann; `always` zeichnet ihn überall |
| `--quiet` | lässt die Statuszeilen weg und den Fortschrittsbalken, sofern `--progress` ihn nicht verlangt. Warnungen, Fehler und das, wofür ein Befehl da ist, etwa der Graph von `tazel lock graph` oder die Ausgabe des Programms, das `tazel run` startet, werden weiter ausgegeben |

```text
tazel --quiet build
tazel build --color=never --progress:never
```

## Die Lockdatei als Text schreiben

`tazel lock create-dump` schreibt `LOCK.dump` neben die Projektdatei. `--path` nennt eine andere Datei, mit beliebigem
Namen und beliebiger Endung, relativ zu dem Verzeichnis, in dem `tazel` läuft:

```text
tazel lock create-dump --path Locks.sql
tazel lock create-dump --path reviews/Locks.sql
```

Der Ordner der Datei muss existieren. Tazel legt ihn nicht an: Ein vertippter Ordner scheitert mit einem Fehler, statt
einen Dump an einer unerwarteten Stelle zu hinterlassen. Ein `--path`, der einen Ordner nennt, wird ebenfalls abgelehnt.

## Der Abhängigkeitsgraph

`tazel lock graph` gibt aus, wovon jedes Projekt abhängt. Der Graph ist das, was die Lockdatei festhält, also wird
`LOCK.sqlite3` zuerst geschrieben, wenn sie fehlt oder nicht mehr festhält, was die Projektdatei deklariert. In der Wurzel
eines Workspace ist jedes Mitglied eine Wurzel des Graphen.

```text
Demo
├── Publisher.Json 1.1.0 [by feature Json]
├── Publisher.Name 1.0.0
├── Local.vipkg (local)
└── [test]
    └── Publisher.Name 2.0.0
```

Eine Abhängigkeit, die ein Feature des Projekts einbringt (`feature = "Json"`), wird gezeigt, wenn dieses Feature
eingeschaltet ist, was standardmäßig heißt, dass es eines der `defaultFeatures` des Projekts ist.

| Option | Wirkung |
| --- | --- |
| `--locked` | lässt `LOCK.sqlite3`, wie es ist; eine fehlende oder veraltete Lockdatei ist ein Fehler |
| `--all-features` | schaltet jedes Feature des Projekts ein |
| `--duplicates`, `-d` | zeigt nur die ViGet-Pakete, die in mehr als einer Version vorkommen, jedes mit seinen Abhängigen |
| `--invert Package`, `-i Package` | zeigt die Projekte, die von einem Paket abhängen |
| `--depth Levels` | gibt höchstens so viele Ebenen unter jeder Wurzel aus; `0` gibt nur die Wurzeln aus |

`--duplicates` und `--invert` können nicht zusammen geschrieben werden. Was `--invert` nennt, hängt davon ab, wie es
geschrieben ist:

| Geschrieben | Bedeutung |
| --- | --- |
| `MyPackage` | jedes Projekt unter dem aktuellen Verzeichnis, dessen `project.name` `MyPackage` ist. Seine Abhängigen sind die Projekte dort, die ein ViGet-Paket dieses Namens verwenden, von beliebigem Herausgeber, oder ein lokales `MyPackage.vipkg`. Ordner, deren Name mit einem Punkt beginnt, werden nicht durchsucht. |
| `Publisher.Name` | dieses ViGet-Paket, in jeder Version, die die Projekte deklarieren |
| `Libraries/Name.vipkg` | dieses lokale Paket. Ein Wort, das auf `.vipkg` endet, ist immer ein lokales Paket. |

Tazel lädt noch keine Pakete aus ViGet, also erscheint ein ViGet-Paket ohne seine eigenen Abhängigkeiten.

## Ausgabe

Tazel gibt für jeden Schritt eine Statuszeile aus, etwa `Compiling Demo (Demo, 3 sources)`, und schließt einen Befehl mit
der Zeit ab, die er gebraucht hat: `Finished build in 1.84s`; `--quiet` lässt sie weg. Während `check`, `build`, `run`,
`fmt` und `lint` ihre Ziele auf einem interaktiven Terminal abarbeiten, zeigt ein Fortschrittsbalken unter den
Statuszeilen den laufenden Schritt, wie viele erledigt sind und die bisherige Zeit; die Ausgabe von `talac`, `talafmt` und
`talalint` wird dann über dem Balken ausgegeben. In einer Pipe, in der CI oder auf einem Terminal, das seinen Cursor nicht
bewegen kann, wird kein Balken gezeichnet, und die Werkzeuge schreiben direkt ins Terminal; `--progress` und `--color`
wählen es anders. Das Programm, das `tazel run` startet, schreibt immer direkt. Die Ausgabe im Terminal verwendet Mordant.

## Vertippte Wörter

Ein Befehl, eine Aktion, ein Flag oder ein Zielname, der nicht bekannt ist, wird mit Exit-Code `2` abgelehnt (`1` für einen
Zielnamen, der gegen das Projekt geprüft wird). Liegt er nahe an einem bekannten, sagt ein Hinweis unter dem Fehler, was
wahrscheinlich gemeint war, mit einer kurzen Bemerkung:

```text
error: 'biuld' is not a command of tazel; write tazel help for the commands
 hint: did you mean tazel build? So close the keys almost had it.
```

Zuerst wird die Groß- und Kleinschreibung verglichen, also schlägt `Build` `build` vor; sonst ist bei einem kurzen Wort
eine Änderung erlaubt und bei einem längeren zwei, wobei zwei vertauschte Buchstaben als eine Änderung zählen.

## Argumente weitergeben

Alles nach `--` geht ungelesen an das Programm, das der Befehl startet:

```text
tazel run -- --port 8080           # to the program that was built
tazel fmt -- --check               # to talafmt
tazel lint -- --fix                # to talalint
tazel lint --workspace -- --fix
```

## Workspaces

In der Wurzel eines Workspace arbeiten `build`, `check`, `run` und `test` an jedem Mitglied. `fmt` und `lint` arbeiten an
den Standardmitgliedern, wenn der Workspace welche nennt, und sonst an der Wurzel; `tazel lint --workspace` prüft jedes
Mitglied. Im Verzeichnis eines Mitglieds ist dieses Mitglied das Projekt.

## Die Werkzeuge finden

Ein Werkzeug wird an drei Stellen gesucht, in dieser Reihenfolge: der Pfad, den `TAZEL_TALAC`, `TAZEL_TALAFMT` oder
`TAZEL_TALALINT` nennt; die Installation, aus der `tazel` läuft; die Verzeichnisse von `PATH`.

## Plugins

Ein Plugin, das ein Projekt mit `plugin("Publisher") { ... }` deklariert, wird im Plugin-Cache des Projekts gesucht,
`.tazel/plugins`. Hat der Cache keine passende Version, lädt Tazel es aus ViGet nach
`.tazel/plugins/<Publisher>/<Name>/<Version>/` und prüft seinen SHA-256 gegen den Index des Plugins; spätere Läufe
verwenden den Cache, ohne ViGet zu fragen. `TAZEL_VIGET_URL` ersetzt die Adresse von ViGet,
`https://viget.progmasoft.com`, für einen Spiegel. Siehe [Ein Plugin schreiben](/docs/extending/plugins).

`build` und `run` führen die Schritte aus, die Plugins dem Build eines Projekts hinzufügen, bevor seine Tala-Ziele
kompiliert werden; `check` und `test` führen sie nicht aus.

## Kompilierte Projektdateien

Der erste Lauf kompiliert die Projektdatei; spätere Läufe laden das kompilierte Skript aus dem Cache und werten es nur
aus. Ein Eintrag wird nur verwendet, wenn alles gleich ist, wovon die Kompilierung abhängt: Text und Name des Skripts, die
Version des Kotlin-Compilers, das JVM-Ziel, die Standardimporte und Compiler-Optionen, der Klassenpfad von Tazel und der
SHA-256 jedes Plugin-JARs. Sonst wird die Datei neu kompiliert. Ein Eintrag, der sich nicht lesen lässt, gilt als
fehlend. Der Cache behält die 256 zuletzt verwendeten Einträge.

Der Cache liegt in `TAZEL_CACHE_DIR`, wenn gesetzt, sonst in `%LOCALAPPDATA%\Progmasoft\Tazel\Cache` unter Windows,
`~/Library/Caches/Progmasoft/Tazel` unter macOS und `$XDG_CACHE_HOME/progmasoft/tazel` (`~/.cache/progmasoft/tazel`)
anderswo. Ihn zu löschen ist immer sicher.

## Der JVM-Daemon

Jedes `tazel` startet eine JVM, und die erste Projektdatei, die es auswertet, lädt den Kotlin-Compiler und den
Skript-Host. Der Daemon ist eine JVM, die läuft und stattdessen die Befehle ausführt, also werden diese Klassen einmal
geladen. Er ersetzt nicht den Cache kompilierter Projektdateien; ein Befehl im Daemon verwendet den Cache ebenfalls.

`tazel jvm start-daemon` startet ihn, sofern nicht schon einer läuft. `tazel jvm stop-daemon` lässt die Befehle, die er
gerade ausführt, höchstens eine Minute lang zu Ende laufen und beendet ihn; ein Daemon, der nicht antwortet, wird
abgebrochen. `tazel jvm restart-daemon` tut beides. Diese drei Befehle laufen immer im Prozess, der sie gelesen hat.

Solange ein Daemon läuft, geht jeder andere Befehl an ihn und gibt aus, was er selbst ausgegeben hätte. Der Daemon führt
den Befehl mit den Argumenten, dem Arbeitsverzeichnis, der Umgebung und dem Terminal des Clients aus, und die Programme,
die er startet, lesen, was im Client eingetippt wird. Jeder Befehl hat seine eigenen Projektkontexte, also können mehrere
Clients gleichzeitig bedient werden; höchstens acht Befehle laufen gleichzeitig, der Rest wartet. `TAZEL_DAEMON` sagt,
wann ein Befehl an den Daemon geht:

| `TAZEL_DAEMON` | Ein Befehl |
| --- | --- |
| `auto` (der Standard) | geht an den Daemon, wenn einer läuft, und läuft sonst direkt |
| `start` | geht an den Daemon, der zuerst gestartet wird, wenn keiner läuft |
| `off` | läuft immer direkt |

Ein Daemon dient einem Benutzer und einer Installation. Seine Dateien liegen in `TAZEL_DAEMON_DIR`, wenn gesetzt, sonst im
Verzeichnis `daemon` unter `%LOCALAPPDATA%\Progmasoft\Tazel` unter Windows, `~/Library/Application Support/Progmasoft/Tazel`
unter macOS und `$XDG_STATE_HOME/progmasoft/tazel` (`~/.local/state/progmasoft/tazel`) anderswo: ein
Unix-Domain-Socket, ein Token, eine Sperre, die Prozess-ID und das Log. Das Verzeichnis ist nur für den Benutzer lesbar,
und ein Client muss das Token vorlegen, das der Daemon dort geschrieben hat. Ein Client einer anderen Version oder eines
anderen Protokolls wird abgelehnt und führt den Befehl direkt aus; eine andere Installation, Version oder Java-Laufzeit
hat einen eigenen Daemon. Die Sperre verhindert, dass ein zweiter Daemon derselben Installation startet, und die Dateien
eines gestorbenen Daemons entfernt der nächste Client.

Der Daemon beendet sich selbst nach `TAZEL_DAEMON_IDLE_MINUTES` ohne Client, standardmäßig 180; `0` lässt ihn laufen. Sein
Heap ist auf `TAZEL_DAEMON_MAX_HEAP` begrenzt (standardmäßig `2g`) und seine Klassen-Metadaten auf 1 GiB; ein Daemon, dem
eines davon ausgeht, endet, und der nächste Befehl läuft direkt oder startet einen neuen. Wenn ein Client mitten in einem
Befehl verschwindet, werden die Programme beendet, die der Befehl gestartet hat.

## Zeiten

Mit `TAZEL_TIMINGS=1` gibt Tazel auf der Standardfehlerausgabe aus, wie lange jede Phase des Laufs gedauert hat: der Start
der JVM, der Kotlin-Skript-Host, Auflösung und Klassenladen der Plugins, Kompilieren des Skripts oder sein Laden aus dem
Cache, die Auswertung des Skripts und der ganze Befehl. Ein Befehl, der im Daemon lief, zeigt auch IPC: die Zeit zwischen
dem Senden des Befehls und seinem Ende, die der Daemon nicht mit dem Befehl verbracht hat. Der Start der JVM ist dann der
Start des Clients.

## Den Rechner ausnutzen

`check`, `build`, `run` und `test` nehmen diese Flags. Sie gehen dem
[Block `execution`](/docs/reference/project-file#execution) der Projektdatei vor, und der Block der Wurzel eines Workspace
gilt für den ganzen Workspace.

| Flag | Was es tut | Standard |
| --- | --- | --- |
| `--jobs`, `-j Number` | wie viele Compiler-Läufe und Testsuiten gleichzeitig laufen | die Prozessoren, oder `--cpus` |
| `--cpus Number` | wie viele Prozessoren der Befehl beschäftigen darf; Jobs gehen nie darüber | jeder Prozessor |
| `--memory Size` | wie viel die Jobs zusammen belegen dürfen, etwa `8g` | keine Grenze |
| `--memory-per-job Size` | was ein Job vermutlich belegt; `--memory` geteilt durch diesen Wert begrenzt die Jobs | `1g` |
| `--keep-going`, `-k` | nach einem gescheiterten Job mit den anderen weitermachen und jeden Fehler melden | anhalten |
| `--incremental`, `--no-incremental` | in einem Debug-Build ein Objekt je Quelle unter `.tazel/incremental` behalten | an, wenn talac es kann |
| `--profile File` | einen Chrome-Trace der Jobs schreiben, für `chrome://tracing` oder Perfetto | keiner |
| `--remote-executor URL` | auf einem anderen Rechner kompilieren; `TAZEL_REMOTE_TOKEN` ist sein Token | keiner |
| `--no-remote-executor` | hier kompilieren, was auch immer die Projektdatei sagt | |

Speicher und Prozessoren sind Budgets dafür, wie viele Jobs starten. Tazel misst keinen Compiler und hält keinen an, der
mehr als `--memory-per-job` belegt, und ein Job läuft immer. Talac-Läufe, die neben dasselbe Quellverzeichnis schreiben,
wechseln sich ab, weil talac seine Ausgabe neben seiner ersten Eingabe hinterlässt, also kompilieren die Testsuiten eines
Projekts nacheinander und laufen dann gleichzeitig. Eine Testsuite, die neben anderen läuft, gibt ihren Bericht aus, wenn
sie endet.

`tazel jvm start-daemon --max-heap 2g` und `restart-daemon --max-heap 2g` begrenzen den Heap des Daemons, wie
`TAZEL_DAEMON_MAX_HEAP` es tut.

### Entfernte Ausführung

`tazel remote serve` kompiliert für andere Rechner:

```text
TAZEL_REMOTE_TOKEN=... tazel remote serve --host 127.0.0.1 --port 7724 --jobs 8
```

Das Token ist erforderlich. Der Server spricht einfaches HTTP, also steht er für andere Rechner hinter einem Proxy mit
TLS, was Tazel von einer solchen Adresse auch verlangt. Er startet nur talac, auf den Quellen, die ihm geschickt wurden,
in einem eigenen Verzeichnis, und lehnt eine Anfrage ab, deren Optionen einen Ort auf seinem Rechner nennen.

Der Client schickt die Quellen und die Optionen eines Compiler-Laufs und bekommt zurück, was talac gesagt und geschrieben
hat. Ergebnisse kommen wie lokale in den Build-Cache, und Programme und Testsuiten laufen immer auf diesem Rechner. Ein
Server mit einer anderen talac-Version oder einer anderen Art von Host antwortet, dass er nicht helfen kann. In diesem
Fall, oder wenn der Server scheitert, warnt Tazel einmal und kompiliert für den Rest des Befehls hier. Wer den Server hat,
entscheidet, welche Programme Sie bekommen, also verwenden Sie nur einen, dem Sie vertrauen.

## Eigene Befehle

`tazel custom` führt Befehle aus, die in `tazel_custom.txt` stehen, gefunden im aktuellen Verzeichnis oder dem nächsten
darüber. Eine Projektdatei ist nicht nötig, die Befehle müssen nichts mit Tazel zu tun haben, und sie laufen im
Verzeichnis der Datei.

```text
# A comment to the end of the line.
<# A comment
   of several lines. #>

build-no-cache: ("tazel" 'build' `--no-cache`);
npm-dev: ('npm' 'dev');

# Several steps run in order; line breaks mean nothing.
fetch:
    ("cargo" "fetch")
    ("tazel" "fetch");

# s(...) is one command line for the shell of the host.
npm-dev-sh: s('npm dev');

fetch-sh:
    s("cargo fetch")
    ("tazel" "fetch");

# Another shell is a program like any other.
npm-dev-zsh: ("zsh" "-lc" "npm dev");

# A name may hold several words.
build no-cache: ("tazel" "build" "--no-cache");

# <N> passes the Nth argument, from 1; <*> passes all of them.
build with: ("tazel" "build" <1> <2>);
test all: ("tazel" "test" <*>);
```

```text
tazel custom fetch
tazel custom build no-cache
tazel custom build with -e MyApp
```

Ein String wird mit `"`, `'` oder `` ` `` geschrieben und hat keine Escapes, also kann er sein eigenes Anführungszeichen
nicht enthalten, und ein Backslash darin ist ein Backslash. `(...)` startet das Programm direkt mit diesen Argumenten: Es
gibt keine Shell, also bedeutet ein Wort wie `|` nichts Besonderes, und jeder String bleibt ein Argument. Unter Windows darf
das Programm ein Skript wie `npm.cmd` sein. `s(...)` nimmt genau einen String und übergibt ihn unverändert an CMD unter
Windows und an `sh` anderswo; Escapes darin liest diese Shell. Die einzige Ausnahme ist eine JVM, die unter Windows mit
`jdk.lang.Process.allowAmbiguousCommands=false` gestartet wurde: Sie kann keine Zeile übergeben, die ein `"` enthält oder
mit `\` endet, also lehnt Tazel einen solchen Befehl ab, bevor es einen seiner Schritte ausführt.

Die Wörter nach `tazel custom` gehören zum Befehl, damit nichts darin eine Option von Tazel ist. Der längste Name, mit dem
sie beginnen, ist der Befehl, und der Rest sind seine Argumente. `--` beendet den Namen: Mit den Befehlen `first` und
`first second` führt `tazel custom first second` `first second` aus, und `tazel custom first -- second` führt `first` mit
dem Argument `second` aus. Nur das erste `--` tut das, und es ist selbst kein Argument; ein späteres ist eines, und ein
Name kann es nicht enthalten. Es gibt höchstens 191 Wörter, die des Namens eingeschlossen und jenes `--` nicht. Ein Befehl
nimmt genau so viele Argumente wie sein höchstes `<N>`, oder mehr mit `<*>`. `<N>` und `<*>` sind keine Strings und stehen
außerhalb von Anführungszeichen; sie kommen nach dem Programm und können nicht in `s(...)` verwendet werden.

Ein Schritt, der scheitert, beendet den Befehl, und `tazel custom` endet mit seinem Exit-Code. Ohne Namen listet es die
Befehle auf.

## Optionen dieses Rechners

`tazel_options.txt` enthält Optionen von Tazel selbst statt eines Projekts. Tazel liest jede solche Datei im aktuellen
Verzeichnis und in den Verzeichnissen darüber: Die nächste Datei entscheidet jede Option, außer dass
`sandboxing-with-microvm: true` in irgendeiner davon gilt, damit ein Projekt eine Sandbox nicht abschalten kann, die ein
Verzeichnis um es herum verlangt. Eine Datei, die sich nicht untersuchen oder lesen lässt, beendet den Befehl, wie eine
fehlerhafte. Sie verwendet die Kommentare und Strings von `tazel_custom.txt`; jede Option endet mit `;`, was bei der
letzten fehlen darf. Eine Option, die nicht geschrieben ist, behält ihren Standard.

```text
# Run what a project brings inside a MicroVM.
sandboxing-with-microvm: true;
microvm-network: true;
microvm-memory: 2048;
microvm-cpus: "auto"
```

| Option | Wert | Standard |
| --- | --- | --- |
| `sandboxing-with-microvm` | `true` oder `false` | `false` |
| `microvm-network` | `true` oder `false` | `false` |
| `microvm-memory` | MiB von 256 bis 1048576, oder `"auto"` | `"auto"` |
| `microvm-cpus` | 1 bis 256, oder `"auto"` | `"auto"` |

`"auto"` darf mit jedem der drei Anführungszeichen geschrieben werden; Zahlen und `true`/`false` stehen ohne sie.

Mit `sandboxing-with-microvm: false` laufen die Projektdatei und ihre Plugins in der JVM von Tazel mit allen Rechten des
Benutzers, der sie gestartet hat, und eigene Befehle, der Compiler und die Werkzeuge laufen als Prozesse des Hostsystems,
nicht in einer MicroVM.

`sandboxing-with-microvm: true` verlangt, dass sie alle in einer MicroVM mit Hardware-Virtualisierung laufen, für
`tazel build` wie für `tazel custom`. Tazel hat keine MicroVM, die es starten könnte, also beendet es jeden Befehl außer
`version` und `help`, die Daemon-Befehle eingeschlossen, mit Exit-Code `1`, bevor etwas läuft, statt ihn auf dem
Hostsystem auszuführen.

## Noch nicht umgesetzt

Diese werden mit Namen und Exit-Code `1` abgelehnt:

- Bibliotheksziele: Der Compiler kann noch keine Bibliothek schreiben. Eine Bibliothek neben einer ausführbaren Datei wird
  mit einer Warnung übersprungen; eine mit Namen ausgewählte Bibliothek ist ein Fehler.
- Projekte mit Abhängigkeiten: Noch lädt nichts eine Abhängigkeit oder übergibt sie dem Compiler. `tazel lock resolve`
  hält trotzdem fest, was das Projekt deklariert.
- `tazel vipkg create`, `tazel update`, `tazel install`, `tazel viget push`, `tazel viget update` und
  `tazel viget vipkg-desc`.

`check`, `build` und `run` kompilieren für den Host. Die `targets` der Projektdatei werden festgehalten und nicht gebaut.
