Ein Projekt wird von einer Datei beschrieben, einem Kotlin-Skript, das [Tazel](/docs/reference/commands) auswertet. Tazel
liest es, findet die Quellen, die es nennt, und startet die Werkzeuge, die sie bauen; diese Werkzeuge sehen nie eine
Projektdatei.

## Auffinden

Eine Projektdatei hat einen von fünf Namen. Tazel sucht sie in dieser Reihenfolge und verwendet den ersten, der existiert;
die anderen werden nicht gelesen:

1. `BUILD.kts`
2. `BUILD.tzl`
3. `BUILD.tazel`
4. `BUILD`
5. `Tazel.build`

Die Namen unterscheiden auf jedem Host Groß- und Kleinschreibung, und alle fünf haben dieselbe Syntax. Ein Befehl arbeitet
am Projekt des aktuellen Verzeichnisses: dem nächsten Verzeichnis nach oben, das eine Projektdatei enthält.

Das Skript wird in Tazel kompiliert und ausgeführt. Ein Rechner braucht eine JRE 25 oder neuer und keine
Kotlin-Installation.

## Kleinstes Projekt

```kotlin
project {
  name = "Example"
}

sources {
  executable {
    entry = "Example.Program"
  }
}
```

```powershell
tazel run
```

Das kompiliert jede `.tala`-Datei unter `Sources/` und schreibt `build/debug/Example.exe` (ohne Endung außerhalb von
Windows).

[`BUILD.kts`](https://github.com/Progmasoft/tazel/blob/main/BUILD.kts) zeigt die ganze DSL in einer Datei. Was nicht in
dieser Datei steht, gehört nicht zur DSL.

## `project`

```kotlin
project {
  name = "Example"
  version = "0.1.0"
  stability = Stability.STABLE // STABLE, RC, UNSTABLE, BETA, NIGHTLY, ALPHA or DEV
  description = "An example project"
  authors("Leitwolf", "Helmut")
  defaultFeatures("TOML")
  defaultRun = "Server" // the executable `tazel run` runs when none is named; default: the only one
}
```

`name` ist immer erforderlich, also hat jede Projektdatei einen Block `project`. Jedes andere Feld ist für sich optional.
Mit `sources.viget.push = true` sind auch `version`, `stability`, `description` und mindestens ein Autor erforderlich;
das wird geprüft, wenn die ganze Datei gelaufen ist, also spielt die Reihenfolge der Blöcke keine Rolle. `name` ist ein
Bezeichner und `version` eine genaue Version: `A.B.C`, bei Bedarf dann `.D`, `.E` und `-METADATA`.

## `compiler`

```kotlin
compiler {
  standard = talaStandardOf(26)
  backend = Backend.LLVM
  buildMode = BuildMode.RELEASE
  werror = true
  warnings = Warnings.ALL
  wshadow = true
  xppOptimizationPasses = true
  xmmOptimizationPasses = true
  optLevel = OptLevel.O3
  staticTalaRTLibrary = true

  llvm {
    compiler = LlvmCompiler.AOT
    lto = LlvmLto.NONE
    args("-time-passes")
  }
}
```

Dieser Block gilt für Tala-Ziele; er stellt Talac ein.

| Einstellung | Werte | Standard | Compiler-Option |
| --- | --- | --- | --- |
| `standard` | `talaStandardOf(26)` | `talaStandardOf(26)` | `--standard` |
| `backend` | `Backend.LLVM` | `LLVM` | `--codegen-backend` |
| `buildMode` | `BuildMode.DEBUG`, `RELEASE` | `DEBUG` | wählt das Ausgabeverzeichnis und den Standard von `optLevel` |
| `werror` | `true`, `false` | `false` | `--warnings-as-errors` |
| `warnings` | `Warnings.ALL`, `MEDIUM`, `LOW`, `NONE` | `MEDIUM` | `--warnings` |
| `wshadow` | `true`, `false` | `false` | `--warnings=shadow` |
| `xppOptimizationPasses` | `true`, `false` | `true` | `--xpp-optimization-passes` |
| `xmmOptimizationPasses` | `true`, `false` | `true` | `--xmm-optimization-passes` |
| `optLevel` | `OptLevel.O0`, `O1`, `O2`, `O3`, `OG`, `OS`, `OZ` | `O0` für `DEBUG`, `O3` für `RELEASE` | `--opt-level` |
| `staticTalaRTLibrary` | `true`, `false`, `null` | `null` | `--static-talart-library` |
| `llvm.compiler` | `LlvmCompiler.AOT`, `ORC` | `AOT` | `--llvm-compiler` |
| `llvm.lto` | `LlvmLto.FAT`, `THIN`, `NONE` | `NONE` | `--llvm-lto` |
| `llvm.args(...)` | Argumente für LLVM | keine | `--llvm-args` |

Tazel schreibt jede Einstellung auf die Befehlszeile des Compilers, auch die mit ihrem Standardwert, also folgt ein Build
aus der Projektdatei und nicht aus den Standardwerten des gerade installierten Compilers. Eine Einstellung, die der
Compiler noch nicht ausführen kann, lehnt der Compiler mit Namen ab; siehe die
[Compiler-Referenz](/docs/reference/commands#noch-nicht-umgesetzt).

`staticTalaRTLibrary` ist die Ausnahme. `null`, oder die Einstellung wegzulassen, schreibt keine Option und überlässt die
Wahl dem Compiler; `true` schreibt `--static-talart-library=true`, das TalaRT in die Ausgabe linkt, und `false` schreibt
`--static-talart-library=false`, das es in einer gemeinsamen Bibliothek neben der Ausgabe lässt.

Keine Warnstufe schaltet `wshadow` ein. `wshadow = true` mit `Warnings.NONE` ist ein Widerspruch und wird abgelehnt.

## `buildCache`

```kotlin
buildCache {
  local {
    enabled = true
    maxEntries = 8
  }

  remote {
    url = "https://cache.example.com"
    read = true
    write = false
    token = System.getenv("TAZEL_CACHE_TOKEN")
    publicKey = "MCowBQYDK2VwAyEA..."
    signingKey = System.getenv("TAZEL_CACHE_SIGNING_KEY")
  }
}
```

| Einstellung | Werte | Standard | Bedeutung |
| --- | --- | --- | --- |
| `local.enabled` | `true`, `false` | `true` | behält Ergebnisse in `.tazel/cache` |
| `local.maxEntries` | 1 oder mehr | `8` | wie viele Ergebnisse jedes Ziels bleiben |
| `remote.url` | eine `https`-Adresse; `http` nur für diesen Rechner | erforderlich | wo die geteilten Ergebnisse liegen |
| `remote.read` | `true`, `false` | `true` | fragt den Server nach Ergebnissen |
| `remote.write` | `true`, `false` | `false` | schickt Ergebnisse an den Server |
| `remote.token` | Text oder `null` | `null` | wird als `Authorization: Bearer` gesendet; leer gilt als keiner |
| `remote.publicKey` | ein Ed25519-Schlüssel oder `null` | `null` | nur Ergebnisse, die für diesen Schlüssel signiert sind, werden verwendet |
| `remote.signingKey` | ein Ed25519-Schlüssel oder `null` | `null` | signiert, was dieser Rechner schreibt; ein Geheimnis |

Der Block ist optional, und ohne ihn hat ein Projekt nur den lokalen Cache. Der lokale Cache hat Vorrang: Der Server wird
nur nach dem gefragt, was dort nicht liegt, und was er liefert, wird lokal behalten, sofern `local.enabled` nicht `false`
ist. Was ein Ergebnis gleich macht, steht unter
[inkrementelle Builds](/docs/reference/commands#inkrementelle-builds).

Schreiben Sie Token und Signierschlüssel als Variablen, nie in die Projektdatei. Eine Projektdatei, die eine Variable mit
`System.getenv("NAME")` liest, bekommt den Wert des Befehls, auch unter dem Daemon: Unterscheidet sich der Wert von dem,
mit dem der Daemon gestartet wurde, läuft der Befehl ohne Daemon und beendet ihn, und der nächste Befehl startet einen, der
den neuen Wert sieht. Dafür muss der Name als Text geschrieben sein; ein zur Laufzeit berechneter Name wird nicht bemerkt.

Ein Ergebnis ist ein Programm, also ist ein Ergebnis von einem Server Code, den dieser Rechner ausführen wird.
`tazel cache keygen` gibt ein Paar von Ed25519-Schlüsseln aus. Geben Sie jedem Projekt den `publicKey` und den
`signingKey` nur dem, was vertrauenswürdige Quellen baut, etwa der CI auf dem Hauptzweig. Ein Leser mit `publicKey`
verwendet ein Ergebnis dann nur mit einer Signatur für diesen Schlüssel, für dieses Ziel und diesen Schlüssel des Caches,
also kann weder ein geleaktes Token noch ein kompromittierter Server ein Programm einschleusen. Ein Ergebnis ohne Signatur
gilt als fehlend, eine falsche Signatur ist eine Warnung; in beiden Fällen läuft der Compiler. Ein Leser ohne `publicKey`
vertraut dem Server und wird gewarnt, wenn er ein Ergebnis verwendet.

Der Server beantwortet zwei Anfragen, jeweils mit dem Token, falls es eines gibt. `GET <url>/<slug>/<key>` liefert das
Ergebnis als ZIP-Archiv oder `404`, wenn es nicht da ist, und `<key>.sig` seine Signatur. `PUT` auf dieselben Pfade
speichert sie und antwortet `200`, `201` oder `204`, und `HEAD` sagt für `tazel cache push`, ob ein Ergebnis da ist.
Weiterleitungen wird nicht gefolgt. Ein Server, der scheitert oder nicht erreichbar ist, ist eine Warnung: Der Build geht
weiter, und der Server wird in diesem Befehl nicht noch einmal gefragt.
[`tazel cache serve`](/docs/reference/commands#ein-server-für-den-entfernten-cache) ist ein solcher Server.

## `outdirs`, `targets` und `pml`

```kotlin
outdirs {
  release = "build/release"
  debug = "build/debug"
}

targets {
  target("x86_64-pc-windows-msvc", "aarch64-apple-darwin")
}

pml {
  enabled = true
}
```

Ausgabeverzeichnisse sind relativ zur Projektdatei und bleiben im Projekt. Ein Artefakt ist nach seinem Ziel benannt:
`build/debug/<name>.exe` für einen Build, `build/debug/<name>.talameta` für eine Prüfung.

`targets` listet die LLVM-Zieltripel, für die das Paket gedacht ist; Standard ist das Ziel des Hosts. `check`, `build` und
`run` kompilieren für den Host. `pml.enabled = false` soll die Progmasoft Library (`Progmasoft.*`) für das Projekt
schließen; die Einstellung wird festgehalten, und der Compiler hat dafür noch keine Option.

## `sources`

```kotlin
sources {
  viget {
    push = true
    exclude("build/**/*")
  }

  executable {
    name = "Example"
    srcDir = "Sources"
    exclude("Sources/Generated")
    entry = "Example.Program"
  }

  library {
    name = "ExampleLibrary"
    viPkgType(ViPkgType.TALALIB, ViPkgType.STATICLIB)
    srcDir = "Sources"
    namespace = "Example.Library"
  }

  test("Unit") {
    testDir = "Tests/Unit"
  }
}
```

Die Ziele in `sources` sind Tala-Ziele; ein Projekt, das nur von Plugins gebaut wird, braucht keine. Ein Projekt hat
beliebig viele ausführbare Dateien und Bibliotheken. `name` ist standardmäßig der Name des Projekts, also muss sich ein
Ziel eines Projekts ohne Namen selbst benennen; Namen unterscheiden Groß- und Kleinschreibung und sind innerhalb ihrer Art
eindeutig. `srcDir` ist standardmäßig `Sources`.

`entry` nennt eine Klasse über ihren Namespace: `Example.Program`. Diese Klasse stellt das parameterlose
`public static void Main()` bereit, das das Programm startet. Der Einstieg wird über Namespace und Klasse gefunden, nicht
über die Datei: Weder Dateinamen noch Verzeichnisse müssen Namespaces abbilden. Eine Bibliothek hat keinen Einstieg;
`namespace` nennt ihren Wurzel-Namespace. `viPkgType` ist `TALALIB`, sofern die Bibliothek nichts anderes sagt;
`STATICLIB` und `CDYLIB` sind die anderen Arten.

Die Quellen eines Ziels sind jede Datei unter seinem `srcDir`, deren Name genau so auf `.tala` endet. Symbolischen Links
wird nicht gefolgt. `exclude` nimmt Muster relativ zur Projektdatei, mit `/` geschrieben:

- `*` und `?` passen innerhalb eines Pfadsegments;
- ein Segment `**` passt auf beliebig viele Segmente;
- ein Muster, das ein Verzeichnis nennt, schließt alles darunter aus.

Muster werden so verglichen, wie der Host Dateinamen vergleicht: unter Windows ohne Rücksicht auf Groß- und
Kleinschreibung, sonst genau.

`test("Name")` deklariert eine benannte Testsuite; ein Name ist ein Bezeichner und darf einmal deklariert werden.
`testDir` ist standardmäßig `Tests/<name>`. Testquellen und Testartefakte kommen nie in ein `.vipkg`.
`sources.viget.exclude` entfernt weitere Dateien aus dem, was verpackt wird.

## `dependencies`

```kotlin
dependencies {
  dependency("Publisher") {
    name = "Name"
    version = "1.2.3"
    stability = Stability.STABLE
  }

  dependency("Publisher") {
    name = "Toml"
    version = "1.0.0"
    feature = "TOML"
    defaultFeatures = false
    feature("Serde") { enabled = true }
  }

  localDependency { path = "Dependency.vipkg" }

  testDependency("Publisher") {
    name = "TestDep"
    version = "0.1.0"
  }

  localTestDependency { path = "TestDependency.vipkg" }
}
```

Eine Abhängigkeit ist ein Paket aus ViGet, geschrieben als Herausgeber, Name und genaue Version. `stability` ist
standardmäßig `STABLE`. Der Herausgeber ist der Name eines Progmasoft-Kontos, mit Groß- und Kleinschreibung. ViGet ist die
einzige entfernte Quelle: Es gibt keine Liste von Repositories und keinen Weg, ein anderes zu nennen.

`feature = "TOML"` macht die Abhängigkeit optional: Sie wird nur eingebracht, wenn das Feature `TOML` dieses Projekts
eingeschaltet ist. `defaultFeatures` und `feature("Name") { enabled = true }` wählen unter den Features der Abhängigkeit
selbst.

`localDependency` nennt ein `.vipkg` im Projektverzeichnis. `testDependency` und `localTestDependency` dienen nur den
Testsuiten. Ein Paket darf je Art einmal deklariert werden; zwei unterschiedliche Deklarationen eines Pakets sind ein
Fehler.

Tazel hält die Deklarationen fest und lädt sie noch nicht, also lehnen `check`, `build` und `run` ein Projekt ab, das eine
Abhängigkeit des Builds deklariert. Die Namespaces der Standardbibliothek sind keine Abhängigkeiten und werden nie
deklariert.

## `execution`

```kotlin
execution {
  jobs = 8
  cpus = 6
  memory = "16g"
  memoryPerJob = "1g"
  keepGoing = true
  incremental = true
  profile = "build/trace.json"

  remote {
    url = "https://build.example.com"
    token = System.getenv("TAZEL_REMOTE_TOKEN")
  }
}
```

Der ganze Block ist optional, und [die Flags](/docs/reference/commands#den-rechner-ausnutzen) eines Befehls gehen ihm vor. In
einem Workspace zählt der Block der Wurzel. `profile` ist relativ zur Projektdatei. `url` nimmt `https` oder `http` nur
für diesen Rechner.

## `workspace`

```kotlin
workspace {
  members("./Server", "../Shared", "Client")
  defaultMembers("./Server", "../Shared")
  exclude("OldProject")
}
```

Jedes Mitglied ist ein Verzeichnis mit einer eigenen Projektdatei, relativ zu dieser Projektdatei geschrieben. Ein
Projekt, das nur Mitglieder sammelt, braucht einen `project.name` und keine `sources`. `defaultMembers` sind die
Mitglieder, an denen `tazel fmt` und `tazel lint` in der Wurzel arbeiten; `exclude` entfernt ein Verzeichnis aus den
Mitgliedern. Siehe [Workspaces](/docs/reference/commands#workspaces).

## `plugins`

Plugins erweitern die DSL. Sie werden in einem Block `plugins` deklariert, den Tazel liest, bevor es den Rest der Datei
kompiliert:

```kotlin
plugins {
  plugin("Progmasoft") {
    name = "CMake"
    version = "0.1.0"
  }

  localPlugin {
    path = "plugin.jar"
  }
}
```

Ein Plugin aus ViGet wird im Cache des Projekts gefunden, `.tazel/plugins`; ein Plugin, das dem Cache fehlt, wird von
`https://viget.progmasoft.com/dslplugins/tazel/<Publisher>/<Name>/` geladen. Ein lokales Plugin ist ein JAR im
Projektverzeichnis. In beiden Fällen beschreibt sich das JAR in `META-INF/tazel-plugin.properties` (Herausgeber, Name,
Version, API-Version, die Importe, die es der Projektdatei hinzufügt) und stellt genau einen Service `ProjectPlugin`
bereit. Tazel prüft Koordinate, Version, API-Version und SHA-256-Digest, bevor es das Plugin lädt; eine Datei
`<plugin>.jar.sha256` neben dem JAR legt den erwarteten Digest fest. Ein Plugin hat keine Stabilität.

Ein Plugin wird gegen das Paket `com.progmasoft.api.tazel.dsl.plugin` geschrieben. Es kann DSL-Erweiterungen
registrieren, Metadaten beitragen und einen Hook ausführen, sobald das Projekt vollständig ist. Ein Plugin ist
vertrauenswürdige Build-Logik: Es läuft mit dem vollen Zugriff der JVM, und Tazel sperrt es nicht ein.
[Ein Plugin schreiben](/docs/extending/plugins) zeigt, wie eines gebaut und geladen wird.

## Werte des Hosts und Helfer

| Name | Bedeutung |
| --- | --- |
| `OS` | das Betriebssystem, auf dem Tazel läuft: `OperatingSystem.LINUX`, `MACOS`, `WINDOWS`, `FREEBSD`, `OPENBSD`, `NETBSD` oder `UNKNOWN` |
| `ARCH` | seine Prozessorarchitektur: `Architecture.X86_64`, `AARCH64`, `ARMV7H`, `RISCV64` oder `UNKNOWN` |
| `panic(message)` | beendet die Auswertung; der Befehl scheitert mit der Meldung |
| `eprint(value)` | schreibt in die Standardfehlerausgabe |

```kotlin
if (OS == OperatingSystem.OPENBSD) panic("this project does not build on OpenBSD")
```

Nach ihren Blöcken `project` und `compiler` kann eine Projektdatei zurücklesen, was sie geschrieben hat: `project.name`,
`compiler.standard`.

## Lockdatei

`LOCK.sqlite3` neben der Projektdatei ist eine SQLite-Datenbank, die die Abhängigkeiten festhält, die das Projekt
deklariert, und die Plugins, die es ausgewertet haben. `tazel lock resolve` erneuert sie; `check`, `build` und `run`
erneuern sie, wenn sie nicht mehr zur Projektdatei passt. Sie hält Deklarationen fest, keinen aufgelösten
Abhängigkeitsgraphen.

`tazel lock create-dump` schreibt `LOCK.dump`: denselben Inhalt als SQL-Text, deterministisch und von SQLite
wiederabspielbar, zur Durchsicht und für Diffs. `--path` schreibt ihn in eine andere Datei in einem bereits existierenden
Ordner; siehe [die Befehle](/docs/reference/commands). [Die Lockdatei](/docs/reference/lockfile) beschreibt ihre Tabellen
und wann jeder Befehl sie schreibt.

## Konfiguration der Werkzeuge

`talafmt.kts`, `talalint.kts` und `tala-analyzer.kts` konfigurieren den Formatierer, den Linter und den Analyzer für
Tala-Quellen. Jedes Werkzeug verwendet seine Standardwerte, wenn seine Datei fehlt.
