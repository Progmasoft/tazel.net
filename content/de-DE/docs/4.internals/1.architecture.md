Tazel ist ein einziges Kotlin-Programm für die JVM. Es liest eine Projektdatei, entscheidet, was zu kompilieren ist, und
startet andere Programme für die Arbeit: Talac kompiliert Tala-Ziele, `talafmt` formatiert, `talalint` prüft, und
Plugins starten die Werkzeuge, die ihre Blöcke nennen. Tazel linkt nie mit ihnen und teilt keinen Code mit ihnen; es
übergibt Argumente, wartet auf den Exit-Code und verschiebt die Dateien, die sie hinterlassen.

Diese Seite verfolgt einen Befehl vom Terminal bis zum Compiler und nennt den Code, dem jeder Schritt gehört.

## Ein Befehl, Schritt für Schritt

```text
tazel build -e Server
  │
  ├─ parseCommandLine         cli/CommandLine.kt   words → a typed Command, or a usage error (exit 2)
  ├─ Tazel.run                cli/Tazel.kt         one branch per command; every failure becomes exit 1
  ├─ discoverProject          dsl/ProjectLoader.kt the nearest project file, upward from the current directory
  ├─ loadWorkspace            driver/Packages.kt   the project, and the members when it is a workspace
  │    └─ ProjectLoader.load  dsl/ProjectLoader.kt plugins first, then the script → a ProjectPlan
  ├─ select                   driver/Packages.kt   the selection (-p, -e, -l) applied to the plan
  ├─ keepLockCurrent          cli/Tazel.kt         LOCK.sqlite3 rewritten when it no longer matches
  ├─ SourceFiles.discover     driver/SourceFiles.kt every .tala file below srcDir, minus the exclusions
  ├─ compilerArguments        driver/CompilerCommand.kt the settings of the plan as talac options
  ├─ Toolchain.require        driver/Toolchain.kt  where talac is
  └─ Processes.run            driver/Processes.kt  talac starts; its exit code decides the step
```

### 1. Die Befehlszeile

`parseCommandLine` ist von Hand geschrieben; Tazel verwendet keine Bibliothek für Befehlszeilen. Es liest die Wörter
einmal und gibt entweder ein `Command` zurück (ein sealed interface mit einem Typ je Befehl, der seine typisierten
Argumente trägt) oder ein `Rejected`-Ergebnis mit der Meldung und, für ein vertipptes Wort, einem Hinweis. Kein späterer
Schritt sieht die rohen Argumente noch einmal an. Eine abgelehnte Zeile endet mit `2`, bevor eine Datei gelesen wird.

Eine Option nimmt ihren Wert aus dem nächsten Argument, nach `=` oder `:` oder, bei einer kurzen Option, direkt
angehängt (`--vipkg Name`, `--vipkg=Name`, `-p:Name`, `-pName`); nach `=` oder `:` nimmt eine wiederholbare Option eine
Liste. Die Ausgabeoptionen `--color`, `--progress` und `--quiet` werden zuerst herausgenommen, wo immer sie vor `--`
stehen, und reisen als `OutputOptions` neben dem Befehl. Alles nach `--` wird ungelesen für das Programm aufbewahrt, das
der Befehl startet.

### 2. Die Projektdatei finden und ausführen

`discoverProject` geht vom aktuellen Verzeichnis nach oben und hält im ersten Verzeichnis an, das einen der fünf Namen
für Projektdateien enthält. Die Namen werden so verglichen, wie sie geschrieben sind, also ist `build.kts` keine
Projektdatei, auch nicht unter Windows und macOS, deren Dateisysteme den Namen sonst finden würden.

`ProjectLoader.load` arbeitet dann in zwei Phasen:

1. **Plugins.** `PluginPreamble` liest nur den Block `plugins { }` der Datei, mit einem kleinen Lexer und Parser, die
   keinen Code ausführen. `PluginResolver` findet jedes deklarierte JAR im Projekt oder in seinem Plugin-Cache, lädt ein
   fehlendes über `ViGetPlugins` (`dsl/plugin/PluginRegistry.kt`) aus ViGet, prüft seinen Deskriptor und seinen Digest,
   und `PluginRuntime` aktiviert die Plugins. Siehe [Ein Plugin schreiben](/docs/extending/plugins).
2. **Das Skript.** Die ganze Datei wird vom Kotlin-Skript-Host kompiliert und ausgeführt, der in Tazel eingebettet ist
   (`BasicJvmScriptingHost`), mit der DSL und den Importen der Plugins als Standardimporten. Ein kompiliertes Skript wird
   in `ScriptCache` (`dsl/ScriptCache.kt`) unter einem SHA-256 von allem aufbewahrt, wovon seine Kompilierung abhängt,
   also überspringt ein späterer Lauf die Kompilierung und wertet es nur aus. Die Blöcke des Skripts füllen den
   `ProjectContext` dieser Auswertung; wenn das Skript endet, wird das Modell als Ganzes geprüft und zu einem
   unveränderlichen `ProjectPlan`. Prüfungen, die von mehreren Blöcken abhängen, etwa die Felder, die
   `sources.viget.push` verlangt, laufen an dieser Stelle, also spielt die Reihenfolge der Blöcke nie eine Rolle.

Jede Auswertung hat ihren eigenen `ProjectContext`: das Modell, die Plugins des Projekts (`PluginState`) und was sein
Block `project` geschrieben hat. Eine Projektdatei ist ein Skript aus Aufrufen auf oberster Ebene, also bindet
`ProjectRuntime` den Kontext an den Thread, der das Skript auswertet, und löst ihn danach; `PluginRuntime`, das Plugins
aufrufen, erreicht die Plugins dieses Kontexts. Projektdateien können deshalb auf mehreren Threads gleichzeitig
ausgewertet werden. Nur der Kotlin-Compiler wird von jeweils einer Auswertung benutzt. Ein Kompilierfehler im Skript wird
mit Dateiname, Zeile und Spalte gemeldet; `panic(message)` beendet die Auswertung mit dieser Meldung.

### 3. Workspaces und Auswahl

`loadWorkspace` lädt das Wurzelprojekt und, wenn es einen `workspace` deklariert, jedes Mitglied, das nicht
ausgeschlossen ist. Jedes Mitglied ist ein eigenes Projekt und wird ebenso geladen. Ein ViPkg wird mit seinem
`project.name` gemeldet oder, wenn es keinen hat, mit seinem Verzeichnis.

`select` wendet die Auswahl des Befehls an. Ohne Auswahl behält es jedes Ziel, sonst scheitert es mit dem Namen, der
nichts ausgewählt hat; ein knapper Fehlgriff bekommt einen Hinweis „meinten Sie“.

### 4. Die Lockdatei

Bevor Tazel ein Projekt kompiliert, vergleicht es `LOCK.sqlite3` mit dem, was der Plan deklariert, und schreibt sie neu,
wenn beide sich unterscheiden. Die Datei hält Deklarationen fest, keinen aufgelösten Graphen; siehe
[Die Lockdatei](/docs/reference/lockfile).

### 5. Quellen und der Compiler

`SourceFiles.discover` durchläuft `srcDir`, ohne symbolischen Links zu folgen, und behält jede Datei, deren Name genau so
auf `.tala` endet. Ausschlussmuster werden je Pfadsegment verglichen; unter Windows ignorieren sie die Groß- und
Kleinschreibung, wie das Dateisystem. Das Ergebnis ist sortiert, also sieht der Compiler auf jedem Rechner dieselbe
Reihenfolge.

`compilerArguments` schreibt jede Compiler-Einstellung des Plans als Option, auch die mit ihrem Standardwert. Ein Build
folgt dann allein aus der Projektdatei, nicht aus den Standardwerten des gerade installierten `talac`. Die Eingaben
kommen nach `--`, also wird auch eine Datei, die wie eine Option heißt, als Datei gelesen.

Talac schreibt seine Ausgabe neben die erste Eingabe. Tazel verschiebt sie in das Ausgabeverzeichnis des Build-Modus,
unter dem Namen des Ziels, mit TalaRT, wenn Talac es dort hinterlassen hat, und scheitert, wenn der Compiler Erfolg
gemeldet und nichts hinterlassen hat.

Bevor es Talac startet, bildet Tazel einen Hash über die Argumente, den Inhalt der Eingaben, die Version des Compilers
sowie Größe und Zeit der Dateien, aus denen er besteht. Das Ergebnis eines Laufs liegt in `.tazel/cache/<slug>/<key>`,
einem Verzeichnis, das abseits vorbereitet und an seinen Platz verschoben wird, also ist es ganz da oder gar nicht. Ein
Cache, der sich nicht lesen oder schreiben lässt, ist eine Warnung: Der Compiler läuft, und der Build geht weiter. Die
Ausgabe des Compilers wird gesammelt, statt sie dem Terminal zu übergeben, damit die Warnungen eines Laufs erneut gezeigt
werden können, wenn sein Ergebnis verwendet wird.

`tazel test` folgt demselben Weg mit `--test` statt `--entry` und fügt je Suite ein zweites Ergebnis hinzu, dessen
Schlüssel auch jede Datei des Testverzeichnisses umfasst und das die Summen eines bestandenen Laufs festhält.

### 6. Formatieren und Prüfen

`tazel fmt` und `tazel lint` laden das Projekt ebenso und starten das Werkzeug einmal je ViPkg, mit den eigenen
Argumenten des Werkzeugs, dann `--`, dann jeder Quelle, die das ViPkg besitzt. Testquellen gehören dazu, wenn der Befehl
alles auswählt. Die Werkzeuge lesen ihre eigenen Konfigurationsdateien; Tazel deutet sie nicht.

## Fehler und Exit-Codes

| Exit-Code | Bedeutung | Ausgelöst von |
| --- | --- | --- |
| `0` | Erfolg | |
| `1` | die Arbeit ist gescheitert: eine falsche Projektdatei, ein Ziel, das es nicht gibt, ein Werkzeug, das die Quellen abgelehnt hat | `ProjectConfigurationException`, `Stop`, `UnknownTargetException`, ein SQLite-Fehler |
| `2` | die Befehlszeile selbst war falsch | `parseCommandLine` |

`tazel run` reicht den Exit-Code des Programms durch, das es gestartet hat. Jeder Fehler wird als eine Zeile auf die
Standardfehlerausgabe geschrieben, mit einer Hinweiszeile darunter, wenn es eine gibt; für einen Fehler, den ein Benutzer
beheben kann, gibt Tazel keinen Stacktrace aus.

## Ausgabe im Terminal

Statuszeilen (`Compiling`, `Checking`, `Finished`) gehen auf die Standardausgabe, Fehler und Warnungen auf die
Standardfehlerausgabe, alles über Mordant. Während auf einem interaktiven Terminal mehrere Ziele abgearbeitet werden,
zeichnet `StepProgress` einen Fortschrittsbalken; die Ausgabe der Werkzeuge wird dann gesammelt und über dem Balken
ausgegeben, statt ihn zu überschreiben. In einer Pipe oder in der CI wird kein Balken gezeichnet, und die Werkzeuge
schreiben direkt ins Terminal. `outputTerminal` baut das Terminal, das `--color` und `--progress` verlangen, im Client
wie im Daemon; `--quiet` lässt die Statuszeilen weg.

## Der Daemon

`main` liest zuerst die Befehlszeile. `tazel jvm ...` behandelt `runDaemonCommand`; jeder andere Befehl wird von
`forwardToDaemon` dem Daemon angeboten, bevor er im Prozess läuft. `DaemonClient` verbindet sich mit dem Unix-Domain-Socket,
den `DaemonPaths` nennt, stellt sich mit Token, Protokoll und Version vor (`DaemonProtocol.kt`) und schickt die
Argumente, das Arbeitsverzeichnis, die Umgebung und was das Terminal darstellen kann. `DaemonServer` beantwortet jeden
Client auf einem eigenen Thread: Es baut für die Anfrage ein `Tazel`, mit einem `ForwardingTerminal` und
`ForwardingProcesses`, die Ausgaben an den Client schicken und seine Eingaben lesen, und mit `RoutedStream` anstelle von
`System.out` und `System.err`, damit das, was eine Projektdatei ausgibt, den Client des Befehls erreicht, der sie
ausgewertet hat. Die Ausgabe kommt als Frames zurück, und der letzte Frame trägt den Exit-Code und die Zeiten der Phasen.
Ein Daemon wird von `DaemonMain` gestartet, auf der Java-Laufzeit und mit dem Klassenpfad des Clients.

## Nahtstellen für Tests

`Tazel` erhält alles, was den Rechner berührt, als Konstruktorargument: das Terminal, das Arbeitsverzeichnis, das
Betriebssystem, die `Toolchain` (mit eigener Umgebung und eigenem Installationsverzeichnis) und `Processes`. Die Tests
übergeben ein aufzeichnendes `Processes`, das die Datei schreibt, die ein echter Compiler hinterlassen würde, also laufen
ganze Befehle gegen Projekte auf der Platte ohne Compiler. Siehe
[Contributing](https://github.com/Progmasoft/tazel/blob/main/CONTRIBUTING.md#tests).
