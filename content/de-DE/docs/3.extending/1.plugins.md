Ein Plugin ist ein JAR, das die Projekt-DSL erweitert. Es kann Blöcke hinzufügen, die eine Projektdatei verwendet, etwa
`cmake { }`, dem Build des Projekts Schritte hinzufügen, Werte in seinem Plan festhalten und das Projekt prüfen, sobald es
vollständig ist. Diese Seite zeigt, wie ein Plugin gebaut wird, wie Tazel es findet und prüft und was es tun darf, sobald
es läuft.

Ein Plugin ist vertrauenswürdige Build-Logik. Es läuft in Tazel mit dem vollen Zugriff der JVM; Tazel prüft, dass das JAR
dasjenige ist, das das Projekt verlangt hat, und sperrt nicht ein, was es tut.

## Ein Plugin verwenden

Ein Projekt deklariert seine Plugins in einem Block `plugins`:

```kotlin
plugins {
  plugin("Publisher") {
    name = "CMake"
    version = "0.1.0"
  }

  localPlugin {
    path = "Tools/plugin.jar"
  }
}
```

- `plugin("Publisher") { name = ...; version = ... }` verlangt ein Plugin aus ViGet. Tazel sucht zuerst im Plugin-Cache
  des Projekts, `.tazel/plugins`; liegt dort keine passende Version, lädt es das Plugin von
  `https://viget.progmasoft.com/dslplugins/tazel/<Publisher>/<Name>/` in den Cache. Ohne `version` wird die neueste
  Version genommen, die nicht zurückgezogen ist und für die Plugin-API dieses Tazel gebaut wurde; eine genannte Version
  wird auch dann genommen, wenn sie zurückgezogen wurde.
- `localPlugin { path = ... }` nennt ein JAR im Projektverzeichnis. Herausgeber, Name und Version stammen aus dem JAR
  selbst.

Tazel liest diesen Block **bevor** es den Rest der Datei ausführt, mit einem kleinen Parser, der keinen Code ausführt.
Dieser Parser akzeptiert nur, was das Beispiel zeigt: `plugin("...")` und `localPlugin`, mit Feldern als einfache
String-Literale; ein Wert, der aus einer Variablen oder einem String-Template berechnet wird, wird abgelehnt. Kommentare
und Strings an anderer Stelle der Datei werden übersprungen, also wird ein Wort `plugins` darin nicht für den Block
gehalten.

Wenn das Skript läuft, deklariert der Block dieselben Plugins noch einmal, und jedes Plugin, das der Parser gefunden hat,
muss deklariert werden. Schreiben Sie den Block auf die oberste Ebene der Datei: In einem `if`, das nicht ausgeführt
wird, bleiben seine Plugins undeklariert, und der Befehl scheitert mit
`resolved plugins were not declared by the script`.

## Ein Plugin bauen

Ein Plugin wird mit Gradle 9 und dem Gradle-Plugin `com.progmasoft.tazel.plugin` gebaut, dessen Version die Version von
Tazel ist, für die das Plugin gebaut wird. Progmasoft veröffentlicht das Gradle-Plugin unter
`https://maven.progmasoft.com/tazel`, neben der API, also nennen die Einstellungen des Builds dieses Repository für
Plugins. Das Repository ist exklusiv für die Gruppen `com.progmasoft.tazel` und `com.progmasoft.tazel.*`: Gradle sucht
sie dort und nirgendwo sonst und sucht jedes andere Plugin, etwa das von Kotlin, im Gradle Plugin Portal:

```kotlin
// settings.gradle.kts of the plugin
pluginManagement {
  repositories {
    exclusiveContent {
      forRepository { maven("https://maven.progmasoft.com/tazel") }
      filter { includeGroupByRegex("com\\.progmasoft\\.tazel(\\..*)?") }
    }
    gradlePluginPortal()
  }
}

rootProject.name = "cmake-plugin"
```

```kotlin
// build.gradle.kts of the plugin
plugins {
  kotlin("jvm") version "2.4.0"
  id("com.progmasoft.tazel.plugin") version "0.4.0.3"
}

repositories {
  mavenCentral()
}

version = "0.1.0"

kotlin { jvmToolchain(25) }

tazelPlugin {
  publisher = "Publisher"
  name = "CMake"
  pluginClass = "com.example.cmake.CMakePlugin"
  imports = listOf("com.example.cmake.dsl.*")
  description = "Configures and builds CMake projects."
  authors = listOf("Ada Lovelace <ada@example.com>")
  license = "MIT"
  homepage = "https://example.com/cmake"
  repository = "https://github.com/example/cmake-plugin"
}

dependencies {
  tazelApi()
}
```

Das Gradle-Plugin

- fügt das Repository der API, `https://maven.progmasoft.com/tazel`, nur für die Gruppe `com.progmasoft.tazel` hinzu;
  Kotlin und alles andere kommen aus den Repositories des Builds, hier Maven Central;
- lässt `tazelApi()` `compileOnly` und `testImplementation` von `com.progmasoft.tazel:tazel-api` in seiner eigenen
  Version bedeuten. Die API wird nicht eingepackt: Tazel stellt sie und die Kotlin-Standardbibliothek bereit, wenn es das
  Plugin lädt;
- schreibt den Deskriptor und den Service-Eintrag unten aus `tazelPlugin { }` in das JAR. Die Version des Plugins ist
  die Version des Projekts, sofern `tazelPlugin.version` keine andere setzt.

`gradlew jar` schreibt dann das Plugin-JAR.

## Das JAR

Ein Plugin-JAR enthält:

```text
com/example/cmake/CMakePlugin.class
com/example/cmake/dsl/CMake.class                                  the functions it adds to the DSL
META-INF/tazel-plugin.properties                                   the descriptor
META-INF/services/com.progmasoft.api.tazel.dsl.plugin.ProjectPlugin
```

### Der Deskriptor

```properties
publisher=Publisher
name=CMake
version=0.1.0
apiVersion=2
imports=com.example.cmake.dsl.*
description=Configures and builds CMake projects.
author.0=Ada Lovelace <ada@example.com>
license=MIT
homepage=https\://example.com/cmake
repository=https\://github.com/example/cmake-plugin
```

| Schlüssel | Regel |
| --- | --- |
| `publisher` | ein Bezeichner: der Name eines Progmasoft-Kontos |
| `name` | ein Bezeichner |
| `version` | eine genaue Version: `A.B.C`, bei Bedarf dann `.D`, `.E` und `-METADATA` |
| `apiVersion` | die Plugin-API, für die es gebaut wurde; Tazel lädt nur `2`, die aktuelle `PROJECT_PLUGIN_API_VERSION` |
| `imports` | optional; durch Kommas getrennte Pakete oder Klassen, die die Projektdatei standardmäßig importiert, etwa `com.example.cmake.dsl.*` |
| `description`, `author.0`, `author.1`, ..., `license`, `homepage`, `repository` | für Tazel optional; ViGet zeigt sie auf der Seite des Plugins. `license` ist ein SPDX-Ausdruck. |

Ein Import muss ein Name mit Punkten sein, optional mit `.*` am Ende; alles andere wird abgelehnt.

### Der Service

`META-INF/services/com.progmasoft.api.tazel.dsl.plugin.ProjectPlugin` nennt die Klasse, die `ProjectPlugin`
implementiert:

```text
com.example.cmake.CMakePlugin
```

Der Eintrag nennt genau eine Klasse; eine Zeile darf mit einem Kommentar `#` enden. Die Klasse implementiert
`ProjectPlugin` und hat einen öffentlichen Konstruktor ohne Parameter. Wer das Plugin ist, ergibt sich allein aus dem
Deskriptor: Die Klasse nennt weder Herausgeber noch Name noch Version.

## Die API

Die API ist `com.progmasoft.tazel:tazel-api`, die Pakete `com.progmasoft.api.tazel` und darunter. Ein Plugin
implementiert `ProjectPlugin`:

```kotlin
fun interface ProjectPlugin {
  fun apply(context: ProjectPluginContext)
}

interface ProjectPluginContext {
  val projectRoot: Path
  val host: Host

  fun registerExtension(name: String)
  fun contribute(key: String, value: String)
  fun onFinalize(action: (ProjectSummary) -> Unit)
}
```

| Aufruf | Was er tut |
| --- | --- |
| `projectRoot` | das Verzeichnis der Projektdatei |
| `host` | das Betriebssystem und die Architektur, auf denen Tazel läuft |
| `registerExtension(name)` | beansprucht einen DSL-Namen, etwa `cmake`, für dieses Plugin. Ein Name ist ein Bezeichner, und zwei Plugins können nicht denselben beanspruchen. |
| `contribute(key, value)` | hält einen Wert im Plan des Projekts fest. Ein Schlüssel beginnt mit einem Buchstaben oder `_` und hat höchstens 128 Buchstaben, Ziffern, `_`, `.` oder `-`; jeder Schlüssel wird je Plugin einmal geschrieben, und der Wert darf nicht leer sein. |
| `onFinalize(action)` | führt `action` mit einer `ProjectSummary` (Name, Version, Build-Modus, Ausgabeverzeichnis) aus, nachdem das Skript geendet hat, für Prüfungen, die das ganze Projekt brauchen |

Die Erweiterungen und Beiträge jedes Plugins landen im Plan des Projekts und in seiner Lockdatei.

### Blöcke und Build-Schritte

Der Block, den eine Projektdatei schreibt, etwa `cmake { }`, ist eine Funktion, die das Plugin in einem seiner `imports`
definiert. Sie verlangt von `PluginExtensions` den Scope ihrer Erweiterung, was scheitert, wenn das Projekt das Plugin
nicht deklariert hat, das sie registriert hat, und fügt die Arbeit des Blocks als Build-Schritte hinzu:

```kotlin
package com.example.cmake.dsl

import com.progmasoft.api.tazel.dsl.TazelPluginDsl
import com.progmasoft.api.tazel.dsl.plugin.PluginExtensions

@TazelPluginDsl
class CMakeScope {
  var enabled = false
  internal val definitions = linkedMapOf<String, String>()

  fun define(vararg values: Pair<String, String>) = definitions.putAll(values)
}

fun cmake(block: CMakeScope.() -> Unit) {
  val settings = CMakeScope().apply(block)
  if (!settings.enabled) return
  val scope = PluginExtensions.require("cmake")
  scope.buildStep("configure") { context ->
    val cmake = context.findProgram("cmake") ?: context.fail("cmake was not found on PATH")
    val exitCode =
      context.run(
        listOf(cmake.toString(), "-S", ".", "-B", context.workDirectory.toString()) +
          settings.definitions.map { (key, value) -> "-D$key=$value" }
      )
    if (exitCode != 0) context.fail("cmake exited with $exitCode")
  }
}
```

`tazel build` und `tazel run` führen die Schritte eines Projekts in der Reihenfolge aus, in der sie hinzugefügt wurden,
bevor seine Tala-Ziele kompiliert werden. Für `tazel build` braucht ein Projekt, dessen Plugins Schritte hinzufügen, kein
Tala-Ziel; `tazel run` braucht eine ausführbare Datei zum Starten und führt die Schritte ihres Projekts aus, bevor es sie
kompiliert. Ein Schritt läuft mit einem `BuildContext`:

| Mitglied | Was es ist |
| --- | --- |
| `projectRoot`, `host`, `buildMode` | das Projekt, der Rechner und `DEBUG` oder `RELEASE` |
| `project` | die `ProjectSummary` des Projekts: sein Name, seine Version, sein Build-Modus und sein Ausgabeverzeichnis |
| `outputDirectory` | das absolute Verzeichnis, in das der Build-Modus des Projekts Artefakte schreibt |
| `workDirectory` | ein Verzeichnis des Schritts für Zwischendateien: `.tazel/build/<Publisher>.<Name>/<step>` des Projekts, in jedem Build dasselbe |
| `status(verb, message)`, `warn(message)` | gibt eine Zeile in der Ausgabe von Tazel aus |
| `run(command, directory, environment)` | startet ein Programm, mit Variablen zusätzlich zu denen von Tazel, und gibt seinen Exit-Code zurück; was es ausgibt, geht in die Ausgabe von Tazel |
| `capture(command, directory, environment)` | startet ein Programm wie `run`, gibt aber seinen Exit-Code und seine Ausgabe zurück, statt sie zu zeigen: für eine Probe, deren Scheitern eine Antwort ist, oder ein Programm, dessen Ausgabe der Schritt liest |
| `findProgram(name)` | das Programm auf `PATH`, mit der Endung ausführbarer Dateien des Hosts, oder `null` |
| `fail(message)` | beendet den Build mit der Koordinate des Plugins, dem Namen des Schritts und der Meldung |

`@TazelPluginDsl` markiert die Scopes eines Plugins, damit ein verschachtelter Block nicht versehentlich die Mitglieder des
Blocks um ihn herum erreicht.

Ein Fehler in `apply`, in einem Finalizer oder in einem Schritt beendet den Befehl mit der Koordinate des Plugins und der
Meldung der Ausnahme, zum Beispiel `plugin 'Publisher.CMake' failed while finalizing the project: the CMake plugin needs a
CMakeLists.txt`.

## Wie Tazel ein Plugin lädt

1. **Auflösen.** Ein lokales Plugin muss eine reguläre Datei sein, kein symbolischer Link, im Projektverzeichnis, auch
   nachdem sein echter Pfad aufgelöst wurde. Ein ViGet-Plugin wird in `.tazel/plugins` nach Herausgeber, Name und, falls
   angegeben, Version gesucht; liegt es dort nicht, werden sein Index, `index.json`, und sein JAR,
   `<Version>/<Name>-<Version>.jar`, aus ViGet geladen, und das JAR wird nur behalten, wenn sein SHA-256 der ist, den der
   Index nennt.
2. **Prüfen.** Tazel liest den Deskriptor, prüft jeden Schlüssel und berechnet den SHA-256-Digest des JARs. Liegt eine
   Datei `<plugin>.jar.sha256` neben dem JAR, muss ihr erstes Wort dieser Digest sein, in Kleinbuchstaben hexadezimal.
3. **Aktivieren.** Die JARs kommen auf einen eigenen Class Loader; für jedes Plugin wird die Klasse, die sein
   Service-Eintrag nennt, mit ihrem öffentlichen Konstruktor erzeugt, und `apply` läuft in der Reihenfolge der
   Deklarationen.
4. **Konfigurieren.** Die Projektdatei läuft. Ihr Block `plugins` deklariert dieselben Plugins noch einmal; jedes muss in
   Schritt 1 mit der Version aufgelöst worden sein, die der Block nennt. Die Blöcke der Plugins fügen ihre Build-Schritte
   hinzu.
5. **Abschließen.** Nach dem Skript läuft jeder Finalizer mit der Zusammenfassung des Projekts, und die Einträge der
   Plugins kommen in seinen Plan.
6. **Sperren.** Herausgeber, Name, Version, API-Version und Digest jedes Plugins werden in `LOCK.sqlite3` festgehalten;
   siehe [Die Lockdatei](/docs/reference/lockfile).
7. **Bauen.** `tazel build` und `tazel run` für das Projekt der ausführbaren Datei, die es startet, führen die
   Build-Schritte aus. Die JARs bleiben geöffnet, bis der Befehl endet.

## Ein Plugin ausprobieren

Die schnellste Schleife ist ein eigenes Projekt, das das JAR als lokales Plugin nennt:

```kotlin
plugins {
  localPlugin { path = "build/libs/cmake-plugin-0.1.0.jar" }
}

project { name = "Demo" }

cmake {
  enabled = true
  define("BUILD_TESTS" to "OFF")
}
```

`tazel build` führt die Schritte des Plugins aus. `tazel lock resolve` lädt das Plugin, führt das Skript aus und schreibt
die Lockdatei, ohne etwas zu bauen; `tazel lock create-dump` zeigt dann das Plugin so, wie die Lockdatei es festhält.
