תוסף הוא JAR שמרחיב את ה-DSL של הפרויקט. הוא יכול להוסיף בלוקים שקובץ פרויקט משתמש בהם, כמו `cmake { }`, להוסיף צעדים
לבנייה של הפרויקט, לרשום ערכים בתוכנית שלו ולבדוק את הפרויקט כשהוא שלם. הדף הזה מראה איך בונים תוסף, איך Tazel מוצאת
ומאמתת אותו, ומה מותר לו לעשות כשהוא רץ.

תוסף הוא לוגיקת בנייה מהימנה. הוא רץ בתוך Tazel עם הגישה המלאה של ה-JVM; ‏Tazel בודקת שה-JAR הוא זה שהפרויקט ביקש, ולא
מגבילה את מה שהוא עושה.

## שימוש בתוסף

פרויקט מצהיר על התוספים שלו בבלוק `plugins`:

```kotlin
plugins {
  plugin("Publisher") {
    name = "CMake"
    version = "0.1.0"
  }

  localPlugin {
    path = "Tools/plugin.jar"
  }
}
```

- ‏`plugin("Publisher") { name = ...; version = ... }` מבקש תוסף מ-ViGet. ‏Tazel מחפשת קודם במטמון התוספים של הפרויקט,
  ‏`.tazel/plugins`; כשאין שם גרסה מתאימה, היא מורידה את התוסף מ-`https://viget.progmasoft.com/dslplugins/tazel/<Publisher>/<Name>/`
  למטמון. בלי `version` נלקחת הגרסה החדשה ביותר שלא נמשכה ושנבנתה עבור ה-API של התוספים של Tazel הזו; גרסה שצוינה
  נלקחת גם אם נמשכה.
- ‏`localPlugin { path = ... }` מציין JAR בתוך תיקיית הפרויקט. המפרסם, השם והגרסה שלו באים מה-JAR עצמו.

‏Tazel קוראת את הבלוק הזה **לפני** שהיא מריצה את שאר הקובץ, עם parser קטן שלא מריץ שום קוד. ה-parser הזה מקבל רק את מה
שהדוגמה מראה: ‏`plugin("...")` ו-`localPlugin`, עם שדות שנכתבו כמחרוזות פשוטות; ערך שמחושב ממשתנה או מתבנית מחרוזת
נדחה. הערות ומחרוזות במקומות אחרים בקובץ מדולגות, כך שהמילה `plugins` בתוכן לא נחשבת לבלוק.

כשהסקריפט רץ, הבלוק מצהיר שוב על אותם תוספים, וכל תוסף שה-parser מצא חייב להיות מוצהר. כתבו את הבלוק ברמה העליונה של
הקובץ: בתוך `if` שלא רץ, התוספים שלו נשארים לא מוצהרים, והפקודה נכשלת עם
‏`resolved plugins were not declared by the script`.

## בניית תוסף

תוסף נבנה עם Gradle 9 ותוסף ה-Gradle ‏`com.progmasoft.tazel.plugin`, שהגרסה שלו היא הגרסה של Tazel שהתוסף נבנה עבורה.
‏Progmasoft מפרסמת את תוסף ה-Gradle ב-`https://maven.progmasoft.com/tazel`, לצד ה-API, ולכן ההגדרות של הבנייה מציינות את
המאגר הזה עבור תוספים. המאגר בלעדי לקבוצות `com.progmasoft.tazel` ו-`com.progmasoft.tazel.*`: ‏Gradle מחפש אותן שם ולא
בשום מקום אחר, ומחפש כל תוסף אחר, כמו זה של Kotlin, ב-Gradle Plugin Portal:

```kotlin
// settings.gradle.kts of the plugin
pluginManagement {
  repositories {
    exclusiveContent {
      forRepository { maven("https://maven.progmasoft.com/tazel") }
      filter { includeGroupByRegex("com\\.progmasoft\\.tazel(\\..*)?") }
    }
    gradlePluginPortal()
  }
}

rootProject.name = "cmake-plugin"
```

```kotlin
// build.gradle.kts of the plugin
plugins {
  kotlin("jvm") version "2.4.0"
  id("com.progmasoft.tazel.plugin") version "0.4.0.3"
}

repositories {
  mavenCentral()
}

version = "0.1.0"

kotlin { jvmToolchain(25) }

tazelPlugin {
  publisher = "Publisher"
  name = "CMake"
  pluginClass = "com.example.cmake.CMakePlugin"
  imports = listOf("com.example.cmake.dsl.*")
  description = "Configures and builds CMake projects."
  authors = listOf("Ada Lovelace <ada@example.com>")
  license = "MIT"
  homepage = "https://example.com/cmake"
  repository = "https://github.com/example/cmake-plugin"
}

dependencies {
  tazelApi()
}
```

תוסף ה-Gradle

- מוסיף את המאגר של ה-API, ‏`https://maven.progmasoft.com/tazel`, לקבוצה `com.progmasoft.tazel` בלבד; ‏Kotlin וכל השאר
  באים מהמאגרים של הבנייה, כאן Maven Central;
- גורם ל-`tazelApi()` להיות `compileOnly` ו-`testImplementation` של `com.progmasoft.tazel:tazel-api` בגרסה שלו עצמו.
  ה-API לא נארז ב-JAR: ‏Tazel מספקת אותו, ואת הספרייה הסטנדרטית של Kotlin, כשהיא טוענת את התוסף;
- כותב ל-JAR את המתאר ואת רשומת השירות שלמטה מתוך `tazelPlugin { }`. הגרסה של התוסף היא הגרסה של הפרויקט, אלא אם
  ‏`tazelPlugin.version` קובע אחרת.

אחר כך `gradlew jar` כותב את ה-JAR של התוסף.

## ה-JAR

‏JAR של תוסף מכיל:

```text
com/example/cmake/CMakePlugin.class
com/example/cmake/dsl/CMake.class                                  the functions it adds to the DSL
META-INF/tazel-plugin.properties                                   the descriptor
META-INF/services/com.progmasoft.api.tazel.dsl.plugin.ProjectPlugin
```

### המתאר

```properties
publisher=Publisher
name=CMake
version=0.1.0
apiVersion=2
imports=com.example.cmake.dsl.*
description=Configures and builds CMake projects.
author.0=Ada Lovelace <ada@example.com>
license=MIT
homepage=https\://example.com/cmake
repository=https\://github.com/example/cmake-plugin
```

| מפתח | כלל |
| --- | --- |
| `publisher` | מזהה אחד: השם של חשבון Progmasoft |
| `name` | מזהה אחד |
| `version` | גרסה מדויקת: `A.B.C`, ואחריה לפי הצורך `.D`, ‏`.E` ו-`-METADATA` |
| `apiVersion` | ה-API של התוספים שהוא נבנה עבורו; ‏Tazel טוענת רק `2`, ה-`PROJECT_PLUGIN_API_VERSION` הנוכחי |
| `imports` | אופציונלי; חבילות או מחלקות מופרדות בפסיקים שקובץ הפרויקט מייבא כברירת מחדל, כמו `com.example.cmake.dsl.*` |
| `description`, ‏`author.0`, ‏`author.1`, ..., ‏`license`, ‏`homepage`, ‏`repository` | אופציונליים עבור Tazel; ‏ViGet מציג אותם בדף של התוסף. ‏`license` הוא ביטוי SPDX. |

ייבוא חייב להיות שם עם נקודות, שיכול להסתיים ב-`.*`; כל דבר אחר נדחה.

### השירות

‏`META-INF/services/com.progmasoft.api.tazel.dsl.plugin.ProjectPlugin` מציין את המחלקה שמממשת את `ProjectPlugin`:

```text
com.example.cmake.CMakePlugin
```

הרשומה מציינת בדיוק מחלקה אחת; שורה יכולה להסתיים בהערת `#`. המחלקה מממשת את `ProjectPlugin` ויש לה בנאי ציבורי בלי
פרמטרים. מי התוסף נקבע מהמתאר בלבד: המחלקה לא מציינת מפרסם, שם או גרסה.

## ה-API

ה-API הוא `com.progmasoft.tazel:tazel-api`, החבילות `com.progmasoft.api.tazel` ומטה. תוסף מממש את `ProjectPlugin`:

```kotlin
fun interface ProjectPlugin {
  fun apply(context: ProjectPluginContext)
}

interface ProjectPluginContext {
  val projectRoot: Path
  val host: Host

  fun registerExtension(name: String)
  fun contribute(key: String, value: String)
  fun onFinalize(action: (ProjectSummary) -> Unit)
}
```

| קריאה | מה היא עושה |
| --- | --- |
| `projectRoot` | התיקייה של קובץ הפרויקט |
| `host` | מערכת ההפעלה והארכיטקטורה ש-Tazel רצה עליהן |
| `registerExtension(name)` | תופס שם DSL, כמו `cmake`, עבור התוסף הזה. שם הוא מזהה אחד, ושני תוספים לא יכולים לתפוס את אותו שם. |
| `contribute(key, value)` | רושם ערך בתוכנית של הפרויקט. מפתח מתחיל באות או ב-`_` ומכיל לכל היותר 128 אותיות, ספרות, ‏`_`, ‏`.` או `-`; כל מפתח נכתב פעם אחת לכל תוסף, והערך לא יכול להיות ריק. |
| `onFinalize(action)` | מריץ את `action` עם `ProjectSummary` (שם, גרסה, מצב בנייה, תיקיית פלט) אחרי שהסקריפט הסתיים, לבדיקות שצריכות את הפרויקט כולו |

ההרחבות והתרומות של כל תוסף מגיעות לתוכנית של הפרויקט ולקובץ הנעילה שלו.

### בלוקים וצעדי בנייה

הבלוק שקובץ פרויקט כותב, כמו `cmake { }`, הוא פונקציה שהתוסף מגדיר באחד מה-`imports` שלו. היא מבקשת מ-`PluginExtensions`
את ה-scope של ההרחבה שלה, מה שנכשל אם הפרויקט לא הצהיר על התוסף שרשם אותה, ומוסיפה את העבודה של הבלוק כצעדי בנייה:

```kotlin
package com.example.cmake.dsl

import com.progmasoft.api.tazel.dsl.TazelPluginDsl
import com.progmasoft.api.tazel.dsl.plugin.PluginExtensions

@TazelPluginDsl
class CMakeScope {
  var enabled = false
  internal val definitions = linkedMapOf<String, String>()

  fun define(vararg values: Pair<String, String>) = definitions.putAll(values)
}

fun cmake(block: CMakeScope.() -> Unit) {
  val settings = CMakeScope().apply(block)
  if (!settings.enabled) return
  val scope = PluginExtensions.require("cmake")
  scope.buildStep("configure") { context ->
    val cmake = context.findProgram("cmake") ?: context.fail("cmake was not found on PATH")
    val exitCode =
      context.run(
        listOf(cmake.toString(), "-S", ".", "-B", context.workDirectory.toString()) +
          settings.definitions.map { (key, value) -> "-D$key=$value" }
      )
    if (exitCode != 0) context.fail("cmake exited with $exitCode")
  }
}
```

‏`tazel build` ו-`tazel run` מריצות את הצעדים של פרויקט בסדר שבו הם נוספו, לפני שיעדי ה-Tala שלו מהודרים. עבור
‏`tazel build`, פרויקט שהתוספים שלו מוסיפים צעדים לא צריך יעד Tala; ‏`tazel run` צריכה קובץ הרצה כדי להריץ, והיא מריצה
את הצעדים של הפרויקט שלו לפני שהיא מהדרת אותו. צעד רץ עם `BuildContext`:

| איבר | מה הוא |
| --- | --- |
| `projectRoot`, ‏`host`, ‏`buildMode` | הפרויקט, המחשב, ו-`DEBUG` או `RELEASE` |
| `project` | ה-`ProjectSummary` של הפרויקט: השם, הגרסה, מצב הבנייה ותיקיית הפלט שלו |
| `outputDirectory` | התיקייה המוחלטת שמצב הבנייה של הפרויקט כותב אליה תוצרים |
| `workDirectory` | תיקייה של הצעד לקבצי ביניים: ‏`.tazel/build/<Publisher>.<Name>/<step>` של הפרויקט, זהה בכל בנייה |
| `status(verb, message)`, ‏`warn(message)` | מדפיס שורה בפלט של Tazel |
| `run(command, directory, environment)` | מריץ תוכנית, עם משתנים בנוסף לאלה של Tazel, ומחזיר את קוד היציאה שלה; מה שהיא מדפיסה הולך לפלט של Tazel |
| `capture(command, directory, environment)` | מריץ תוכנית כמו `run`, אבל מחזיר את קוד היציאה שלה ואת מה שהדפיסה במקום להציג אותו: לבדיקה שהכישלון שלה הוא תשובה, או לתוכנית שהצעד קורא את הפלט שלה |
| `findProgram(name)` | התוכנית ב-`PATH`, עם סיומת קובצי ההרצה של המארח, או `null` |
| `fail(message)` | עוצר את הבנייה עם הקואורדינטה של התוסף, שם הצעד וההודעה |

‏`@TazelPluginDsl` מסמן את ה-scopes של תוסף, כדי שבלוק מקונן לא יגיע בטעות לאיברים של הבלוק שסביבו.

כישלון בתוך `apply`, ב-finalizer או בצעד עוצר את הפקודה עם הקואורדינטה של התוסף וההודעה של החריגה, למשל
‏`plugin 'Publisher.CMake' failed while finalizing the project: the CMake plugin needs a CMakeLists.txt`.

## איך Tazel טוענת תוסף

1. **פתרון.** תוסף מקומי חייב להיות קובץ רגיל, לא קישור סמלי, בתוך תיקיית הפרויקט, גם אחרי שהנתיב האמיתי שלו נפתר.
   תוסף מ-ViGet מחופש ב-`.tazel/plugins` לפי מפרסם, שם, וכשצוינה, גרסה; כשהוא לא שם, האינדקס שלו, ‏`index.json`, וה-JAR
   שלו, ‏`<Version>/<Name>-<Version>.jar`, מורדים מ-ViGet, וה-JAR נשמר רק כשה-SHA-256 שלו הוא זה שהאינדקס מציין.
2. **אימות.** ‏Tazel קוראת את המתאר, בודקת כל מפתח ומחשבת את תקציר ה-SHA-256 של ה-JAR. כשקובץ `<plugin>.jar.sha256` נמצא
   לצד ה-JAR, המילה הראשונה שלו חייבת להיות התקציר הזה, בהקסדצימלי באותיות קטנות.
3. **הפעלה.** קובצי ה-JAR מוכנסים ל-class loader משלהם; לכל תוסף, המחלקה שרשומת השירות שלו מציינת נוצרת עם הבנאי הציבורי
   שלה, ו-`apply` רץ לפי סדר ההצהרות.
4. **הגדרה.** קובץ הפרויקט רץ. הבלוק `plugins` שלו מצהיר שוב על אותם תוספים; כל אחד חייב להיפתר בצעד 1 עם הגרסה שהבלוק
   מציין. הבלוקים של התוספים מוסיפים את צעדי הבנייה שלהם.
5. **סיום.** אחרי הסקריפט, כל finalizer רץ עם הסיכום של הפרויקט, והרשומות של התוספים נוספות לתוכנית שלו.
6. **נעילה.** המפרסם, השם, הגרסה, גרסת ה-API והתקציר של כל תוסף נרשמים ב-`LOCK.sqlite3`; ראו
   [קובץ הנעילה](/docs/reference/lockfile).
7. **בנייה.** ‏`tazel build`, וגם `tazel run` עבור הפרויקט של קובץ ההרצה שהיא מריצה, מריצות את צעדי הבנייה. קובצי ה-JAR
   נשארים פתוחים עד שהפקודה מסתיימת.

## ניסוי בתוסף

הלולאה המהירה ביותר היא פרויקט נפרד שמציין את ה-JAR כתוסף מקומי:

```kotlin
plugins {
  localPlugin { path = "build/libs/cmake-plugin-0.1.0.jar" }
}

project { name = "Demo" }

cmake {
  enabled = true
  define("BUILD_TESTS" to "OFF")
}
```

‏`tazel build` מריצה את הצעדים של התוסף. ‏`tazel lock resolve` טוענת את התוסף, מריצה את הסקריפט וכותבת את קובץ הנעילה
בלי לבנות דבר; אחר כך `tazel lock create-dump` מציגה את התוסף כפי שקובץ הנעילה רושם אותו.
