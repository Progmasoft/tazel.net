‏`LOCK.sqlite3` נמצא לצד קובץ הפרויקט. זהו מסד נתונים של SQLite שרושם את מה שהפרויקט מצהיר עליו: התלויות שלו, עם
התכונות שלהן, והתוספים שהעריכו את קובץ הפרויקט, עם התקציר (digest) של כל JAR. הוא רושם הצהרות, לא גרף תלויות פתור;
‏Tazel עדיין לא יודעת להוריד חבילות מ-ViGet, כך שאין מה לפתור.

בצעו commit ל-`LOCK.sqlite3` יחד עם קובץ הפרויקט. הצורה הטקסטואלית שלו, `LOCK.dump`, נועדה לקריאה ולסקירת שינוי.

## מתי הוא נכתב

| פקודה | מה קורה ל-`LOCK.sqlite3` |
| --- | --- |
| `tazel lock resolve` | נכתב עבור הפרויקט ועבור כל חבר ב-workspace שלו |
| `tazel check`, ‏`build`, ‏`run` | נכתב לפני שהפרויקט מהודר, כשהוא כבר לא רושם את מה שהפרויקט מצהיר עליו |
| `tazel lock graph` | נכתב כשהוא חסר או לא עדכני; עם `--locked` קובץ לא עדכני הוא שגיאה במקום זאת |
| `tazel lock create-dump` | נקרא בלבד |

"לא עדכני" נקבע לפי התוכן: ‏Tazel קוראת את הקובץ ומשווה את מה שהוא רושם למה שקובץ הפרויקט מצהיר עליו עכשיו. קובץ
בפורמט ישן, קובץ פגום וקובץ חסר — כולם לא עדכניים.

קובץ נעילה חדש נכתב לקובץ זמני באותה תיקייה ואז מועבר מעל הישן, באופן אטומי כשמערכת הקבצים מאפשרת זאת, כך שכתיבה
שנקטעה לעולם לא משאירה חצי קובץ נעילה.

## פורמט 5

הטבלה `metadata` מחזיקה את הפורמט: `format_version` הוא `5`. פורמט 5 הוא פורמט 4 עם היציבות `RC`, ולכן קובץ בפורמט 4
נקרא כמו שהוא ונשאר עד שהפרויקט משתנה. קובץ נעילה בכל פורמט אחר לא נקרא; ‏Tazel מבקשת `tazel lock resolve`, שכותבת את
הפורמט הנוכחי. גרסאות של Tazel שלפני פורמט 5 דוחות באותו אופן קובץ בפורמט 5.

| טבלה | מפתח | עמודות |
| --- | --- | --- |
| `metadata` | `key` | `value`; מחזיקה את `format_version` |
| `packages` | `name`, ‏`scope` | `stability`, ‏`version`, ‏`feature` (התכונה של הפרויקט הזה שמביאה את החבילה, או `NULL`), ‏`default_features` (`0` או `1`) |
| `package_features` | `package_name`, ‏`scope`, ‏`feature` | `enabled` (`0` או `1`): התכונות של התלות עצמה שהפרויקט מפעיל או מכבה |
| `local_packages` | `path`, ‏`scope` | קובצי `.vipkg` שהפרויקט מציין, יחסית לקובץ הפרויקט |
| `plugins` | `publisher`, ‏`name` | `version`, ‏`api_version`, ‏`sha256` (64 ספרות הקסדצימליות) |

‏`name` ב-`packages` הוא הקואורדינטה של החבילה, `Publisher.Name`. ‏`scope` הוא `BUILD` עבור `dependency`
ו-`localDependency`, ו-`TEST` עבור `testDependency` ו-`localTestDependency`. כל טבלה היא `WITHOUT ROWID`: שורה מזוהה
רק לפי המפתח שלה, כך שאי אפשר לרשום חבילה אחת פעמיים באותו scope.

עבור קובץ הפרויקט הזה:

```kotlin
dependencies {
  dependency("Publisher") {
    name = "Toml"
    version = "1.0.0"
    feature = "TOML"
    defaultFeatures = false
    feature("Serde") { enabled = true }
  }
  localDependency { path = "Libraries/Shared.vipkg" }
}
```

קובץ הנעילה מכיל:

| טבלה | שורה |
| --- | --- |
| `packages` | `Publisher.Toml`, ‏`BUILD`, ‏`STABLE`, ‏`1.0.0`, ‏`TOML`, ‏`0` |
| `package_features` | `Publisher.Toml`, ‏`BUILD`, ‏`Serde`, ‏`1` |
| `local_packages` | `Libraries/Shared.vipkg`, ‏`BUILD` |

## הייצוא הטקסטואלי

```text
tazel lock create-dump
tazel lock create-dump --path reviews/Locks.sql
```

‏`LOCK.dump` הוא SQL ש-SQLite יכול להריץ מחדש: הערת כותרת, `PRAGMA foreign_keys=OFF;`, ואחריה טרנזקציה אחת עם משפט
‏`CREATE TABLE` של כל טבלה ואחריו השורות שלה. הטבלאות מופיעות לפי סדר השמות שלהן והשורות לפי סדר העמודות שלהן, כך
שאותו קובץ נעילה תמיד נותן אותם בתים, ו-diff מראה רק את מה שהשתנה.

כדי להפוך ייצוא בחזרה למסד נתונים:

```text
sqlite3 LOCK.sqlite3 < LOCK.dump
```

הייצוא לעולם לא נכתב מעל קובץ הנעילה הבינארי, והתיקייה שלו חייבת להתקיים; ראו
[את הפקודה](/docs/reference/commands#writing-the-lockfile-as-text).

## גרף התלויות

‏`tazel lock graph` מצייר את מה שקובצי הנעילה רושמים, ולכן מחדש אותם קודם. הוא מציג כל פרויקט ב-workspace כשורש, מתחתיו
את החבילות שלו מ-ViGet ואת החבילות המקומיות, ואת תלויות הבדיקה תחת `[test]`. חבילה שתכונה מביאה מוצגת רק כל עוד
התכונה הזו פועלת. האפשרויות מתוארות לצד [הפקודה](/docs/reference/commands#the-dependency-graph).
