פרויקט מתואר בקובץ אחד, סקריפט Kotlin ש-[Tazel](/docs/reference/commands) מעריכה. ‏Tazel קוראת אותו, מוצאת את המקורות
שהוא מציין ומפעילה את הכלים שבונים אותם; הכלים האלה לעולם לא רואים קובץ פרויקט.

## איתור

לקובץ פרויקט יש אחד מחמישה שמות. ‏Tazel מחפשת אותם בסדר הזה ומשתמשת בראשון שקיים; האחרים לא נקראים:

1. `BUILD.kts`
2. `BUILD.tzl`
3. `BUILD.tazel`
4. `BUILD`
5. `Tazel.build`

השמות תלויי רישיות בכל מארח, ולכל החמישה אותו תחביר. פקודה עובדת על הפרויקט של התיקייה הנוכחית: התיקייה הקרובה ביותר,
כלפי מעלה, שמכילה קובץ פרויקט.

הסקריפט מהודר ומורץ בתוך Tazel. מחשב צריך JRE בגרסה 25 ומעלה, ולא צריך התקנה של Kotlin.

## פרויקט מינימלי

```kotlin
project {
  name = "Example"
}

sources {
  executable {
    entry = "Example.Program"
  }
}
```

```powershell
tazel run
```

זה מהדר כל קובץ `.tala` שמתחת ל-`Sources/` וכותב את `build/debug/Example.exe` (בלי סיומת מחוץ ל-Windows).

‏[`BUILD.kts`](https://github.com/Progmasoft/tazel/blob/main/BUILD.kts) מראה את כל ה-DSL בקובץ אחד. מה שלא נמצא בקובץ
הזה אינו חלק מה-DSL.

## `project`

```kotlin
project {
  name = "Example"
  version = "0.1.0"
  stability = Stability.STABLE // STABLE, RC, UNSTABLE, BETA, NIGHTLY, ALPHA or DEV
  description = "An example project"
  authors("Leitwolf", "Helmut")
  defaultFeatures("TOML")
  defaultRun = "Server" // the executable `tazel run` runs when none is named; default: the only one
}
```

‏`name` תמיד נדרש, ולכן בכל קובץ פרויקט יש בלוק `project`. כל שדה אחר אופציונלי כשלעצמו. עם `sources.viget.push = true`
נדרשים גם `version`, ‏`stability`, ‏`description` ולפחות מחבר אחד; זה נבדק אחרי שכל הקובץ רץ, כך שסדר הבלוקים לא משנה.
‏`name` הוא מזהה אחד ו-`version` היא גרסה מדויקת: ‏`A.B.C`, ואחריה לפי הצורך `.D`, ‏`.E` ו-`-METADATA`.

## `compiler`

```kotlin
compiler {
  standard = talaStandardOf(26)
  backend = Backend.LLVM
  buildMode = BuildMode.RELEASE
  werror = true
  warnings = Warnings.ALL
  wshadow = true
  xppOptimizationPasses = true
  xmmOptimizationPasses = true
  optLevel = OptLevel.O3
  staticTalaRTLibrary = true

  llvm {
    compiler = LlvmCompiler.AOT
    lto = LlvmLto.NONE
    args("-time-passes")
  }
}
```

הבלוק הזה מיועד ליעדי Tala; הוא מגדיר את Talac.

| הגדרה | ערכים | ברירת מחדל | אפשרות מהדר |
| --- | --- | --- | --- |
| `standard` | `talaStandardOf(26)` | `talaStandardOf(26)` | `--standard` |
| `backend` | `Backend.LLVM` | `LLVM` | `--codegen-backend` |
| `buildMode` | `BuildMode.DEBUG`, ‏`RELEASE` | `DEBUG` | בוחר את תיקיית הפלט ואת ברירת המחדל של `optLevel` |
| `werror` | `true`, ‏`false` | `false` | `--warnings-as-errors` |
| `warnings` | `Warnings.ALL`, ‏`MEDIUM`, ‏`LOW`, ‏`NONE` | `MEDIUM` | `--warnings` |
| `wshadow` | `true`, ‏`false` | `false` | `--warnings=shadow` |
| `xppOptimizationPasses` | `true`, ‏`false` | `true` | `--xpp-optimization-passes` |
| `xmmOptimizationPasses` | `true`, ‏`false` | `true` | `--xmm-optimization-passes` |
| `optLevel` | `OptLevel.O0`, ‏`O1`, ‏`O2`, ‏`O3`, ‏`OG`, ‏`OS`, ‏`OZ` | `O0` עבור `DEBUG`, ‏`O3` עבור `RELEASE` | `--opt-level` |
| `staticTalaRTLibrary` | `true`, ‏`false`, ‏`null` | `null` | `--static-talart-library` |
| `llvm.compiler` | `LlvmCompiler.AOT`, ‏`ORC` | `AOT` | `--llvm-compiler` |
| `llvm.lto` | `LlvmLto.FAT`, ‏`THIN`, ‏`NONE` | `NONE` | `--llvm-lto` |
| `llvm.args(...)` | ארגומנטים ל-LLVM | אין | `--llvm-args` |

‏Tazel כותבת כל הגדרה לשורת הפקודה של המהדר, גם את אלה שבערך ברירת המחדל שלהן, כך שבנייה נובעת מקובץ הפרויקט ולא
מברירות המחדל של המהדר שמותקן. הגדרה שהמהדר עדיין לא יכול לבצע נדחית על ידי המהדר, בשמה; ראו את
[העיון במהדר](/docs/reference/commands#עדיין-לא-מומש).

‏`staticTalaRTLibrary` הוא היוצא מן הכלל. ‏`null`, או השמטת ההגדרה, לא כותב שום אפשרות ומשאיר את הבחירה למהדר; ‏`true`
כותב `--static-talart-library=true`, שמקשר את TalaRT לתוך הפלט, ו-`false` כותב `--static-talart-library=false`, ששומר
אותו בספרייה משותפת לצד הפלט.

אף רמת אזהרה לא מפעילה את `wshadow`. ‏`wshadow = true` יחד עם `Warnings.NONE` הוא סתירה ונדחה.

## `buildCache`

```kotlin
buildCache {
  local {
    enabled = true
    maxEntries = 8
  }

  remote {
    url = "https://cache.example.com"
    read = true
    write = false
    token = System.getenv("TAZEL_CACHE_TOKEN")
    publicKey = "MCowBQYDK2VwAyEA..."
    signingKey = System.getenv("TAZEL_CACHE_SIGNING_KEY")
  }
}
```

| הגדרה | ערכים | ברירת מחדל | משמעות |
| --- | --- | --- | --- |
| `local.enabled` | `true`, ‏`false` | `true` | שומר תוצאות ב-`.tazel/cache` |
| `local.maxEntries` | 1 או יותר | `8` | כמה תוצאות של כל יעד נשמרות |
| `remote.url` | כתובת `https`; ‏`http` רק למחשב הזה | נדרש | איפה התוצאות המשותפות |
| `remote.read` | `true`, ‏`false` | `true` | מבקש תוצאות מהשרת |
| `remote.write` | `true`, ‏`false` | `false` | שולח תוצאות לשרת |
| `remote.token` | טקסט או `null` | `null` | נשלח כ-`Authorization: Bearer`; ריק נחשב כחסר |
| `remote.publicKey` | מפתח Ed25519 או `null` | `null` | משתמשים רק בתוצאות שנחתמו עבור המפתח הזה |
| `remote.signingKey` | מפתח Ed25519 או `null` | `null` | חותם על מה שהמחשב הזה כותב; סוד |

הבלוק אופציונלי, ובלעדיו לפרויקט יש רק המטמון המקומי. למטמון המקומי יש קדימות: מבקשים מהשרת רק את מה שלא נמצא בו, ומה
שהוא נותן נשמר מקומית, אלא אם `local.enabled` הוא `false`. מה הופך תוצאה לזהה מתואר תחת
[בנייה מצטברת](/docs/reference/commands#בנייה-מצטברת).

כתבו אסימונים ואת מפתח החתימה כמשתנים, לעולם לא בתוך קובץ הפרויקט. קובץ פרויקט שקורא משתנה עם `System.getenv("NAME")`
מקבל את הערך של הפקודה, גם תחת ה-daemon: כשהערך שונה מזה שה-daemon הופעל איתו, הפקודה רצה בלי ה-daemon ועוצרת אותו,
והפקודה הבאה מפעילה daemon שרואה את הערך החדש. לשם כך השם חייב להיכתב כטקסט; שם שמחושב בזמן ריצה לא מורגש.

תוצאה היא תוכנית, ולכן תוצאה משרת היא קוד שהמחשב הזה יריץ. ‏`tazel cache keygen` מדפיסה זוג מפתחות Ed25519. תנו את
ה-`publicKey` לכל פרויקט, ואת ה-`signingKey` רק למה שבונה מקורות מהימנים, כמו CI על הענף הראשי. קורא עם `publicKey` משתמש
אז בתוצאה רק עם חתימה עבור המפתח הזה, עבור היעד הזה ועבור המפתח הזה של המטמון, כך שלא אסימון שדלף ולא שרת שנפרץ יכולים
להשתיל תוכנית. תוצאה בלי חתימה נחשבת חסרה, וחתימה שגויה היא אזהרה; בכל מקרה המהדר רץ. קורא בלי `publicKey` סומך על
השרת, ומקבל אזהרה כשהוא משתמש בתוצאה.

השרת עונה לשתי בקשות, כל אחת עם האסימון אם יש כזה. ‏`GET <url>/<slug>/<key>` מחזירה את התוצאה כארכיון ZIP, או `404`
כשהיא לא שם, ו-`<key>.sig` את החתימה שלה. ‏`PUT` לאותם נתיבים שומרת אותם ועונה `200`, ‏`201` או `204`, ו-`HEAD` אומרת
עבור `tazel cache push` אם תוצאה קיימת. לא עוקבים אחרי הפניות. שרת שנכשל או שאי אפשר להגיע אליו הוא אזהרה: הבנייה
ממשיכה, ולא פונים שוב לשרת במהלך אותה פקודה. ‏[`tazel cache serve`](/docs/reference/commands#שרת-למטמון-מרוחק) הוא
שרת כזה.

## `outdirs`, ‏`targets` ו-`pml`

```kotlin
outdirs {
  release = "build/release"
  debug = "build/debug"
}

targets {
  target("x86_64-pc-windows-msvc", "aarch64-apple-darwin")
}

pml {
  enabled = true
}
```

תיקיות פלט הן יחסיות לקובץ הפרויקט ונשארות בתוך הפרויקט. תוצר נקרא על שם היעד שלו: ‏`build/debug/<name>.exe` לבנייה,
‏`build/debug/<name>.talameta` לבדיקה.

‏`targets` מפרט את ה-target triples של LLVM שהחבילה מיועדת להם; ברירת המחדל היא היעד של המארח. ‏`check`, ‏`build`
ו-`run` מהדרות עבור המארח. ‏`pml.enabled = false` נועד לסגור את Progmasoft Library ‏(`Progmasoft.*`) בפני הפרויקט;
ההגדרה נרשמת, ולמהדר עדיין אין אפשרות עבורה.

## `sources`

```kotlin
sources {
  viget {
    push = true
    exclude("build/**/*")
  }

  executable {
    name = "Example"
    srcDir = "Sources"
    exclude("Sources/Generated")
    entry = "Example.Program"
  }

  library {
    name = "ExampleLibrary"
    viPkgType(ViPkgType.TALALIB, ViPkgType.STATICLIB)
    srcDir = "Sources"
    namespace = "Example.Library"
  }

  test("Unit") {
    testDir = "Tests/Unit"
  }
}
```

היעדים ב-`sources` הם יעדי Tala; פרויקט שרק התוספים שלו בונים אותו לא צריך אותם. לפרויקט יכול להיות כל מספר של קובצי
הרצה וספריות. ‏`name` הוא כברירת מחדל שם הפרויקט, ולכן יעד של פרויקט בלי שם חייב לתת לעצמו שם; שמות תלויי רישיות
וייחודיים בתוך הסוג שלהם. ‏`srcDir` הוא כברירת מחדל `Sources`.

‏`entry` מציין מחלקה לפי ה-namespace שלה: ‏`Example.Program`. המחלקה הזו מספקת את `public static void Main()` בלי
פרמטרים שמפעיל את התוכנית. נקודת הכניסה נמצאת לפי namespace ומחלקה, לא לפי קובץ: לא שמות קבצים ולא תיקיות צריכים לשקף
namespaces. לספרייה אין נקודת כניסה; ‏`namespace` מציין את ה-namespace השורשי שלה. ‏`viPkgType` הוא `TALALIB`, אלא אם
הספרייה אומרת אחרת; ‏`STATICLIB` ו-`CDYLIB` הם הסוגים האחרים.

המקורות של יעד הם כל קובץ מתחת ל-`srcDir` שלו ששמו מסתיים ב-`.tala`, כתוב בדיוק כך. לא עוקבים אחרי קישורים סמליים.
‏`exclude` מקבל דפוסים יחסית לקובץ הפרויקט, כתובים עם `/`:

- ‏`*` ו-`?` מתאימים בתוך מקטע נתיב אחד;
- מקטע שהוא `**` מתאים לכל מספר של מקטעים;
- דפוס שמציין תיקייה מחריג את כל מה שמתחתיה.

הדפוסים מושווים כמו שהמארח משווה שמות קבצים: בלי תלות ברישיות ב-Windows, ובדיוק במקומות אחרים.

‏`test("Name")` מצהיר על חבילת בדיקות בעלת שם; שם הוא מזהה אחד ואפשר להצהיר עליו פעם אחת. ‏`testDir` הוא כברירת מחדל
‏`Tests/<name>`. מקורות בדיקה ותוצרי בדיקה לעולם לא נכנסים ל-`.vipkg`. ‏`sources.viget.exclude` מסיר קבצים נוספים ממה
שנארז.

## `dependencies`

```kotlin
dependencies {
  dependency("Publisher") {
    name = "Name"
    version = "1.2.3"
    stability = Stability.STABLE
  }

  dependency("Publisher") {
    name = "Toml"
    version = "1.0.0"
    feature = "TOML"
    defaultFeatures = false
    feature("Serde") { enabled = true }
  }

  localDependency { path = "Dependency.vipkg" }

  testDependency("Publisher") {
    name = "TestDep"
    version = "0.1.0"
  }

  localTestDependency { path = "TestDependency.vipkg" }
}
```

תלות היא חבילה מ-ViGet, שנכתבת כמפרסם, שם וגרסה מדויקת. ‏`stability` הוא כברירת מחדל `STABLE`. המפרסם הוא השם של
חשבון Progmasoft, תלוי רישיות. ‏ViGet הוא המקור המרוחק היחיד: אין רשימת מאגרים ואין דרך לציין מאגר אחר.

‏`feature = "TOML"` הופך את התלות לאופציונלית: היא מובאת רק כשהתכונה `TOML` של הפרויקט הזה פועלת. ‏`defaultFeatures`
ו-`feature("Name") { enabled = true }` בוחרים בין התכונות של התלות עצמה.

‏`localDependency` מציין `.vipkg` בתוך תיקיית הפרויקט. ‏`testDependency` ו-`localTestDependency` משרתים רק את חבילות
הבדיקה. אפשר להצהיר על חבילה פעם אחת לכל סוג; שתי הצהרות שונות על אותה חבילה הן שגיאה.

‏Tazel רושמת את ההצהרות ועדיין לא מורידה אותן, ולכן `check`, ‏`build` ו-`run` דוחות פרויקט שמצהיר על תלות של הבנייה.
ה-namespaces של הספרייה הסטנדרטית אינם תלויות ולעולם לא מוצהרים.

## `execution`

```kotlin
execution {
  jobs = 8
  cpus = 6
  memory = "16g"
  memoryPerJob = "1g"
  keepGoing = true
  incremental = true
  profile = "build/trace.json"

  remote {
    url = "https://build.example.com"
    token = System.getenv("TAZEL_REMOTE_TOKEN")
  }
}
```

הבלוק כולו אופציונלי, ו[הדגלים](/docs/reference/commands#ניצול-המחשב) של פקודה קודמים לו. ב-workspace קובע
הבלוק של השורש. ‏`profile` יחסי לקובץ הפרויקט. ‏`url` מקבל `https`, או `http` רק למחשב הזה.

## `workspace`

```kotlin
workspace {
  members("./Server", "../Shared", "Client")
  defaultMembers("./Server", "../Shared")
  exclude("OldProject")
}
```

כל חבר הוא תיקייה עם קובץ פרויקט משלה, שנכתבת יחסית לקובץ הפרויקט הזה. פרויקט שרק מאגד חברים צריך `project.name` ולא
צריך `sources`. ‏`defaultMembers` הם החברים ש-`tazel fmt` ו-`tazel lint` עובדות עליהם בשורש; ‏`exclude` מסיר תיקייה
מהחברים. ראו [workspaces](/docs/reference/commands#workspaces).

## `plugins`

תוספים מרחיבים את ה-DSL. מצהירים עליהם בבלוק `plugins` ש-Tazel קוראת לפני שהיא מהדרת את שאר הקובץ:

```kotlin
plugins {
  plugin("Progmasoft") {
    name = "CMake"
    version = "0.1.0"
  }

  localPlugin {
    path = "plugin.jar"
  }
}
```

תוסף מ-ViGet נמצא במטמון של הפרויקט, ‏`.tazel/plugins`; תוסף שחסר במטמון מורד
מ-`https://viget.progmasoft.com/dslplugins/tazel/<Publisher>/<Name>/`. תוסף מקומי הוא JAR בתוך תיקיית הפרויקט. בכל
מקרה ה-JAR מתאר את עצמו ב-`META-INF/tazel-plugin.properties` (מפרסם, שם, גרסה, גרסת API, הייבואים שהוא מוסיף לקובץ
הפרויקט) ומספק בדיוק שירות `ProjectPlugin` אחד. ‏Tazel בודקת את הקואורדינטה, הגרסה, גרסת ה-API ותקציר ה-SHA-256 לפני
שהיא טוענת את התוסף; קובץ `<plugin>.jar.sha256` לצד ה-JAR קובע את התקציר הצפוי. לתוסף אין יציבות.

תוסף נכתב מול החבילה `com.progmasoft.api.tazel.dsl.plugin`. הוא יכול לרשום הרחבות DSL, לתרום מטא-נתונים ולהריץ hook
כשהפרויקט שלם. תוסף הוא לוגיקת בנייה מהימנה: הוא רץ עם הגישה המלאה של ה-JVM, ו-Tazel לא מגבילה אותו.
‏[כתיבת תוסף](/docs/extending/plugins) מראה איך בונים וטוענים תוסף.

| `OS` | מערכת ההפעלה ש-Tazel רצה עליה: ‏`OperatingSystem.LINUX`, ‏`MACOS`, ‏`WINDOWS`, ‏`FREEBSD`, ‏`OPENBSD`, ‏`NETBSD` או `UNKNOWN` |
| `ARCH` | ארכיטקטורת המעבד שלה: ‏`Architecture.X86_64`, ‏`AARCH64`, ‏`ARMV7H`, ‏`RISCV64` או `UNKNOWN` |
| `panic(message)` | עוצר את ההערכה; הפקודה נכשלת עם ההודעה |
| `eprint(value)` | כותב לפלט השגיאה הסטנדרטי |

```kotlin
if (OS == OperatingSystem.OPENBSD) panic("this project does not build on OpenBSD")
```

אחרי הבלוקים `project` ו-`compiler` שלו, קובץ פרויקט יכול לקרוא בחזרה את מה שכתב: ‏`project.name`,
‏`compiler.standard`.

## קובץ נעילה

‏`LOCK.sqlite3`, לצד קובץ הפרויקט, הוא מסד נתונים של SQLite שרושם את התלויות שהפרויקט מצהיר עליהן ואת התוספים שהעריכו
אותו. ‏`tazel lock resolve` מחדשת אותו; ‏`check`, ‏`build` ו-`run` מחדשות אותו כשהוא כבר לא תואם את קובץ הפרויקט. הוא
רושם הצהרות, לא גרף תלויות פתור.

‏`tazel lock create-dump` כותבת את `LOCK.dump`: אותו תוכן כטקסט SQL, דטרמיניסטי וניתן להרצה מחדש ב-SQLite, לסקירה
ול-diffs. ‏`--path` כותב אותו לקובץ אחר בתיקייה שכבר קיימת; ראו [הפקודות](/docs/reference/commands).
‏[קובץ הנעילה](/docs/reference/lockfile) מתאר את הטבלאות שלו ומתי כל פקודה כותבת אותו.

## תצורת הכלים

‏`talafmt.kts`, ‏`talalint.kts` ו-`tala-analyzer.kts` מגדירים את המעצב, את ה-linter ואת המנתח של מקורות Tala. כל כלי
משתמש בברירות המחדל שלו כשהקובץ שלו חסר.
