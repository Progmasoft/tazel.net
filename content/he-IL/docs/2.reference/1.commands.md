‏Tazel מפעילה את הכלים של פרויקט כתוכניות נפרדות: ‏Talac, ‏`talafmt` ו-`talalint` ליעדי Tala, והתוכניות שהצעדים של
תוספים מציינים. שורות הפקודה של כלי Tala מתוארות לצדם: [Talac](https://talac.tala.run/docs/command-line), וקובצי ה-README
של [talafmt](https://github.com/Progmasoft/talafmt) ושל [talalint](https://github.com/Progmasoft/talalint). קודי היציאה
משותפים: ‏`0` הצלחה, ‏`1` העבודה נכשלה, ‏`2` שורת הפקודה עצמה הייתה שגויה. ‏`tazel run` מעבירה הלאה את קוד היציאה של
התוכנית שהריצה.

```text
tazel [output options] <command> [arguments]
```

‏`tazel` עובדת על הפרויקט שהתיקייה הנוכחית שייכת אליו: התיקייה הקרובה ביותר, כלפי מעלה, שמכילה
[קובץ פרויקט](/docs/reference/project-file).

| פקודה | מה היא עושה |
| --- | --- |
| `tazel check` | בודקת את המקורות בלי לכתוב קובץ הרצה |
| `tazel build` | בונה את היעדים |
| `tazel run [-- arguments]` | בונה קובץ הרצה אחד ומריצה אותו |
| `tazel test` | בונה ומריצה את חבילות הבדיקה |
| `tazel fetch` | מורידה את התלויות מראש: תוספים מ-ViGet אל `.tazel/plugins`, ונכשלת אם חבילה מקומית חסרה או אם הוצהרה חבילת ViGet, כי ViGet עדיין לא מגיש חבילות Tala |
| `tazel custom [name] [arguments]` | מריצה פקודה מ-`tazel_custom.txt`, או מציגה את רשימתן; ראו [פקודות מותאמות](#פקודות-מותאמות) |
| `tazel lock resolve` | פותרת את התלויות ומחדשת את `LOCK.sqlite3` |
| `tazel lock create-dump [--path File]` | כותבת את קובץ הנעילה כטקסט, ל-`LOCK.dump` או לקובץ ש-`--path` מציין |
| `tazel lock graph [options]` | מדפיסה את גרף התלויות; מחדשת את `LOCK.sqlite3` אלא אם צוין `--locked` |
| `tazel update` | מעדכנת את התלויות של המערכת ושל הפרויקט |
| `tazel install [--global \| -g] Publisher.Name` | מורידה חבילה מ-ViGet לפרויקט, או למערכת |
| `tazel vipkg create` | כותבת `.vipkg` מקומי לכל יעד, בלי בדיקה ובלי פרסום |
| `tazel viget push` | בונה, בודקת ומפרסמת את החבילה ב-ViGet בפעם הראשונה |
| `tazel viget update` | בונה, בודקת ומפרסמת גרסה חדשה של החבילה |
| `tazel viget vipkg-desc Publisher.Name` | מדפיסה את התיאור (`project.description`) של חבילה מ-ViGet |
| `tazel fmt [-- options]` | מעצבת את המקורות עם `talafmt` |
| `tazel lint [--workspace] [-- options]` | מנתחת את המקורות עם `talalint` |
| `tazel jvm start-daemon` | מפעילה את ה-daemon של ה-JVM ששומר את Tazel חמה בין פקודות |
| `tazel jvm restart-daemon` | עוצרת את ה-daemon ומפעילה אותו מחדש |
| `tazel jvm stop-daemon` | עוצרת את ה-daemon |
| `tazel version` | מדפיסה את הגרסה של Tazel |
| `tazel help [command]` | מדפיסה את העזרה, או את העזרה של פקודה אחת |

‏`tazel check` מפעילה את Talac עם `--emit=metadata` ועם אפשרויות המהדר של קובץ הפרויקט. ‏`tazel build` מפעילה אותו עם
‏`--emit=executable` ומעבירה את התוצאה לתיקיית הפלט של מצב הבנייה, תחת שם היעד, עם TalaRT לצדה כש-Talac השאיר את הספרייה
המשותפת.

## בנייה מצטברת

‏`check`, ‏`build`, ‏`run` ו-`test` מפעילות את Talac רק כשמשהו שקובע את הפלט שלו השתנה: התוכן או השמות של המקורות,
ההגדרות של קובץ הפרויקט, או המהדר. ‏Talac מהדר את המקורות של יעד כתוכנית אחת, ולכן היעד הוא היחידה: מקור אחד שהשתנה
מהדר מחדש את כל היעד, ושאר היעדים נשארים כמו שהם.

```text
   Compiling Demo (Demo, 12 sources)
    Finished build in 4.21s

       Fresh Demo (Demo, 12 sources)
    Finished build in 0.31s
```

התוכן קובע, הזמנים לא, ולכן קובץ שרק נגעו בו לא משנה דבר. המהדר מזוהה לפי הגרסה שלו ולפי התוכן של הקבצים שלו, וגם
המערכת והארכיטקטורה של המארח נחשבות, כך שלשני מחשבים עם אותו מהדר, אותם מקורות ואותן הגדרות יש אותן תוצאות; הבלוק
‏[`buildCache`](/docs/reference/project-file#buildcache) של קובץ הפרויקט יכול לשתף אותן דרך שרת. התוצאות נשמרות
ב-`.tazel/cache` של הפרויקט, כברירת מחדל שמונה האחרונות לכל יעד, כך שחזרה לענף או למצב בנייה קודם מציגה `Restored` ולא
מהדרת דבר. תוכנית שנמחקה או שונתה חוזרת באותה דרך. האזהרות של ההרצה שיצרה תוצאה מוצגות שוב בכל פעם שמשתמשים בה. הרצה
שנכשלה לא משאירה תוצאה. הצעדים של תוספים לא מדולגים: הם רצים בכל בנייה, לפני שהמקורות נקראים, כך שמה שהם מייצרים
נחשב.

הרצה אומרת למה היא רצה, וזה הדבר הראשון לשאול על בנייה שלקחה זמן רב:

```text
   Compiling Demo (Demo, 12 sources) Sources/Math.tala changed
   Compiling Demo (Demo, 13 sources) Sources/New.tala added
   Compiling Demo (Demo, 12 sources) Sources/Math.tala changed, and 2 more
   Compiling Demo (Demo, 12 sources) the settings changed
   Compiling Demo (Demo, 12 sources) the compiler changed
```

השורה האחרונה של פקודה סופרת מה המטמון חסך: ‏`Finished build, 3 of 4 from the cache in 2.10s`.

‏`--no-cache` עושה את העבודה בכל זאת ועדיין רושם את התוצאה. אפשר למחוק את `.tazel/cache` בכל עת.

## תחזוקת המטמונים

| פקודה | מה היא עושה |
| --- | --- |
| `tazel cache status` | מציגה לכל פרויקט ב-workspace מה המטמון המקומי שלו מחזיק, לפי יעד, ומה מצב המטמון המרוחק שלו: גישה, חתימות, והאם הוא עונה |
| `tazel cache clean` | מוחקת את `.tazel/cache` של כל פרויקט ב-workspace; לא נוגעת במטמון מרוחק |
| `tazel cache push` | שולחת את מה שהמטמונים המקומיים מחזיקים ואין לשרת; צריכה `write = true` |
| `tazel cache pull [selection]` | מביאה את התוצאות של המקורות כפי שהם עכשיו: של הבנייות, הבדיקות, חבילות הבדיקה ושל החבילות שעברו. שום דבר לא מהודר, כך שהבנייה הבאה מוצאת אותן, גם בלי רשת |

שרת לא שומר רשימה של התוצאות שלו, ו-`pull` לא צריכה כזו, כי המפתחות נובעים מהמקורות. ‏`pull` מבקשת כל תוצאה בנפרד
וסופרת מה מצאה: ‏`Pulled 3 of 6 results`. תוצאה שאף אחד עוד לא בנה אינה שגיאה.

## שרת למטמון מרוחק

‏`tazel cache serve` שומרת את התוצאות של [מטמון מרוחק](/docs/reference/project-file#buildcache) בתיקייה:

```text
tazel cache serve --directory /var/cache/tazel --port 7723 --max-size 50
```

| אפשרות | ברירת מחדל | השפעה |
| --- | --- | --- |
| `--directory` | נדרשת | איפה התוצאות נשמרות |
| `--host` | `127.0.0.1` | הכתובת שהוא מאזין עליה |
| `--port` | `7723` | הפורט שהוא מאזין עליו |
| `--max-size` | `10` | כמה ג'יגה-בייט הוא שומר; התוצאות שהשימוש האחרון בהן הכי ישן נמחקות ראשונות |

‏`TAZEL_CACHE_TOKEN` הוא האסימון ש-`PUT` צריך; בלעדיו השרת לא מקבל תוצאות. ‏`TAZEL_CACHE_READ_TOKEN`, כשהוא מוגדר, הוא
האסימון ש-`GET` צריך. אסימונים נשארים מחוץ לשורת הפקודה, שבה משתמשים אחרים יכלו לקרוא אותם.

השרת מדבר HTTP פשוט. עבור מחשבים אחרים הוא עומד מאחורי proxy עם TLS, כי Tazel דורשת `https` לכל כתובת חוץ מהמחשב הזה.
הוא לא מסתכל על שום דבר בתוך תוצאה; האם תוצאה אמיתית נקבע על ידי הקורא לפי החתימה שלה, כך שלא צריך לסמוך על השרת
בעניין הזה.

‏`tazel cache keygen` מדפיסה זוג מפתחות חדש לקובץ פרויקט.

מלבד `GET` ו-`PUT` הוא עונה גם ל-`HEAD`, ש-`tazel cache push` משתמשת בה כדי לגלות מה כבר קיים.

## חבילות בדיקה

‏`tazel test` בונה ומריצה כל חבילת בדיקה בבחירה, אחת אחרי השנייה:

```text
   Compiling Unit (Demo, 14 sources)
     Testing Unit (Demo)
PASS Math.Adds
Tests/Unit/MathTests.tala:9:9: expectation failed: Math.Clamp(50, 0, 10) == 9
    Math.Clamp(50, 0, 10) is 10
FAIL Math.Clamps (1 failed expectation)
2 tests, 1 passed, 1 failed
error: 1 suite, 2 tests, 1 passed, 1 failed: 'Unit' failed
```

חבילה מהודרת על ידי `talac --test` ממה שהבחירה מהדרת, קובצי ההרצה והספריות, ואחריהם המקורות של ה-`testDir` שלה.
מקורות שנמצאים ב-`testDir` של חבילה כלשהי לא נכללים בחלק הראשון, כך שחבילה לעולם לא רואה את הבדיקות של חבילה אחרת.
המריץ נכתב אל `.tazel/tests/<suite>/` ומתחיל בתיקיית הפרויקט, שבה בדיקה מוצאת את הקבצים שלה לפי נתיבים יחסיים לפרויקט.

‏`tazel test` צריכה Talac שיש לו `--test`. חבילה בלי מקור `.tala` היא שגיאה, כך ש-`testDir` עם שגיאת הקלדה לא יכול לעבור
בשקט. בדיקה שנכשלת לא עוצרת את החבילות שאחריה; חבילה שלא מתהדרת מסיימת את הפקודה. קוד היציאה הוא `1` כשבדיקה נכשלה,
וגם כשמריץ נעצר לפני שכתב את הסיכומים שלו, יהיה קוד היציאה שלו אשר יהיה.

חבילה שעברה לא רצה שוב כל עוד כל מה שהיא יכולה לראות נשאר זהה: המקורות שלה, ההגדרות, המהדר וכל קובץ מתחת ל-`testDir`
שלה, כולל קובצי נתונים. היא מציגה אז `Cached` ונספרת בסיכומים. חבילה שנכשלה תמיד רצה שוב, וראשונה, כך שהתשובה על מה
שעובדים עליו מגיעה לפני השאר. בדיקה שקוראת משהו אחר, כמו קובץ מחוץ לפרויקט או הרשת, צריכה `--no-cache`; וכך גם הרצה
ב-CI שחייבת להוכיח שהבדיקות עוברות.

## בחירת יעדים

‏`check`, ‏`build`, ‏`run`, ‏`test` ו-`lint` מקבלות בחירה. בלעדיה הן עובדות על הכול. עבור `test`, בחירה קובעת את
הפרויקטים ואת המקורות שהחבילות מהודרות איתם; כל חבילה של פרויקט שנבחר רצה.

```text
tazel build --vipkg Name          tazel build -p Name
tazel build --executable Name     tazel build -e Name
tazel build --library Name        tazel build -l Name
```

אפשר לכתוב כל דגל כמה פעמים, ואפשר לשלב את הסוגים; [כתיבת אפשרויות](#כתיבת-אפשרויות) מראה את צורות הכתיבה. ‏`--vipkg`
שומר את ה-ViPkgs שצוינו; ברגע ש-`--executable` או `--library` נכתבים, נשארים רק יעדים שצוינו. שם שלא בוחר דבר הוא שגיאה.

‏`tazel run` בונה ומריצה בדיוק קובץ הרצה אחד, ולכן היא מקבלת לכל היותר `--vipkg` אחד ו-`--executable` אחד, ולא
‏`--library`. בלי `--executable` היא מריצה את קובץ ההרצה היחיד בבחירה; כשיש כמה, היא מריצה את `project.defaultRun` של
ה-ViPkg היחיד שנבחר וקובע אותו. כל דבר אחר הוא שגיאה שמפרטת את קובצי ההרצה, ושום דבר לא נבנה.

```text
tazel run                    # the only executable, or project.defaultRun
tazel run -p App             # the same, within App
tazel run -p App -e Server   # Server of App
```

## כתיבת אפשרויות

אפשרות מקבלת את הערך שלה בכל אחת מצורות הכתיבה האלה; הקצרות עובדות אותו דבר עבור `-p`, ‏`-l` ו-`-i`, והארוכות עבור כל
אפשרות עם ערך, כמו `--path`, ‏`--invert` ו-`--depth`:

```text
tazel build -eFirst -eSecond                 # short, joined
tazel build -e First -e Second               # short, after a space
tazel build -e=First,Second                  # short, after =
tazel build -e:First,Second                  # short, after :
tazel build --executable First --executable Second
tazel build --executable=First,Second
tazel build --executable:First,Second
```

אחרי `=` או `:` אפשרות שאפשר לכתוב כמה פעמים מקבלת רשימה מופרדת בפסיקים; צמוד או אחרי רווח, ערך הוא שם אחד, ולכן
‏`-e First,Second` נדחה. הערך של אפשרות שנכתבת פעם אחת הוא כל מה שאחרי ה-`=` או ה-`:` הראשון, כך
ש-`--path=C:\Locks\old.sql` שומר את הנקודתיים שלו. ערך אחרי רווח לא יכול להתחיל ב-`-`, ודגל בלי ערך, כמו `--locked`,
דוחה ערך: ‏`--locked=yes` הוא שגיאה. רמז לערך עם שגיאת הקלדה נכתב כפי שהאפשרות נכתבה: ‏`--color:awlyas` מציע
‏`--color:always`.

## אפשרויות פלט

אפשר לשים אותן בכל מקום לפני `--`, לפני הפקודה או אחריה:

| אפשרות | השפעה |
| --- | --- |
| `--color always\|auto\|never` | צבעים. ‏`auto`, ברירת המחדל, משתמש בהם בטרמינל שתומך בהם; ‏`always` גם ב-pipe או ב-CI |
| `--progress always\|auto\|never` | פס ההתקדמות. ‏`auto`, ברירת המחדל, מצייר אותו בטרמינל אינטראקטיבי שיכול להזיז את הסמן שלו; ‏`always` מצייר אותו בכל מקום |
| `--quiet` | משמיט את שורות המצב, ואת פס ההתקדמות אלא אם `--progress` מבקש אותו. אזהרות, שגיאות ומה שפקודה נועדה לו, כמו הגרף של `tazel lock graph` או הפלט של התוכנית ש-`tazel run` מפעילה, עדיין מודפסים |

```text
tazel --quiet build
tazel build --color=never --progress:never
```

## כתיבת קובץ הנעילה כטקסט

‏`tazel lock create-dump` כותבת את `LOCK.dump` לצד קובץ הפרויקט. ‏`--path` מציין קובץ אחר, בכל שם וסיומת, יחסית
לתיקייה ש-`tazel` רצה בה:

```text
tazel lock create-dump --path Locks.sql
tazel lock create-dump --path reviews/Locks.sql
```

התיקייה של הקובץ חייבת להתקיים. ‏Tazel לא יוצרת אותה: תיקייה עם שגיאת הקלדה נכשלת עם שגיאה במקום להשאיר ייצוא במקום
לא צפוי. גם `--path` שמציין תיקייה נדחה.

## גרף התלויות

‏`tazel lock graph` מדפיסה במה כל פרויקט תלוי. הגרף הוא מה שקובץ הנעילה רושם, ולכן `LOCK.sqlite3` נכתב קודם כשהוא חסר
או כבר לא רושם את מה שקובץ הפרויקט מצהיר עליו. בשורש של workspace כל חבר הוא שורש של הגרף.

```text
Demo
├── Publisher.Json 1.1.0 [by feature Json]
├── Publisher.Name 1.0.0
├── Local.vipkg (local)
└── [test]
    └── Publisher.Name 2.0.0
```

תלות שתכונה של הפרויקט מביאה (`feature = "Json"`) מוצגת כשהתכונה הזו פועלת, מה שכברירת מחדל אומר שהיא אחת
מה-`defaultFeatures` של הפרויקט.

| אפשרות | השפעה |
| --- | --- |
| `--locked` | משאירה את `LOCK.sqlite3` כמו שהוא; קובץ נעילה חסר או לא עדכני הוא שגיאה |
| `--all-features` | מפעילה כל תכונה של הפרויקט |
| `--duplicates`, ‏`-d` | מציגה רק את חבילות ה-ViGet שקיימות ביותר מגרסה אחת, כל אחת עם התלויים בה |
| `--invert Package`, ‏`-i Package` | מציגה את הפרויקטים שתלויים בחבילה אחת |
| `--depth Levels` | מדפיסה לכל היותר את מספר הרמות הזה מתחת לכל שורש; ‏`0` מדפיסה רק את השורשים |

אי אפשר לכתוב את `--duplicates` ואת `--invert` יחד. מה ש-`--invert` מציין תלוי באופן שבו הוא נכתב:

| נכתב | משמעות |
| --- | --- |
| `MyPackage` | כל פרויקט מתחת לתיקייה הנוכחית שה-`project.name` שלו הוא `MyPackage`. התלויים בו הם הפרויקטים שם שמשתמשים בחבילת ViGet בשם הזה, מכל מפרסם, או ב-`MyPackage.vipkg` מקומי. תיקיות ששמן מתחיל בנקודה לא נסרקות. |
| `Publisher.Name` | חבילת ה-ViGet הזו, בכל גרסה שהפרויקטים מצהירים עליה |
| `Libraries/Name.vipkg` | החבילה המקומית הזו. מילה שמסתיימת ב-`.vipkg` היא תמיד חבילה מקומית. |

‏Tazel עדיין לא מורידה חבילות מ-ViGet, ולכן חבילת ViGet מופיעה בלי התלויות שלה עצמה.

## פלט

‏Tazel מדפיסה שורת מצב לכל צעד, כמו `Compiling Demo (Demo, 3 sources)`, ומסיימת פקודה עם הזמן שלקחה:
‏`Finished build in 1.84s`; ‏`--quiet` משמיט אותן. בזמן ש-`check`, ‏`build`, ‏`run`, ‏`fmt` ו-`lint` עובדות על היעדים
שלהן בטרמינל אינטראקטיבי, פס התקדמות מתחת לשורות המצב מציג את הצעד הנוכחי, כמה הושלמו ואת הזמן עד כה; הפלט של
‏`talac`, ‏`talafmt` ו-`talalint` מודפס אז מעל הפס. ב-pipe, ב-CI או בטרמינל שלא יכול להזיז את הסמן שלו לא מצויר פס,
והכלים כותבים ישירות לטרמינל; ‏`--progress` ו-`--color` בוחרים אחרת. התוכנית ש-`tazel run` מפעילה תמיד כותבת ישירות.
הפלט בטרמינל משתמש ב-Mordant.

## מילים עם שגיאות הקלדה

פקודה, פעולה, דגל או שם יעד שאינם מוכרים נדחים עם קוד יציאה `2` (`1` לשם יעד, שנבדק מול הפרויקט). כשהמילה קרובה למילה
מוכרת, רמז מתחת לשגיאה אומר למה כנראה התכוונו, עם הערה קצרה:

```text
error: 'biuld' is not a command of tazel; write tazel help for the commands
 hint: did you mean tazel build? So close the keys almost had it.
```

קודם משווים רישיות, כך ש-`Build` מציע `build`; אחרת מותר שינוי אחד במילה קצרה ושניים במילה ארוכה יותר, כששתי אותיות
שהוחלפו נחשבות שינוי אחד.

## העברת ארגומנטים הלאה

כל מה שאחרי `--` הולך, בלי שנקרא, לתוכנית שהפקודה מפעילה:

```text
tazel run -- --port 8080           # to the program that was built
tazel fmt -- --check               # to talafmt
tazel lint -- --fix                # to talalint
tazel lint --workspace -- --fix
```

## ‏Workspaces

בשורש של workspace, ‏`build`, ‏`check`, ‏`run` ו-`test` עובדות על כל חבר. ‏`fmt` ו-`lint` עובדות על חברי ברירת המחדל
כשה-workspace מציין כאלה, ואחרת על השורש; ‏`tazel lint --workspace` מנתחת כל חבר. בתוך התיקייה של חבר, החבר הזה הוא
הפרויקט.

## מציאת הכלים

כלי מחופש בשלושה מקומות, בסדר הזה: הנתיב ש-`TAZEL_TALAC`, ‏`TAZEL_TALAFMT` או `TAZEL_TALALINT` מציינים; ההתקנה
ש-`tazel` רצה ממנה; התיקיות של `PATH`.

## תוספים

תוסף שפרויקט מצהיר עליו עם `plugin("Publisher") { ... }` מחופש במטמון התוספים של הפרויקט, ‏`.tazel/plugins`. כשאין
במטמון גרסה מתאימה, ‏Tazel מורידה אותו מ-ViGet אל `.tazel/plugins/<Publisher>/<Name>/<Version>/` ובודקת את ה-SHA-256
שלו מול האינדקס של התוסף; הרצות מאוחרות יותר משתמשות במטמון בלי לשאול את ViGet. ‏`TAZEL_VIGET_URL` מחליף את הכתובת של
ViGet, ‏`https://viget.progmasoft.com`, עבור mirror. ראו [כתיבת תוסף](/docs/extending/plugins).

‏`build` ו-`run` מריצות את הצעדים שתוספים מוסיפים לבנייה של פרויקט לפני שיעדי ה-Tala שלו מהודרים; ‏`check` ו-`test`
לא מריצות אותם.

## קובצי פרויקט מהודרים

ההרצה הראשונה מהדרת את קובץ הפרויקט; הרצות מאוחרות יותר טוענות את הסקריפט המהודר מהמטמון ורק מעריכות אותו. רשומה
משמשת רק כשכל מה שההידור תלוי בו זהה: הטקסט והשם של הסקריפט, גרסת מהדר ה-Kotlin, יעד ה-JVM, ייבואי ברירת המחדל
ואפשרויות המהדר, ה-classpath של Tazel וה-SHA-256 של כל JAR של תוסף. אחרת הקובץ מהודר שוב. רשומה שאי אפשר לקרוא נחשבת
חסרה. המטמון שומר את 256 הרשומות שהשימוש בהן הכי עדכני.

המטמון נמצא ב-`TAZEL_CACHE_DIR` כשהוא מוגדר, ואחרת ב-`%LOCALAPPDATA%\Progmasoft\Tazel\Cache` ב-Windows,
ב-`~/Library/Caches/Progmasoft/Tazel` ב-macOS וב-`$XDG_CACHE_HOME/progmasoft/tazel` ‏(`~/.cache/progmasoft/tazel`) במקומות
אחרים. מחיקה שלו תמיד בטוחה.

## ה-daemon של ה-JVM

כל `tazel` מפעילה JVM, וקובץ הפרויקט הראשון שהיא מעריכה טוען את מהדר ה-Kotlin ואת מארח הסקריפטים. ה-daemon הוא JVM
שנשארת פועלת ומריצה את הפקודות במקום, כך שהמחלקות האלה נטענות פעם אחת. הוא לא מחליף את המטמון של קובצי פרויקט
מהודרים; פקודה ב-daemon משתמשת גם היא במטמון.

‏`tazel jvm start-daemon` מפעילה אותו, אלא אם כבר רץ אחד. ‏`tazel jvm stop-daemon` נותנת לפקודות שהוא מריץ להסתיים,
לכל היותר דקה, ועוצרת אותו; ‏daemon שלא עונה מופסק. ‏`tazel jvm restart-daemon` עושה את שניהם. שלוש הפקודות האלה תמיד
רצות בתהליך שקרא אותן.

כל עוד daemon רץ, כל פקודה אחרת הולכת אליו ומדפיסה את מה שהייתה מדפיסה בעצמה. ה-daemon מריץ את הפקודה עם הארגומנטים,
תיקיית העבודה, הסביבה והטרמינל של הלקוח, והתוכניות שהוא מפעיל קוראות את מה שמוקלד בלקוח. לכל פקודה יש הקשרי פרויקט
משלה, כך שאפשר לשרת כמה לקוחות בבת אחת; לכל היותר שמונה פקודות רצות בו-זמנית והשאר ממתינות. ‏`TAZEL_DAEMON` קובע מתי
פקודה הולכת ל-daemon:

| `TAZEL_DAEMON` | פקודה |
| --- | --- |
| `auto` (ברירת המחדל) | הולכת ל-daemon כשרץ אחד, ואחרת רצה ישירות |
| `start` | הולכת ל-daemon, שמופעל קודם כשאף אחד לא רץ |
| `off` | תמיד רצה ישירות |

‏daemon משרת משתמש אחד והתקנה אחת. הקבצים שלו נמצאים ב-`TAZEL_DAEMON_DIR` כשהוא מוגדר, ואחרת בתיקייה `daemon` תחת
‏`%LOCALAPPDATA%\Progmasoft\Tazel` ב-Windows, ‏`~/Library/Application Support/Progmasoft/Tazel` ב-macOS
ו-`$XDG_STATE_HOME/progmasoft/tazel` ‏(`~/.local/state/progmasoft/tazel`) במקומות אחרים: ‏Unix domain socket, אסימון,
נעילה, מזהה התהליך והיומן. התיקייה ניתנת לקריאה רק למשתמש, ולקוח חייב להציג את האסימון שה-daemon כתב שם. לקוח מגרסה
או פרוטוקול אחרים נדחה ומריץ את הפקודה ישירות; להתקנה, לגרסה או לסביבת Java אחרת יש daemon משלה. הנעילה מונעת מ-daemon
שני של אותה התקנה לעלות, והקבצים של daemon שמת נמחקים על ידי הלקוח הבא.

ה-daemon נעצר מעצמו אחרי `TAZEL_DAEMON_IDLE_MINUTES` בלי לקוח, 180 כברירת מחדל; ‏`0` משאיר אותו פועל. ה-heap שלו מוגבל
ל-`TAZEL_DAEMON_MAX_HEAP` ‏(`2g` כברירת מחדל) ומטא-הנתונים של המחלקות שלו ל-1 GiB; ‏daemon שנגמר לו אחד מהם יוצא, והפקודה
הבאה רצה ישירות או מפעילה חדש. כשלקוח נעלם באמצע פקודה, התוכניות שהפקודה הפעילה נעצרות.

## זמנים

עם `TAZEL_TIMINGS=1`, ‏Tazel מדפיסה כמה זמן לקח כל שלב של ההרצה, לפלט השגיאה הסטנדרטי: עליית ה-JVM, מארח הסקריפטים של
Kotlin, פתרון התוספים וטעינת המחלקות, הידור הסקריפט או טעינתו מהמטמון, הערכת הסקריפט, והפקודה כולה. פקודה שרצה
ב-daemon מציגה גם IPC: הזמן בין שליחת הפקודה לסיומה שה-daemon לא הקדיש לפקודה. עליית ה-JVM היא אז העלייה של הלקוח.

## ניצול המחשב

‏`check`, ‏`build`, ‏`run` ו-`test` מקבלות את הדגלים האלה. הם קודמים ל[בלוק `execution`](/docs/reference/project-file#execution)
של קובץ הפרויקט, והבלוק של השורש של workspace חל על כל ה-workspace.

| דגל | מה הוא עושה | ברירת מחדל |
| --- | --- | --- |
| `--jobs`, ‏`-j Number` | כמה הרצות מהדר וחבילות בדיקה רצות בבת אחת | מספר המעבדים, או `--cpus` |
| `--cpus Number` | כמה מעבדים הפקודה יכולה להעסיק; משימות לעולם לא עוברות את זה | כל המעבדים |
| `--memory Size` | כמה המשימות יכולות להחזיק יחד, כמו `8g` | בלי הגבלה |
| `--memory-per-job Size` | כמה משימה אחת אמורה להחזיק; ‏`--memory` חלקי זה מגביל את המשימות | `1g` |
| `--keep-going`, ‏`-k` | להמשיך עם המשימות האחרות אחרי שאחת נכשלה, ולדווח על כל כישלון | עצירה |
| `--incremental`, ‏`--no-incremental` | בבניית debug, לשמור אובייקט לכל מקור מתחת ל-`.tazel/incremental` | פועל, אם ל-talac יש את זה |
| `--profile File` | לכתוב Chrome trace של המשימות, עבור `chrome://tracing` או Perfetto | אין |
| `--remote-executor URL` | להדר במחשב אחר; ‏`TAZEL_REMOTE_TOKEN` הוא האסימון שלו | אין |
| `--no-remote-executor` | להדר כאן, מה שלא יגיד קובץ הפרויקט | |

זיכרון ומעבדים הם תקציבים לכמה משימות מתחילות. ‏Tazel לא מודדת מהדר ולא עוצרת מהדר שמחזיק יותר מ-`--memory-per-job`,
ומשימה אחת תמיד רצה. הרצות Talac שכותבות לצד אותה תיקיית מקורות מתחלפות בתורות, כי talac משאיר את הפלט שלו לצד הקלט
הראשון שלו, ולכן חבילות הבדיקה של פרויקט אחד מתהדרות אחת אחרי השנייה ואז רצות בבת אחת. חבילת בדיקה שרצה לצד אחרות
מדפיסה את הדוח שלה כשהיא מסתיימת.

‏`tazel jvm start-daemon --max-heap 2g` ו-`restart-daemon --max-heap 2g` מגבילות את ה-heap של ה-daemon, כמו
‏`TAZEL_DAEMON_MAX_HEAP`.

### הרצה מרוחקת

‏`tazel remote serve` מהדרת עבור מחשבים אחרים:

```text
TAZEL_REMOTE_TOKEN=... tazel remote serve --host 127.0.0.1 --port 7724 --jobs 8
```

האסימון נדרש. השרת מדבר HTTP פשוט, ולכן עבור מחשבים אחרים הוא עומד מאחורי proxy עם TLS, וזה גם מה ש-Tazel דורשת
מכתובת כזו. הוא רק מפעיל את talac, על המקורות שנשלחו אליו, בתיקייה משלהם, ודוחה בקשה שהאפשרויות שלה מציינות מקום
במחשב שלו.

הלקוח שולח את המקורות ואת האפשרויות של הרצת מהדר ומקבל בחזרה את מה ש-talac אמר וכתב. התוצאות נכנסות למטמון הבנייה כמו
תוצאות מקומיות, ותוכניות וחבילות בדיקה תמיד רצות במחשב הזה. שרת עם גרסת talac אחרת או סוג מארח אחר עונה שהוא לא יכול
לעזור. במקרה הזה, או כשהשרת נכשל, ‏Tazel מזהירה פעם אחת ומהדרת כאן עד סוף הפקודה. מי שמחזיק בשרת מחליט אילו תוכניות
תקבלו, ולכן השתמשו רק בשרת שאתם סומכים עליו.

## פקודות מותאמות

‏`tazel custom` מריצה פקודות שנכתבו ב-`tazel_custom.txt`, שנמצא בתיקייה הנוכחית או בקרובה ביותר מעליה. לא צריך קובץ
פרויקט, הפקודות לא חייבות לערב את Tazel, והן רצות בתיקייה של הקובץ.

```text
# A comment to the end of the line.
<# A comment
   of several lines. #>

build-no-cache: ("tazel" 'build' `--no-cache`);
npm-dev: ('npm' 'dev');

# Several steps run in order; line breaks mean nothing.
fetch:
    ("cargo" "fetch")
    ("tazel" "fetch");

# s(...) is one command line for the shell of the host.
npm-dev-sh: s('npm dev');

fetch-sh:
    s("cargo fetch")
    ("tazel" "fetch");

# Another shell is a program like any other.
npm-dev-zsh: ("zsh" "-lc" "npm dev");

# A name may hold several words.
build no-cache: ("tazel" "build" "--no-cache");

# <N> passes the Nth argument, from 1; <*> passes all of them.
build with: ("tazel" "build" <1> <2>);
test all: ("tazel" "test" <*>);
```

```text
tazel custom fetch
tazel custom build no-cache
tazel custom build with -e MyApp
```

מחרוזת נכתבת עם `"`, ‏`'` או `` ` `` ואין בה escapes, ולכן היא לא יכולה להכיל את המירכאה שלה עצמה, ולוכסן הפוך בתוכה הוא
לוכסן הפוך. ‏`(...)` מפעיל את התוכנית ישירות עם הארגומנטים האלה: אין shell, ולכן מילה כמו `|` לא אומרת שום דבר מיוחד,
וכל מחרוזת נשארת ארגומנט אחד. ב-Windows התוכנית יכולה להיות סקריפט כמו `npm.cmd`. ‏`s(...)` מקבל בדיוק מחרוזת אחת
ומעביר אותה בלי שינוי ל-CMD ב-Windows ול-`sh` במקומות אחרים; את ה-escapes שבה קורא ה-shell הזה. היוצא מן הכלל היחיד
הוא JVM שהופעלה ב-Windows עם `jdk.lang.Process.allowAmbiguousCommands=false`: היא לא יכולה להעביר שורה שמכילה `"` או
שמסתיימת ב-`\`, ולכן Tazel דוחה פקודה כזו לפני שהיא מריצה אף אחד מהצעדים שלה.

המילים שאחרי `tazel custom` שייכות לפקודה, כדי ששום דבר בהן לא יהיה אפשרות של Tazel. השם הארוך ביותר שהן מתחילות בו
הוא הפקודה, והשאר הם הארגומנטים שלה. ‏`--` מסיים את השם: עם הפקודות `first` ו-`first second`,
‏`tazel custom first second` מריצה את `first second`, ו-`tazel custom first -- second` מריצה את `first` עם הארגומנט
‏`second`. רק ה-`--` הראשון עושה זאת, והוא עצמו אינו ארגומנט; מאוחר יותר הוא כן, ושם לא יכול להכיל אותו. יש לכל היותר
191 מילים, כולל אלה של השם ובלי אותו `--`. פקודה מקבלת בדיוק כמה ארגומנטים כמו ה-`<N>` הגבוה ביותר שלה, או יותר
עם `<*>`. ‏`<N>` ו-`<*>` אינם מחרוזות ועומדים מחוץ למירכאות; הם באים אחרי התוכנית ואי אפשר להשתמש בהם בתוך `s(...)`.

צעד שנכשל מסיים את הפקודה, ו-`tazel custom` יוצאת עם קוד היציאה שלו. בלי שם היא מציגה את רשימת הפקודות.

## אפשרויות של המחשב הזה

‏`tazel_options.txt` מחזיק אפשרויות של Tazel עצמה ולא של פרויקט. ‏Tazel קוראת כל קובץ כזה בתיקייה הנוכחית ובתיקיות
שמעליה: הקובץ הקרוב ביותר קובע כל אפשרות, אלא ש-`sandboxing-with-microvm: true` באחד מהם תקף, כך שפרויקט לא יכול לכבות
ארגז חול שתיקייה סביבו מבקשת. קובץ שאי אפשר לבחון או לקרוא עוצר את הפקודה, כמו קובץ פגום. הוא משתמש בהערות
ובמחרוזות של `tazel_custom.txt`; כל אפשרות מסתיימת ב-`;`, שהאחרונה יכולה להשמיט. אפשרות שלא נכתבה שומרת על ברירת
המחדל שלה.

```text
# Run what a project brings inside a MicroVM.
sandboxing-with-microvm: true;
microvm-network: true;
microvm-memory: 2048;
microvm-cpus: "auto"
```

| אפשרות | ערך | ברירת מחדל |
| --- | --- | --- |
| `sandboxing-with-microvm` | `true` או `false` | `false` |
| `microvm-network` | `true` או `false` | `false` |
| `microvm-memory` | ‏MiB מ-256 עד 1048576, או `"auto"` | `"auto"` |
| `microvm-cpus` | 1 עד 256, או `"auto"` | `"auto"` |

אפשר לכתוב את `"auto"` עם כל אחת משלוש המירכאות; מספרים ו-`true`/`false` נכתבים בלעדיהן.

עם `sandboxing-with-microvm: false`, קובץ הפרויקט והתוספים שלו רצים ב-JVM של Tazel עם כל ההרשאות של המשתמש שהפעיל אותה,
ופקודות מותאמות, המהדר והכלים רצים כתהליכים של מערכת המארח, לא ב-MicroVM.

‏`sandboxing-with-microvm: true` מבקש שכולם ירוצו בתוך MicroVM של וירטואליזציה בחומרה, עבור `tazel build` כמו עבור
‏`tazel custom`. ל-Tazel אין MicroVM להפעיל, ולכן היא עוצרת כל פקודה חוץ מ-`version` ו-`help`, כולל פקודות ה-daemon,
עם קוד יציאה `1` לפני שמשהו רץ, במקום להריץ אותה במערכת המארח.

## עדיין לא מומש

אלה נדחים בשמם עם קוד יציאה `1`:

- יעדי ספרייה: המהדר עדיין לא יכול לכתוב ספרייה. ספרייה שנמצאת לצד קובץ הרצה מדולגת עם אזהרה; ספרייה שנבחרה בשמה היא
  שגיאה.
- פרויקטים עם תלויות: עדיין שום דבר לא מוריד תלות ולא מעביר אותה למהדר. ‏`tazel lock resolve` עדיין רושמת את מה
  שהפרויקט מצהיר עליו.
- ‏`tazel vipkg create`, ‏`tazel update`, ‏`tazel install`, ‏`tazel viget push`, ‏`tazel viget update`
  ו-`tazel viget vipkg-desc`.

‏`check`, ‏`build` ו-`run` מהדרות עבור המארח. ה-`targets` של קובץ הפרויקט נרשמים ולא נבנים.
