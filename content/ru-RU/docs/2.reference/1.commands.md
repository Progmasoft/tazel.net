Tazel запускает инструменты проекта как отдельные программы: Talac, `talafmt` и `talalint` для целей Tala и программы,
которые называют шаги плагинов. Командные строки инструментов Tala описаны у них самих:
[Talac](https://talac.tala.run/docs/command-line), а также README [talafmt](https://github.com/Progmasoft/talafmt) и
[talalint](https://github.com/Progmasoft/talalint). Коды выхода общие: `0` — успех, `1` — работа не удалась, `2` — неверна
сама командная строка. `tazel run` передаёт код выхода запущенной программы.

```text
tazel [output options] <command> [arguments]
```

`tazel` работает с проектом, к которому относится текущий каталог: ближайшим каталогом вверх, в котором есть
[файл проекта](/docs/reference/project-file).

| Команда | Что она делает |
| --- | --- |
| `tazel check` | проверяет исходники, не записывая исполняемый файл |
| `tazel build` | собирает цели |
| `tazel run [-- arguments]` | собирает один исполняемый файл и запускает его |
| `tazel test` | собирает и запускает наборы тестов |
| `tazel fetch` | заранее загружает зависимости: плагины из ViGet в `.tazel/plugins`; завершается ошибкой, если локального пакета нет или объявлен пакет ViGet, потому что ViGet пока не раздаёт пакеты Tala |
| `tazel custom [name] [arguments]` | выполняет команду из `tazel_custom.txt` или выводит их список; см. [собственные команды](#собственные-команды) |
| `tazel lock resolve` | разрешает зависимости и обновляет `LOCK.sqlite3` |
| `tazel lock create-dump [--path File]` | записывает lock-файл текстом в `LOCK.dump` или в файл, который называет `--path` |
| `tazel lock graph [options]` | выводит граф зависимостей; обновляет `LOCK.sqlite3`, если не указан `--locked` |
| `tazel update` | обновляет зависимости системы и проекта |
| `tazel install [--global \| -g] Publisher.Name` | загружает пакет из ViGet в проект или в систему |
| `tazel vipkg create` | записывает локальный `.vipkg` для каждой цели, без тестов и публикации |
| `tazel viget push` | собирает, тестирует и впервые публикует пакет в ViGet |
| `tazel viget update` | собирает, тестирует и публикует новую версию пакета |
| `tazel viget vipkg-desc Publisher.Name` | выводит описание (`project.description`) пакета из ViGet |
| `tazel fmt [-- options]` | форматирует исходники с помощью `talafmt` |
| `tazel lint [--workspace] [-- options]` | проверяет исходники с помощью `talalint` |
| `tazel jvm start-daemon` | запускает демон JVM, который держит Tazel прогретым между командами |
| `tazel jvm restart-daemon` | останавливает демон и запускает его снова |
| `tazel jvm stop-daemon` | останавливает демон |
| `tazel version` | выводит версию Tazel |
| `tazel help [command]` | выводит справку или справку по одной команде |

`tazel check` запускает Talac с `--emit=metadata` и параметрами компилятора из файла проекта. `tazel build` запускает его
с `--emit=executable` и перемещает результат в выходной каталог режима сборки под именем цели, вместе с TalaRT, если
Talac оставил разделяемую библиотеку.

## Инкрементные сборки

`check`, `build`, `run` и `test` запускают Talac, только если изменилось то, что определяет его результат: содержимое или
имена исходников, настройки файла проекта или компилятор. Talac компилирует исходники цели как одну программу, поэтому
единица — это цель: один изменённый исходник перекомпилирует всю цель, а остальные цели не трогаются.

```text
   Compiling Demo (Demo, 12 sources)
    Finished build in 4.21s

       Fresh Demo (Demo, 12 sources)
    Finished build in 0.31s
```

Важно содержимое, а не время, поэтому файл, которого только коснулись, ничего не меняет. Компилятор узнаётся по версии и
содержимому его файлов, и система и архитектура хоста тоже учитываются, поэтому у двух машин с одним компилятором, одними
исходниками и одними настройками одинаковые результаты; блок [`buildCache`](/docs/reference/project-file#buildcache)
файла проекта может делить их через сервер. Результаты хранятся в `.tazel/cache` проекта, по умолчанию последние восемь
для каждой цели, поэтому возврат к прежней ветке или режиму сборки показывает `Restored` и ничего не компилирует.
Удалённая или изменённая программа возвращается так же. Предупреждения запуска, создавшего результат, показываются снова
при каждом его использовании. Неудачный запуск не оставляет результата. Шаги плагинов не пропускаются: они выполняются в
каждой сборке до чтения исходников, поэтому то, что они генерируют, учитывается.

Запуск сообщает, почему он запущен, — это первое, что стоит спросить о долгой сборке:

```text
   Compiling Demo (Demo, 12 sources) Sources/Math.tala changed
   Compiling Demo (Demo, 13 sources) Sources/New.tala added
   Compiling Demo (Demo, 12 sources) Sources/Math.tala changed, and 2 more
   Compiling Demo (Demo, 12 sources) the settings changed
   Compiling Demo (Demo, 12 sources) the compiler changed
```

Последняя строка команды подсчитывает, что сэкономил кэш: `Finished build, 3 of 4 from the cache in 2.10s`.

`--no-cache` всё равно выполняет работу и при этом записывает результат. `.tazel/cache` можно удалить в любой момент.

## Обслуживание кэшей

| Команда | Что она делает |
| --- | --- |
| `tazel cache status` | показывает для каждого проекта workspace, что хранит его локальный кэш, по целям, и в каком состоянии его удалённый кэш: доступ, подписи и отвечает ли он |
| `tazel cache clean` | удаляет `.tazel/cache` каждого проекта workspace; удалённый кэш не трогается |
| `tazel cache push` | отправляет то, что есть в локальных кэшах и чего нет на сервере; нужен `write = true` |
| `tazel cache pull [selection]` | загружает результаты для исходников в их текущем виде: сборок, проверок, наборов тестов и успешно пройденных наборов. Ничего не компилируется, поэтому следующая сборка находит их, в том числе без сети |

Сервер не хранит списка своих результатов, и `pull` он не нужен, потому что ключи следуют из исходников. `pull`
запрашивает каждый результат отдельно и подсчитывает найденное: `Pulled 3 of 6 results`. Результат, который ещё никто не
собрал, — не ошибка.

## Сервер удалённого кэша

`tazel cache serve` хранит результаты [удалённого кэша](/docs/reference/project-file#buildcache) в каталоге:

```text
tazel cache serve --directory /var/cache/tazel --port 7723 --max-size 50
```

| Параметр | По умолчанию | Действие |
| --- | --- | --- |
| `--directory` | обязателен | где хранятся результаты |
| `--host` | `127.0.0.1` | адрес, на котором он слушает |
| `--port` | `7723` | порт, на котором он слушает |
| `--max-size` | `10` | сколько гигабайт он хранит; первыми удаляются результаты, использованные давнее всего |

`TAZEL_CACHE_TOKEN` — токен, нужный для `PUT`; без него сервер не принимает результаты. `TAZEL_CACHE_READ_TOKEN`, если
задан, — токен, нужный для `GET`. Токены не передаются в командной строке, где их могли бы прочитать другие
пользователи.

Сервер говорит на простом HTTP. Для других машин он стоит за прокси с TLS, потому что Tazel требует `https` для любого
адреса, кроме этой машины. Он ничего не смотрит внутри результата; подлинность результата решает читатель по его
подписи, поэтому доверять в этом серверу не нужно.

`tazel cache keygen` выводит новую пару ключей для файла проекта.

Кроме `GET` и `PUT` он отвечает на `HEAD`, с помощью которого `tazel cache push` узнаёт, что уже есть.

## Наборы тестов

`tazel test` собирает и запускает каждый набор тестов выборки, один за другим:

```text
   Compiling Unit (Demo, 14 sources)
     Testing Unit (Demo)
PASS Math.Adds
Tests/Unit/MathTests.tala:9:9: expectation failed: Math.Clamp(50, 0, 10) == 9
    Math.Clamp(50, 0, 10) is 10
FAIL Math.Clamps (1 failed expectation)
2 tests, 1 passed, 1 failed
error: 1 suite, 2 tests, 1 passed, 1 failed: 'Unit' failed
```

Набор компилируется `talac --test` из того, что компилирует выборка, — исполняемых файлов и библиотек, — за которыми идут
исходники его `testDir`. Исходники, лежащие в `testDir` любого набора, исключаются из первой части, поэтому набор никогда
не видит тестов другого. Исполнитель записывается в `.tazel/tests/<suite>/` и запускается в каталоге проекта, где тест
находит свои файлы по путям относительно проекта.

`tazel test` нужен Talac с `--test`. Набор без исходника `.tala` — ошибка, поэтому опечатка в `testDir` не может пройти
незаметно. Упавший тест не останавливает следующие наборы; набор, который не компилируется, завершает команду. Код выхода
равен `1`, если тест упал, а также если исполнитель остановился до того, как записал итоги, каким бы ни был его код
выхода.

Пройденный набор не запускается снова, пока всё, что он может видеть, остаётся прежним: его исходники, настройки,
компилятор и каждый файл в его `testDir`, включая файлы данных. Тогда он показывает `Cached` и учитывается в итогах.
Упавший набор всегда запускается снова, и первым, поэтому ответ о том, над чем идёт работа, приходит раньше остального.
Тесту, который читает что-то ещё, например файл вне проекта или сеть, нужен `--no-cache`; как и запуску в CI, который
должен доказать, что тесты проходят.

## Выбор целей

`check`, `build`, `run`, `test` и `lint` принимают выборку. Без неё они работают со всем. Для `test` выборка определяет
проекты и исходники, с которыми компилируются наборы; запускается каждый набор выбранного проекта.

```text
tazel build --vipkg Name          tazel build -p Name
tazel build --executable Name     tazel build -e Name
tazel build --library Name        tazel build -l Name
```

Каждый флаг можно написать несколько раз, а виды можно сочетать; варианты записи показаны в разделе
[Запись параметров](#запись-параметров). `--vipkg` оставляет названные ViPkg; как только написан `--executable` или
`--library`, остаются только названные цели. Имя, которое ничего не выбирает, — ошибка.

`tazel run` собирает и запускает ровно один исполняемый файл, поэтому принимает не больше одного `--vipkg` и одного
`--executable` и не принимает `--library`. Без `--executable` он запускает единственный исполняемый файл выборки; если их
несколько, он запускает `project.defaultRun` того единственного выбранного ViPkg, который его задаёт. Всё остальное —
ошибка со списком исполняемых файлов, и ничего не собирается.

```text
tazel run                    # the only executable, or project.defaultRun
tazel run -p App             # the same, within App
tazel run -p App -e Server   # Server of App
```

## Запись параметров

Параметр принимает значение в любой из этих записей; короткие работают так же для `-p`, `-l` и `-i`, а длинные — для
любого параметра со значением, например `--path`, `--invert` и `--depth`:

```text
tazel build -eFirst -eSecond                 # short, joined
tazel build -e First -e Second               # short, after a space
tazel build -e=First,Second                  # short, after =
tazel build -e:First,Second                  # short, after :
tazel build --executable First --executable Second
tazel build --executable=First,Second
tazel build --executable:First,Second
```

После `=` или `:` параметр, который можно писать несколько раз, принимает список через запятую; слитно или после пробела
значение — одно имя, поэтому `-e First,Second` отклоняется. Значение параметра, который пишется один раз, — всё после
первого `=` или `:`, поэтому `--path=C:\Locks\old.sql` сохраняет своё двоеточие. Значение после пробела не может
начинаться с `-`, а флаг без значения, например `--locked`, значение не принимает: `--locked=yes` — ошибка. Подсказка
к опечатке в значении записывается так, как был записан параметр: `--color:awlyas` предлагает `--color:always`.

## Параметры вывода

Их можно ставить где угодно до `--`, до команды или после неё:

| Параметр | Действие |
| --- | --- |
| `--color always\|auto\|never` | цвета. `auto`, по умолчанию, использует их на терминале, который их поддерживает; `always` — также в конвейере или в CI |
| `--progress always\|auto\|never` | индикатор прогресса. `auto`, по умолчанию, рисует его на интерактивном терминале, который умеет двигать курсор; `always` рисует его везде |
| `--quiet` | убирает строки состояния и индикатор прогресса, если его не запрашивает `--progress`. Предупреждения, ошибки и то, ради чего нужна команда, например граф `tazel lock graph` или вывод программы, которую запускает `tazel run`, по-прежнему выводятся |

```text
tazel --quiet build
tazel build --color=never --progress:never
```

## Запись lock-файла текстом

`tazel lock create-dump` записывает `LOCK.dump` рядом с файлом проекта. `--path` называет другой файл с любым именем и
расширением относительно каталога, в котором запущен `tazel`:

```text
tazel lock create-dump --path Locks.sql
tazel lock create-dump --path reviews/Locks.sql
```

Папка файла должна существовать. Tazel её не создаёт: папка с опечаткой даёт ошибку, а не оставляет дамп в неожиданном
месте. `--path`, который называет папку, тоже отклоняется.

## Граф зависимостей

`tazel lock graph` выводит, от чего зависит каждый проект. Граф — это то, что записано в lock-файле, поэтому
`LOCK.sqlite3` сначала записывается, если его нет или он больше не отражает то, что объявляет файл проекта. В корне
workspace каждый участник — корень графа.

```text
Demo
├── Publisher.Json 1.1.0 [by feature Json]
├── Publisher.Name 1.0.0
├── Local.vipkg (local)
└── [test]
    └── Publisher.Name 2.0.0
```

Зависимость, которую подключает фича проекта (`feature = "Json"`), показывается, когда эта фича включена, что по
умолчанию означает, что она входит в `defaultFeatures` проекта.

| Параметр | Действие |
| --- | --- |
| `--locked` | оставляет `LOCK.sqlite3` как есть; отсутствующий или устаревший lock-файл — ошибка |
| `--all-features` | включает все фичи проекта |
| `--duplicates`, `-d` | показывает только пакеты ViGet, которые есть в нескольких версиях, каждый с его зависимыми |
| `--invert Package`, `-i Package` | показывает проекты, которые зависят от одного пакета |
| `--depth Levels` | выводит не больше указанного числа уровней под каждым корнем; `0` выводит только корни |

`--duplicates` и `--invert` нельзя писать вместе. Что называет `--invert`, зависит от того, как он записан:

| Запись | Смысл |
| --- | --- |
| `MyPackage` | каждый проект в текущем каталоге и ниже, у которого `project.name` равен `MyPackage`. Его зависимые — проекты там, которые используют пакет ViGet с этим именем от любого издателя или локальный `MyPackage.vipkg`. Папки, имя которых начинается с точки, не просматриваются. |
| `Publisher.Name` | этот пакет ViGet во всех версиях, которые объявляют проекты |
| `Libraries/Name.vipkg` | этот локальный пакет. Слово, оканчивающееся на `.vipkg`, всегда означает локальный пакет. |

Tazel пока не загружает пакеты из ViGet, поэтому пакет ViGet показывается без собственных зависимостей.

## Вывод

Tazel печатает строку состояния для каждого шага, например `Compiling Demo (Demo, 3 sources)`, и завершает команду
временем, которое она заняла: `Finished build in 1.84s`; `--quiet` их убирает. Пока `check`, `build`, `run`, `fmt` и
`lint` обрабатывают свои цели на интерактивном терминале, индикатор прогресса под строками состояния показывает текущий
шаг, сколько выполнено и сколько прошло времени; вывод `talac`, `talafmt` и `talalint` тогда печатается над индикатором.
В конвейере, в CI или на терминале, который не умеет двигать курсор, индикатор не рисуется, и инструменты пишут прямо в
терминал; `--progress` и `--color` меняют это. Программа, которую запускает `tazel run`, всегда пишет напрямую. Вывод в
терминал использует Mordant.

## Опечатки

Неизвестная команда, действие, флаг или имя цели отклоняются с кодом выхода `2` (`1` для имени цели, которое проверяется
по проекту). Если слово близко к известному, подсказка под ошибкой говорит, что, вероятно, имелось в виду, с коротким
замечанием:

```text
error: 'biuld' is not a command of tazel; write tazel help for the commands
 hint: did you mean tazel build? So close the keys almost had it.
```

Сначала сравнивается регистр, поэтому `Build` предлагает `build`; иначе для короткого слова допускается одна правка, а
для длинного — две, причём две переставленные буквы считаются одной правкой.

## Передача аргументов

Всё после `--` непрочитанным передаётся программе, которую запускает команда:

```text
tazel run -- --port 8080           # to the program that was built
tazel fmt -- --check               # to talafmt
tazel lint -- --fix                # to talalint
tazel lint --workspace -- --fix
```

## Workspace

В корне workspace `build`, `check`, `run` и `test` работают с каждым участником. `fmt` и `lint` работают с участниками по
умолчанию, если workspace их называет, а иначе с корнем; `tazel lint --workspace` проверяет каждого участника. Внутри
каталога участника проектом является этот участник.

## Поиск инструментов

Инструмент ищется в трёх местах в таком порядке: путь, который называет `TAZEL_TALAC`, `TAZEL_TALAFMT` или
`TAZEL_TALALINT`; установка, из которой запущен `tazel`; каталоги из `PATH`.

## Плагины

Плагин, который проект объявляет через `plugin("Publisher") { ... }`, ищется в кэше плагинов проекта, `.tazel/plugins`.
Если в кэше нет подходящей версии, Tazel загружает его из ViGet в `.tazel/plugins/<Publisher>/<Name>/<Version>/` и
проверяет его SHA-256 по индексу плагина; последующие запуски используют кэш, не обращаясь к ViGet. `TAZEL_VIGET_URL`
заменяет адрес ViGet, `https://viget.progmasoft.com`, для зеркала. См. [Как написать плагин](/docs/extending/plugins).

`build` и `run` выполняют шаги, которые плагины добавляют в сборку проекта, до компиляции его целей Tala; `check` и
`test` их не выполняют.

## Скомпилированные файлы проекта

Первый запуск компилирует файл проекта; последующие загружают скомпилированный скрипт из кэша и только вычисляют его.
Запись используется, только если одинаково всё, от чего зависит компиляция: текст и имя скрипта, версия компилятора
Kotlin, цель JVM, импорты и параметры компилятора по умолчанию, classpath Tazel и SHA-256 каждого JAR плагина. Иначе
файл компилируется заново. Запись, которую нельзя прочитать, считается отсутствующей. Кэш хранит 256 последних
использованных записей.

Кэш находится в `TAZEL_CACHE_DIR`, если переменная задана, иначе в `%LOCALAPPDATA%\Progmasoft\Tazel\Cache` в Windows,
`~/Library/Caches/Progmasoft/Tazel` в macOS и `$XDG_CACHE_HOME/progmasoft/tazel` (`~/.cache/progmasoft/tazel`) в
остальных системах. Удалять его всегда безопасно.

## Демон JVM

Каждый `tazel` запускает JVM, и первый файл проекта, который он вычисляет, загружает компилятор Kotlin и скриптовый хост.
Демон — это JVM, которая остаётся запущенной и выполняет команды вместо этого, поэтому эти классы загружаются один раз.
Он не заменяет кэш скомпилированных файлов проекта; команда в демоне тоже использует кэш.

`tazel jvm start-daemon` запускает его, если он ещё не запущен. `tazel jvm stop-daemon` даёт выполняемым командам
завершиться, не дольше минуты, и останавливает его; демон, который не отвечает, завершается принудительно.
`tazel jvm restart-daemon` делает и то и другое. Эти три команды всегда выполняются в процессе, который их прочитал.

Пока демон запущен, каждая другая команда идёт к нему и выводит то, что вывела бы сама. Демон выполняет команду с
аргументами, рабочим каталогом, окружением и терминалом клиента, а программы, которые он запускает, читают то, что
вводится в клиенте. У каждой команды свои контексты проектов, поэтому можно обслуживать несколько клиентов одновременно;
одновременно выполняется не больше восьми команд, остальные ждут. `TAZEL_DAEMON` определяет, когда команда идёт к демону:

| `TAZEL_DAEMON` | Команда |
| --- | --- |
| `auto` (по умолчанию) | идёт к демону, если он запущен, иначе выполняется напрямую |
| `start` | идёт к демону, который сначала запускается, если его нет |
| `off` | всегда выполняется напрямую |

Демон обслуживает одного пользователя и одну установку. Его файлы находятся в `TAZEL_DAEMON_DIR`, если переменная
задана, иначе в каталоге `daemon` в `%LOCALAPPDATA%\Progmasoft\Tazel` в Windows,
`~/Library/Application Support/Progmasoft/Tazel` в macOS и `$XDG_STATE_HOME/progmasoft/tazel`
(`~/.local/state/progmasoft/tazel`) в остальных системах: Unix-сокет, токен, блокировка, идентификатор процесса и журнал.
Каталог доступен для чтения только пользователю, и клиент должен предъявить токен, который демон там записал. Клиент
другой версии или протокола отклоняется и выполняет команду напрямую; у другой установки, версии или среды Java свой
демон. Блокировка не даёт запуститься второму демону той же установки, а файлы умершего демона удаляет следующий клиент.

Демон останавливается сам после `TAZEL_DAEMON_IDLE_MINUTES` без клиентов, по умолчанию 180; `0` оставляет его
работающим. Его куча ограничена `TAZEL_DAEMON_MAX_HEAP` (по умолчанию `2g`), а метаданные классов — 1 ГиБ; демон, которому
не хватает одного из них, завершается, и следующая команда выполняется напрямую или запускает новый. Если клиент уходит
посреди команды, запущенные командой программы останавливаются.

## Время фаз

С `TAZEL_TIMINGS=1` Tazel печатает в стандартный поток ошибок, сколько заняла каждая фаза запуска: запуск JVM, скриптовый
хост Kotlin, разрешение плагинов и загрузка классов, компиляция скрипта или его загрузка из кэша, вычисление скрипта и
вся команда. Команда, выполненная в демоне, показывает также IPC: время между отправкой команды и её окончанием, которое
демон не потратил на команду. Запуск JVM тогда — это запуск клиента.

## Использование машины

`check`, `build`, `run` и `test` принимают эти флаги. Они имеют приоритет над
[блоком `execution`](/docs/reference/project-file#execution) файла проекта, а блок корня workspace действует на весь
workspace.

| Флаг | Что он делает | По умолчанию |
| --- | --- | --- |
| `--jobs`, `-j Number` | сколько запусков компилятора и наборов тестов выполняется одновременно | число процессоров или `--cpus` |
| `--cpus Number` | сколько процессоров команда может занять; задач никогда не больше | все процессоры |
| `--memory Size` | сколько задачи могут занимать вместе, например `8g` | без ограничения |
| `--memory-per-job Size` | сколько, по расчёту, занимает одна задача; `--memory`, делённое на это, ограничивает задачи | `1g` |
| `--keep-going`, `-k` | продолжать другие задачи после неудачи одной и сообщать о каждой неудаче | остановиться |
| `--incremental`, `--no-incremental` | в отладочной сборке хранить объект на каждый исходник в `.tazel/incremental` | включено, если talac это умеет |
| `--profile File` | записать трассировку задач в формате Chrome для `chrome://tracing` или Perfetto | нет |
| `--remote-executor URL` | компилировать на другой машине; `TAZEL_REMOTE_TOKEN` — её токен | нет |
| `--no-remote-executor` | компилировать здесь, что бы ни говорил файл проекта | |

Память и процессоры — это бюджеты на то, сколько задач запускается. Tazel не измеряет компилятор и не останавливает тот,
что занимает больше `--memory-per-job`, а одна задача выполняется всегда. Запуски Talac, которые пишут рядом с одним и тем
же каталогом исходников, идут по очереди, потому что talac оставляет результат рядом с первым входным файлом, поэтому
наборы тестов одного проекта компилируются по одному, а затем запускаются одновременно. Набор тестов, который
выполняется рядом с другими, выводит свой отчёт по завершении.

`tazel jvm start-daemon --max-heap 2g` и `restart-daemon --max-heap 2g` ограничивают кучу демона, как и
`TAZEL_DAEMON_MAX_HEAP`.

### Удалённое выполнение

`tazel remote serve` компилирует для других машин:

```text
TAZEL_REMOTE_TOKEN=... tazel remote serve --host 127.0.0.1 --port 7724 --jobs 8
```

Токен обязателен. Сервер говорит на простом HTTP, поэтому для других машин он стоит за прокси с TLS, чего Tazel и
требует от такого адреса. Он только запускает talac на присланных исходниках в отдельном каталоге и отклоняет запрос,
параметры которого указывают на место на его машине.

Клиент отправляет исходники и параметры запуска компилятора и получает обратно то, что talac сказал и записал. Результаты
попадают в кэш сборки как локальные, а программы и наборы тестов всегда выполняются на этой машине. Сервер с другой версией
talac или другим видом хоста отвечает, что не может помочь. В этом случае, или если сервер даёт сбой, Tazel один раз
предупреждает и до конца команды компилирует здесь. Тот, кто владеет сервером, решает, какие программы вы получите,
поэтому используйте только тот, которому доверяете.

## Собственные команды

`tazel custom` выполняет команды, записанные в `tazel_custom.txt`, который ищется в текущем каталоге или ближайшем выше.
Файл проекта не нужен, команды не обязаны использовать Tazel, и они выполняются в каталоге файла.

```text
# A comment to the end of the line.
<# A comment
   of several lines. #>

build-no-cache: ("tazel" 'build' `--no-cache`);
npm-dev: ('npm' 'dev');

# Several steps run in order; line breaks mean nothing.
fetch:
    ("cargo" "fetch")
    ("tazel" "fetch");

# s(...) is one command line for the shell of the host.
npm-dev-sh: s('npm dev');

fetch-sh:
    s("cargo fetch")
    ("tazel" "fetch");

# Another shell is a program like any other.
npm-dev-zsh: ("zsh" "-lc" "npm dev");

# A name may hold several words.
build no-cache: ("tazel" "build" "--no-cache");

# <N> passes the Nth argument, from 1; <*> passes all of them.
build with: ("tazel" "build" <1> <2>);
test all: ("tazel" "test" <*>);
```

```text
tazel custom fetch
tazel custom build no-cache
tazel custom build with -e MyApp
```

Строка записывается в `"`, `'` или `` ` `` и не имеет экранирования, поэтому не может содержать собственную кавычку, а
обратная косая черта в ней — это обратная косая черта. `(...)` запускает программу напрямую с этими аргументами: оболочки
нет, поэтому слово вроде `|` не значит ничего особенного, и каждая строка остаётся одним аргументом. В Windows программой
может быть скрипт, например `npm.cmd`. `s(...)` принимает ровно одну строку и передаёт её без изменений CMD в Windows и
`sh` в остальных системах; экранирование в ней читает эта оболочка. Единственное исключение — JVM, запущенная в Windows с
`jdk.lang.Process.allowAmbiguousCommands=false`: она не может передать строку, которая содержит `"` или оканчивается на
`\`, поэтому Tazel отклоняет такую команду до выполнения любого из её шагов.

Слова после `tazel custom` принадлежат команде, чтобы ничто в них не стало параметром Tazel. Самое длинное имя, с которого
они начинаются, — это команда, а остальное — её аргументы. `--` завершает имя: при командах `first` и `first second`
`tazel custom first second` выполняет `first second`, а `tazel custom first -- second` выполняет `first` с аргументом
`second`. Так действует только первый `--`, и сам он аргументом не является; последующий является, и имя не может его
содержать. Слов не больше 191, включая слова имени и не считая этого `--`. Команда принимает ровно столько аргументов,
сколько её наибольший `<N>`, или больше с `<*>`. `<N>` и `<*>` — не строки и стоят вне кавычек; они идут после программы и
не могут использоваться в `s(...)`.

Неудачный шаг завершает команду, и `tazel custom` завершается с его кодом выхода. Без имени она выводит список команд.

## Параметры этой машины

`tazel_options.txt` содержит параметры самого Tazel, а не проекта. Tazel читает каждый такой файл в текущем каталоге и в
каталогах выше: ближайший файл определяет каждый параметр, но `sandboxing-with-microvm: true` в любом из них действует,
чтобы проект не мог отключить песочницу, которую требует окружающий его каталог. Файл, который нельзя проверить или
прочитать, останавливает команду, как и повреждённый. Он использует комментарии и строки `tazel_custom.txt`; каждый
параметр заканчивается на `;`, что можно опустить у последнего. Параметр, который не записан, сохраняет значение по
умолчанию.

```text
# Run what a project brings inside a MicroVM.
sandboxing-with-microvm: true;
microvm-network: true;
microvm-memory: 2048;
microvm-cpus: "auto"
```

| Параметр | Значение | По умолчанию |
| --- | --- | --- |
| `sandboxing-with-microvm` | `true` или `false` | `false` |
| `microvm-network` | `true` или `false` | `false` |
| `microvm-memory` | МиБ от 256 до 1048576 или `"auto"` | `"auto"` |
| `microvm-cpus` | от 1 до 256 или `"auto"` | `"auto"` |

`"auto"` можно записать в любых из трёх кавычек; числа и `true`/`false` пишутся без них.

С `sandboxing-with-microvm: false` файл проекта и его плагины выполняются в JVM Tazel со всеми правами пользователя,
который её запустил, а собственные команды, компилятор и инструменты выполняются как процессы хост-системы, а не в
MicroVM.

`sandboxing-with-microvm: true` требует, чтобы всё это выполнялось внутри MicroVM с аппаратной виртуализацией, как для
`tazel build`, так и для `tazel custom`. У Tazel нет MicroVM, которую можно запустить, поэтому он останавливает каждую
команду, кроме `version` и `help`, включая команды демона, с кодом выхода `1` до того, как что-либо выполнится, вместо
того чтобы выполнить её в хост-системе.

## Пока не реализовано

Это отклоняется по имени с кодом выхода `1`:

- цели-библиотеки: компилятор пока не умеет записывать библиотеку. Библиотека рядом с исполняемым файлом пропускается с
  предупреждением; библиотека, выбранная по имени, — ошибка.
- проекты с зависимостями: пока ничто не загружает зависимость и не передаёт её компилятору. `tazel lock resolve` всё
  равно записывает то, что объявляет проект.
- `tazel vipkg create`, `tazel update`, `tazel install`, `tazel viget push`, `tazel viget update` и
  `tazel viget vipkg-desc`.

`check`, `build` и `run` компилируют для хоста. `targets` файла проекта записываются, но не собираются.
