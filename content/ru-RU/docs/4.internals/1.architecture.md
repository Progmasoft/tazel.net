Tazel — одна программа на Kotlin для JVM. Она читает файл проекта, решает, что компилировать, и запускает для работы
другие программы: Talac компилирует цели Tala, `talafmt` форматирует, `talalint` проверяет, а плагины запускают
инструменты, которые называют их блоки. Tazel никогда не компонуется с ними и не делит с ними код; она передаёт
аргументы, ждёт код выхода и перемещает файлы, которые они оставляют.

Эта страница прослеживает одну команду от терминала до компилятора и называет код, которому принадлежит каждый шаг.

## Команда шаг за шагом

```text
tazel build -e Server
  │
  ├─ parseCommandLine         cli/CommandLine.kt   words → a typed Command, or a usage error (exit 2)
  ├─ Tazel.run                cli/Tazel.kt         one branch per command; every failure becomes exit 1
  ├─ discoverProject          dsl/ProjectLoader.kt the nearest project file, upward from the current directory
  ├─ loadWorkspace            driver/Packages.kt   the project, and the members when it is a workspace
  │    └─ ProjectLoader.load  dsl/ProjectLoader.kt plugins first, then the script → a ProjectPlan
  ├─ select                   driver/Packages.kt   the selection (-p, -e, -l) applied to the plan
  ├─ keepLockCurrent          cli/Tazel.kt         LOCK.sqlite3 rewritten when it no longer matches
  ├─ SourceFiles.discover     driver/SourceFiles.kt every .tala file below srcDir, minus the exclusions
  ├─ compilerArguments        driver/CompilerCommand.kt the settings of the plan as talac options
  ├─ Toolchain.require        driver/Toolchain.kt  where talac is
  └─ Processes.run            driver/Processes.kt  talac starts; its exit code decides the step
```

### 1. Командная строка

`parseCommandLine` написан вручную; Tazel не использует библиотек для командной строки. Он читает слова один раз и
возвращает либо `Command` (sealed interface с отдельным типом для каждой команды, который несёт её типизированные
аргументы), либо результат `Rejected` с сообщением и, для опечатки, подсказкой. Ни один последующий шаг больше не
смотрит на сырые аргументы. Отклонённая строка завершается кодом `2` до чтения какого-либо файла.

Параметр берёт значение из следующего аргумента, после `=` или `:` или, для короткого параметра, слитно с ним
(`--vipkg Name`, `--vipkg=Name`, `-p:Name`, `-pName`); после `=` или `:` повторяемый параметр принимает список. Параметры
вывода `--color`, `--progress` и `--quiet` извлекаются первыми, где бы они ни стояли до `--`, и передаются рядом с
командой как `OutputOptions`. Всё после `--` сохраняется непрочитанным для программы, которую запускает команда.

### 2. Поиск и выполнение файла проекта

`discoverProject` поднимается от текущего каталога и останавливается в первом каталоге, где есть одно из пяти имён файла
проекта. Имена сравниваются так, как они написаны, поэтому `build.kts` не является файлом проекта даже в Windows и macOS,
файловые системы которых иначе нашли бы его.

Затем `ProjectLoader.load` работает в две фазы:

1. **Плагины.** `PluginPreamble` читает только блок `plugins { }` файла, небольшими лексером и парсером, которые не
   выполняют никакого кода. `PluginResolver` находит каждый объявленный JAR в проекте или в его кэше плагинов, загружает
   недостающий из ViGet через `ViGetPlugins` (`dsl/plugin/PluginRegistry.kt`), проверяет его дескриптор и дайджест, а
   `PluginRuntime` активирует плагины. См. [Как написать плагин](/docs/extending/plugins).
2. **Скрипт.** Весь файл компилируется и выполняется встроенным в Tazel скриптовым хостом Kotlin
   (`BasicJvmScriptingHost`), с DSL и импортами плагинов в качестве импортов по умолчанию. Скомпилированный скрипт
   хранится в `ScriptCache` (`dsl/ScriptCache.kt`) под SHA-256 всего, от чего зависит его компиляция, поэтому следующий
   запуск пропускает компиляцию и только вычисляет его. Блоки скрипта заполняют `ProjectContext` этого вычисления; когда
   скрипт заканчивается, модель проверяется целиком и становится неизменяемым `ProjectPlan`. Проверки, зависящие от
   нескольких блоков, например поля, которых требует `sources.viget.push`, выполняются в этот момент, поэтому порядок
   блоков никогда не важен.

У каждого вычисления свой `ProjectContext`: модель, плагины проекта (`PluginState`) и то, что записал его блок
`project`. Файл проекта — это скрипт из вызовов верхнего уровня, поэтому `ProjectRuntime` привязывает контекст к потоку,
который вычисляет скрипт, и отвязывает после; `PluginRuntime`, который вызывают плагины, обращается к плагинам этого
контекста. Поэтому файлы проектов можно вычислять в нескольких потоках одновременно. Только компилятор Kotlin используется
одним вычислением за раз. Ошибка компиляции в скрипте сообщается с именем файла, строкой и столбцом; `panic(message)`
останавливает вычисление с этим сообщением.

### 3. Workspace и выбор

`loadWorkspace` загружает корневой проект и, если он объявляет `workspace`, каждого участника, который не исключён.
Каждый участник — отдельный проект и загружается так же. ViPkg называется по его `project.name` или, если его нет, по
его каталогу.

`select` применяет выбор команды. Без выбора он оставляет каждую цель, иначе завершается ошибкой с именем, которое ничего
не выбрало; при небольшой опечатке выводится подсказка «возможно, вы имели в виду».

### 4. Lock-файл

Перед компиляцией проекта Tazel сравнивает `LOCK.sqlite3` с тем, что объявляет план, и перезаписывает его, если они
различаются. Файл записывает объявления, а не разрешённый граф; см. [Lock-файл](/docs/reference/lockfile).

### 5. Исходники и компилятор

`SourceFiles.discover` обходит `srcDir`, не следуя по символическим ссылкам, и оставляет каждый файл, имя которого
оканчивается на `.tala`, написанное именно так. Шаблоны исключений сравниваются по сегментам пути; в Windows они не
учитывают регистр, как и файловая система. Результат сортируется, поэтому компилятор видит один и тот же порядок на любой
машине.

`compilerArguments` записывает каждую настройку компилятора из плана как параметр, в том числе со значением по
умолчанию. Тогда сборка следует только из файла проекта, а не из значений по умолчанию того `talac`, который установлен.
Входные файлы идут после `--`, поэтому файл с именем, похожим на параметр, всё равно читается как файл.

Talac записывает свой результат рядом с первым входным файлом. Tazel перемещает его в выходной каталог режима сборки под
именем цели, вместе с TalaRT, если Talac оставил его там, и завершается ошибкой, если компилятор сообщил об успехе и
ничего не оставил.

Перед запуском Talac Tazel хеширует аргументы, содержимое входных файлов, версию компилятора, а также размер и время
файлов, из которых он состоит. Результат запуска хранится в `.tazel/cache/<slug>/<key>` — каталоге, который
подготавливается в стороне и перемещается на место, поэтому он есть целиком или не есть вовсе. Кэш, который нельзя
прочитать или записать, — это предупреждение: компилятор запускается, и сборка продолжается. Вывод компилятора
собирается, а не передаётся терминалу, чтобы предупреждения запуска можно было показать снова, когда используется его
результат.

`tazel test` идёт тем же путём с `--test` вместо `--entry` и добавляет второй результат для каждого набора, ключ которого
включает также каждый файл тестового каталога и который записывает итоги успешного запуска.

### 6. Форматирование и проверка

`tazel fmt` и `tazel lint` загружают проект так же и запускают инструмент по одному разу на каждый ViPkg, с собственными
аргументами инструмента, затем `--`, затем каждым исходником, который принадлежит ViPkg. Тестовые исходники включаются,
когда команда выбирает всё. Инструменты читают собственные файлы конфигурации; Tazel их не интерпретирует.

## Ошибки и коды выхода

| Код выхода | Значение | Кто вызывает |
| --- | --- | --- |
| `0` | успех | |
| `1` | работа не удалась: неверный файл проекта, несуществующая цель, инструмент отклонил исходники | `ProjectConfigurationException`, `Stop`, `UnknownTargetException`, ошибка SQLite |
| `2` | неверна сама командная строка | `parseCommandLine` |

`tazel run` передаёт код выхода запущенной программы. Каждая ошибка выводится в стандартный поток ошибок одной строкой,
с строкой подсказки под ней, если она есть; для ошибки, которую пользователь может исправить, Tazel не выводит
трассировку стека.

## Вывод в терминал

Строки состояния (`Compiling`, `Checking`, `Finished`) идут в стандартный вывод, ошибки и предупреждения — в стандартный
поток ошибок, всё через Mordant. Пока на интерактивном терминале обрабатываются несколько целей, `StepProgress` рисует
индикатор прогресса; вывод инструментов тогда собирается и печатается над индикатором, а не поверх него. В конвейере или
в CI индикатор не рисуется, и инструменты пишут прямо в терминал. `outputTerminal` строит терминал, который запрашивают
`--color` и `--progress`, и в клиенте, и в демоне; `--quiet` убирает строки состояния.

## Демон

`main` сначала разбирает командную строку. `tazel jvm ...` обрабатывает `runDaemonCommand`; любую другую команду
`forwardToDaemon` предлагает демону, прежде чем выполнить её в процессе. `DaemonClient` подключается к Unix-сокету,
который называет `DaemonPaths`, представляется токеном, протоколом и версией (`DaemonProtocol.kt`) и отправляет
аргументы, рабочий каталог, окружение и то, что умеет показывать терминал. `DaemonServer` отвечает каждому клиенту в
отдельном потоке: он строит для запроса `Tazel` с `ForwardingTerminal` и `ForwardingProcesses`, которые отправляют вывод
клиенту и читают его ввод, и с `RoutedStream` вместо `System.out` и `System.err`, чтобы то, что печатает файл проекта,
доходило до клиента команды, которая его вычислила. Вывод возвращается кадрами, а последний кадр несёт код выхода и
время фаз. Демон запускает `DaemonMain` на среде Java и с classpath клиента.

## Швы для тестов

`Tazel` получает всё, что касается машины, как аргумент конструктора: терминал, рабочий каталог, операционную систему,
`Toolchain` (с собственным окружением и каталогом установки) и `Processes`. Тесты передают записывающий `Processes`,
который пишет файл, оставленный бы настоящим компилятором, поэтому целые команды выполняются над проектами на диске без
компилятора. См. [Contributing](https://github.com/Progmasoft/tazel/blob/main/CONTRIBUTING.md#tests).
